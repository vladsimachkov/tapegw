# ADR-0021. Протокол tapegw ↔ tapegw-mover

- **Статус:** принято
- **Дата:** 2026-11-05
- **Этап плана:** M4 (обязан быть принят до первой строки кода mover)
- **Связано:** [ADR-0007](0007-mover-worker.md) (mover как отдельный бинарь),
  [ADR-0020](0020-tape-record-format.md) (формат записи на ленту),
  [ADR-0006](0006-libphobos-linkage.md), [ADR-0008](0008-object-medium.md),
  [ADR-0013](0013-tape-pools.md), [ADR-0014](0014-encryption-per-tenant.md),
  спайки [M0-02](../spikes/M0-02-libphobos-api.md),
  [M0-05](../spikes/M0-05-eject-before-unload.md).

## Контекст

ADR-0007 решил, **что** mover — отдельный процесс с одним `phobos_init`, и
набросок протокола там один: «put батч UUID», «get батч UUID». Этого мало для
реализации, и дописывать протокол поверх существующих вызовов нельзя — он
повторит их один в один и перестанет быть границей.

Формат того, что ложится на ленту, зафиксирован в ADR-0020 отдельно: он меняется
только перезаписью ленты, а протокол — вместе с обоими бинарями и без миграции
данных.

Что должно следовать из решения, кроме самих команд:

- **реакция на смерть mover'а.** libltfs падает во время `mt offline`
  ([M0-07](../spikes/M0-07-mhvtl-ltfs.md)), а не возвращает ошибку. Значит
  «процесс умер» — штатное событие, и по нему нельзя делать вывод «операция не
  выполнилась»: батч мог записаться целиком до падения;
- **долгая операция.** Батч на 200 GiB идёт минуты и часы. Таймаут «на операцию
  целиком» либо бесконечный, либо рвёт нормальную работу;
- **атрибуты не выдумываются.** Набор атрибутов задаёт ADR-0020, считает их
  `tapegw` (`archive.Attributes`), а mover только кладёт. При этом именно mover
  знает, что LTFS не примет больше 4079 байт (M2-01), и узнать об этом после
  начала записи — значит получить `ENOSPC` в середине батча;
- **ключей у mover нет** (ADR-0007, ADR-0014), и это должно быть видно в
  протоколе, а не обеспечено внимательностью.

## Решение

### Транспорт: stdin/stdout, построчный JSON

Супервизор запускает mover дочерним процессом и общается с ним через его
stdin/stdout. Одно сообщение — одна строка JSON (NDJSON).

Выбор в пользу pipes, а не unix-сокета: **срок жизни соединения равен сроку жизни
процесса**. Обрыв pipes означает «mover умер» без heartbeat, без таймаута на
пропущенный heartbeat и без мусорного сокет-файла после `SIGKILL`. Один mover —
одна операция за раз (ADR-0007), поэтому мультиплексирование не нужно и
идентификаторы запросов в протоколе отсутствуют: в полёте ровно один запрос.

Данные по каналу **не ходят** никогда. Ходят только UUID, числа, короткие строки и
атрибуты. Тело объекта mover читает с диска сам.

Строка ограничена (`phobos.mover.max_line_bytes`, по умолчанию 1 MiB): батч из
2000 объектов с атрибутами в неё не должен влезать, и лучше честно отказать в
начале, чем раздуть буфер.

### Рукопожатие и версионирование

Сразу после запуска mover обязан отправить `hello`, до получения любой команды:

```json
{"t":"hello","proto":1,"mover":"0.4.0","phobos":"3.4.1"}
```

Супервизор требует точного совпадения `proto` (мажорная версия протокола) и
известную `mover`. Расхождение — не «попробуем работать», а отказ запускать:
несовместимый mover, отработавший полчаса на ленте, стоит дороже, чем не
поднятый пул. `phobos` записывается в логи и в метрику сборки — он объясняет
поведение постфактум.

### Команды

Запрос — `"t"`, ответ — `"r"` с тем же `"op"` (номер запроса от супервизора,
только для связки в логах; мультиплексирования по-прежнему нет).

| команда | назначение | ключевые поля запроса |
| --- | --- | --- |
| `put` | записать батч на ленту | `items[]` (`uuid`, `size`, `attrs`), `tags`, `no_split` |
| `get` | прочитать объект(ы) на диск | `items[]` (`uuid`) |
| `delete` | удалить объект в Phobos | `ids[]` |
| `stat` | проверить наличие и полноту | `ids[]` |
| `extents` | носитель(и) объектов | `ids[]` |

`extents` — это то, чем закрыли спайк M0-04: Locate в TLC-протоколе нет, носитель
узнаётся при архивации (ADR-0008). `store.Store.Locate` в терминах этого
протокола = `extents`.

### Идентификаторы вместо путей

**В протоколе нет ни одного пути.** mover вычисляет путь файла сам из UUID по
правилу раскладки спула, которое знает `tapegw` (ADR-0007). Это не
удобство, а граница: вместе с путём в протоколе появилась бы возможность
попросить mover прочитать что угодно, и проверять это пришлось бы в mover'е —
в процессе с cgo, который переживает падение основного.

Для пачки (ADR-0020) UUID пачки — такой же UUID, правило раскладки то же.

### Атрибуты проверяются до начала записи

mover обязан просуммировать размер JSON всех атрибутов каждого объекта и
отказать **до** обращения к ленте, если тот больше 4079 байт (замер M2-01):

```json
{"t":"r","op":7,"items":[{"uuid":"…","code":"attr_too_large","bytes":9120}]}
```

Причина не в аккуратности: `ENOSPC` от LTFS приходит в середине батча, а
`ENOSPC` в Phobos двусмысленен — так же отвечает «нет ленты с таким тегом»
([M0-08](../spikes/M0-08-phobos-tags.md)). Отказ по атрибутам должен быть
отличим от отказа по месту.

### Итог по каждому объекту

Батч может удалиться частично, поэтому итог — у каждого элемента, а не у
запроса. Коды замкнуты, новых mover не выдаёт:

| код | смысл | что делает воркер |
| --- | --- | --- |
| `ok` | записан и подтверждён | переход состояния |
| `not_found` | объекта нет в Phobos | `deleting` → `deleted`, либо ошибка |
| `no_space` | нет места **или** нет ленты с тегом | ретрай с экспоненциальным `next_try_at` |
| `busy` | Phobos/LRS занят | ретрай сразу, без `attempts+1` |
| `incomplete` | объект есть, копия неполная | ретрай; см. ниже |
| `attr_too_large` | атрибуты не влезут | ошибка конфигурации, алерт |
| `io` | ошибка чтения/записи | ретрай |
| `unknown` | итог неизвестен | перепроверка через `stat` |

`incomplete` — отдельный код, а не `io`, потому что `phobos_getmd` возвращает
объект и при `copy_status = incomplete` (спайк M0-02). Считать такой объект
заархивированным — значит потерять данные молча.

### Прогресс и таймаут бездействия

Во время долгой операции mover пишет строки прогресса:

```json
{"t":"progress","op":7,"done":41,"bytes":8589934592}
```

Супервизор считает не «таймаут на операцию», а **таймаут бездействия**
(`phobos.mover.inactivity_timeout`): если mover прислал хоть что-то за это
время, он жив. Ограничение на полную длительность отсутствует сознательно —
батч на 200 GiB имеет право идти часы, а сматка ленты и `umount` LTFS занимают
минуты сами по себе ([M0-05](../spikes/M0-05-eject-before-unload.md)).

### Отмены нет: есть отказ и перепроверка

Прервать идущий C-вызов нельзя (ADR-0006), поэтому **команды отмены в протоколе
нет**. При остановке супервизор перестаёт слать новые запросы и ждёт текущий;
при таймауте бездействия или зависании — `SIGTERM`, потом `SIGKILL`.

После смерти mover'а итог считается **неизвестным**, а не неудачным. Прерванная
запись оставляет на носителе осиротевший файл (замер M0-02), и единственный
способ узнать правду — `stat`: объект есть **и** `copy_status = complete` →
архивирован, иначе обратно в `pending`. Порядок ровно тот же, что в M4 для
обычного сбоя, — протокол не вводит второго способа интерпретировать сбой.

Мусор на носителе убирает janitor через API Phobos, сам mover при перезапуске
ничего не «доочищает».

### Границы mover'а

Протокол обязан оставаться таким, чтобы эти границы проверялись по его же
описанию:

- **ни развёрнутых DEK, ни TEK, ни KEK** (ADR-0007). В `attrs` лежит обёрнутый
  DEK — для mover'а это непрозрачные данные атрибута;
- **нет доступа к Postgres**: ни DSN, ни переменных подключения в окружении
  дочернего процесса. Правило 13 («транзакция не открыта во время вызова
  Phobos») выполняется тем, что у mover'а транзакции быть не может;
- **нет имён объектов**: имена в манифестах (ADR-0019), mover их не видит и не
  логирует;
- окружение mover'а очищается до запуска, а не наследуется целиком: в нём не
  должно оказаться `TAPEGW_DB_DSN` и пути к файлу KEK.

### Пулы и супервизор

Два пула процессов — `phobos.movers.migrator` и `phobos.movers.recaller`
(ADR-0007), `N + M` не больше числа драйвов, `M ≥ 1`. Супервизор отвечает за
запуск, рукопожатие, перезапуск с экспоненциальной задержкой, таймаут
бездействия и метрики (`mover_up`, `mover_restarts_total`,
`mover_inactivity_timeouts_total`).

## Последствия

- **Появляются** пакет `internal/mover` (клиент супервизора, чистый Go,
  тестируется с подставным бинарём через `go test` без Phobos — правило 2) и
  `cmd/tapegw-mover` (тонкая обёртка над `store/phobos` под build tag `phobos`).
- **Протокол тестируется отдельно от ленты**: «mover умер посреди батча» и
  «ответ пришёл с `incomplete`» проверяются на подставном процессе, который
  печатает заранее заготовленные строки и умирает по сигналу.
- **Тесты на реализацию:**
  - mover убит после `put`, объект на самом деле записан → `stat` подтверждает,
    воркер ставит `archived`, дубликата нет;
  - mover убит после `put`, объект записан неполно → `stat` даёт `incomplete`,
    объект возвращается в `pending`, `attempts+1`;
  - атрибуты 4080 байт → `attr_too_large` **до** обращения к ленте (на стенде
    проверяется, что `ENOSPC` из LTFS в этом тесте не появляется);
  - `hello` с чужим `proto` → супервизор не поднимает пул, ошибка в логе и в
    health-check;
  - молчание mover'а дольше `inactivity_timeout` → `SIGTERM`, итог `unknown`,
    перепроверка через `stat`.
- **В конфиг** (правило 9): `phobos.mover.binary`,
  `phobos.mover.inactivity_timeout`, `phobos.mover.max_line_bytes`,
  `phobos.movers.migrator`, `phobos.movers.recaller`. Отдельно и **вместе с
  кодом mover'а**: ADR-0007 упразднил `phobos.max_inflight`, но настройка до сих
  пор в `config.Config` и в `deploy/tapegw.yaml.example` — сейчас она ни на что
  не влияет, потому что mover'а нет. Менять её раньше нечего: переименование
  настройки без кода, который её читает, только создало бы расхождение конфига с
  документацией.
- **Что упрощается:** S3-слой и тесты не знают, что такое Phobos; падение
  libltfs не задевает клиентов; протокол можно менять, не трогая ленты.
- **Что усложняется:** супервизор — новая ответственность с собственными
  состояниями; «итог неизвестен» становится обычным, а не аварийным состоянием
  воркера, и каждый воркер обязан уметь перепроверку.

## Отклонённые альтернативы

- **Unix-сокет.** Требует heartbeat и уборку сокет-файла после `SIGKILL`, а
  выигрыш — только если бы mover был общим демоном с несколькими клиентами. У
  нас один супервизор и один mover на драйв.
- **Передача fd между процессами** (`SCM_RIGHTS`). ADR-0007 уже отказался:
  пути выводятся из UUID, усложнение не нужно.
- **HTTP/gRPC поверх сокета.** Протокол из шести команд с одним запросом в
  полёте; транспортная обвязка добавила бы зависимостей и не добавила бы
  строгости.
- **Команда `cancel`.** Отменить C-вызов нельзя; честная семантика — «отказаться
  и перепроверить», а не «отменить и считать, что не произошло».
- **Один ADR с форматом ленты** — см. контекст и ADR-0020.
- **Соглашаться на несовместимого mover'а** с предупреждением. Цена рассогласования
  — испорченная лента и часы разбора; цена отказа — не поднятый пул.
