# ADR-0018. Системный тенант: id = 1 закрыт для клиентов

- **Статус:** принято
- **Дата:** 2026-11-03
- **Этап плана:** T1 (PR#2)
- **Связано:** ADR-0009 (модель тенантов), ADR-0017 §6 (у root нет `ProjectID`),
  ADR-0010 (изоляция тенантов), раздел «План разработки» в `docs/ARCHITECTURE.md`

## Контекст

По ADR-0017 §6 бакеты, созданные учёткой root, попадают в тенант `default` с
`id = 1`, потому что у root `ProjectID` не заполнен (`authentication.go:44`
заполняет только `Access`, `Secret`, `Role`), а `buckets.tenant_id` — `NOT NULL`.

Отсюда следствие, которое ревьюер поставил условием перед PR#2: **если тенант 1
когда-нибудь получит клиента, все бакеты, созданные root, станут его бакетами.**
Изоляция (ADR-0010) строится на фильтре по `tenant_id`, так что общий тенант у
оператора и клиента означает общий доступ.

Значит тенант 1 обязан быть **системным и закрытым для клиентов**. Дальше две
силы тянут в разные стороны.

Сила первая — правило должно быть в данных, а не в договорённости. Константа
`1` в коде живёт ровно до первого рефакторинга, а `DEFAULT 1` на `tenant_id`
уже один раз нас подвёл (миграция 0005: `DEFAULT` пришлось снимать, чтобы
забытый тенант падал на `NOT NULL`, а не получал чужой).

Сила вторая — выразить правило декларативно в БД неочевидно. Наивный
`CHECK (id > 1)` на `tenants` **неприменим**: строка с `id = 1` обязана
существовать, и чек упадёт на ней же при валидации миграции. Межтабличное
правило «на этот тенант имеет право ссылаться только admin» обычным `CHECK`
тоже не пишется — `accounts.tenant_id` смотрит на `tenants`, а не наоборот.

## Решение

Признак системности становится **данными**: колонка `tenants.system`
(`boolean NOT NULL DEFAULT false`), `true` ровно для тенанта `id = 1`.

Правило «не-admin не может принадлежать системному тенанту» закрепляется
**декларативно, составным внешним ключом** — вариант ревьюера, без триггеров:

```sql
ALTER TABLE tenants
  ADD COLUMN system boolean NOT NULL DEFAULT false;
UPDATE tenants SET system = true WHERE id = 1;
ALTER TABLE tenants ADD UNIQUE (id, system);

-- Колонку нельзя добавить сразу NOT NULL: на непустой accounts она будет
-- содержать NULL, и ALTER упадёт ещё до backfill. Проверено на живом
-- Postgres — см. «Проверка» ниже.
ALTER TABLE accounts ADD COLUMN tenant_system boolean;
UPDATE accounts a SET tenant_system = t.system
  FROM tenants t WHERE t.id = a.tenant_id;
ALTER TABLE accounts ALTER COLUMN tenant_system SET NOT NULL;

ALTER TABLE accounts
  ADD CONSTRAINT accounts_tenant_fkey
    FOREIGN KEY (tenant_id, tenant_system) REFERENCES tenants (id, system)
    ON UPDATE CASCADE,
  ADD CONSTRAINT accounts_not_system_unless_admin
    CHECK (role = 'admin' OR NOT tenant_system);
```

Пара `(tenant_id, tenant_system)` попадает в `UNIQUE (id, system)` только при
**точном** совпадении флага с тенантом:

| учётка | исход |
|---|---|
| `role = 'user'`, `tenant_id = 1`, `tenant_system = true` | `CHECK` → отказ |
| `role = 'user'`, `tenant_id = 1`, `tenant_system = false` | FK → отказ (нет пары `(1, false)`) |
| `role = 'admin'`, `tenant_id = 1`, `tenant_system = true` | ок |
| `role = 'userplus'`, `tenant_id = 2`, `tenant_system = true` | `CHECK` → отказ |
| `role = 'user'`, `tenant_id = 2`, `tenant_system = false` | ок |
| `UPDATE ... SET tenant_system = true` для клиентской учётки | `CHECK` → отказ |

То есть записать учётку с неверным флагом нельзя ни в какую сторону, и правило
видно прямо в схеме. `userplus` под `role = 'admin'` не подпадает, поэтому в
системный тенант не проходит — как и задумано.

Параллельно то же правило проверяется **в коде IAM** (`ADR-0017`-подобный
отказ при выдаче учётки) и покрывается тестом. Проверка в схеме защищает от
ручной правки таблицы и от миграции данных, проверка в коде даёт понятный
`AccessDenied` вместо `SQLSTATE 23514`.

API создания тенантов (появится в T1) **никогда не выдаёт `id = 1`** — он не
просто «не предлагает» его, а отвергает явную просьбу.

## Последствия

**Проще.** Правило выживет при рефакторинге: чтобы его сломать, надо править
схему, а не забыть `if`. Оператор видит признак в админском выводе тенантов и
понимает, почему в этот тенант нельзя назначать клиента. При появлении второго
системного тенанта код менять не придётся — достаточно `UPDATE tenants SET
system = true`.

**Сложнее.**

- `tenant_system` в `accounts` — денормализация. Она обязана совпадать с
  `tenants.system`, и за это отвечает FK; при смене `system` у тенанта нужен
  каскад (`ON UPDATE CASCADE`). Для системного тенанта это событие исключительное,
  но **миграция обязана идти в три шага** (nullable → backfill → `SET NOT NULL`)
  и укладываться в одну транзакцию вместе с флагом на `tenants`, иначе FK не
  выполнится на уже лежащих строках.
- `accounts` теперь нельзя пополнять «вслепую»: INSERT обязан прочитать
  `system` у тенанта. Это правильно, но об этом легко забыть при генерации
  тестовых данных — стенды (`testdb`, `users.json`) обязаны это учитывать.
- CI-стенд переезжает: `userplus` из тенанта 1 уходит в **отдельный тенант 2**,
  а проверка «политика разрешает чтение» строится внутри тенанта 2 двумя ключами
  одного тенанта. Прежний вид теста по факту проверял доступ к бакету системного
  тенанта — то есть не тот сценарий.

**Что меняется в коде.** IAM (PR#2) читает `system` и отказывает не-admin;
`meta.AdminTenantID` остаётся как точка назначения для бакетов root, но перестаёт
быть «просто единицей» — рядом появляется признак, и проверка идёт по нему.

## Проверка

SQL выше прогнан на живом Postgres (схема-копия `tenants` + `accounts` из
миграции 0005). Миграция проходит, все шесть строк таблицы воспроизводятся с
указанными ограничениями. Отдельно проверено, что вариант «`ADD COLUMN
NOT NULL` одной командой» на непустой `accounts` даёт
`column "tenant_system" ... contains null values` — поэтому последовательность
зафиксирована здесь, а не оставляется на усмотрение автору миграции.

## Отклонённые альтернативы

- **Только константа в коде (IAM + API), без колонки.** Отклонено: правило
  держится на внимательности, а ручная правка `accounts` или сид стенда его
  обходит. Ревьюер допускал такой вариант при наличии теста, но раз декларативный
  способ доступен без триггеров, брать надо его.
- **`CHECK (id > 1)` на `tenants`.** Неприменим: строка `id = 1` обязана
  существовать, чек упадёт на ней же.
- **Триггер `BEFORE INSERT OR UPDATE` на `accounts`.** Работает и проще в записи,
  но правило прячется в теле процедуры: его не видно ни в `\d accounts`, ни в
  описании схемы, а отладка сообщений об ошибках в PL/pgSQL дороже. При
  доступности декларативной записи триггер проигрывает.
- **Отдельная таблица `system_tenants(id)`.** Избавляет от денормализации во
  `accounts`, но превращает проверку в `NOT EXISTS` — то есть снова запрос и
  снова код, а декларативность теряется: «не admin + системный» выразить
  декларативно всё равно нельзя.
- **Отказаться от тенанта у root вообще** (сделать `buckets.tenant_id`
  nullable). Отклонено: `NULL` в колонке изоляции — это «фильтр не сработал»,
  самый опасный вид отсутствующего значения (см. ADR-0017 про `ProjectID == 0`).
