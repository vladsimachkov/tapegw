# M0-12: разрешение на запись, почтовые слоты, смена магазина

- **Статус:** частично закрыт — главный вопрос (окно TLC) и вопрос флага `put`
  закрыты; почтовые слоты и пересканирование после замены магазина не проверялись
- **Дата:** 2026-11-05
- **Phobos:** 3.4.1, стенд `tapegw-vm` (AlmaLinux 9.8, mhVTL 0.18.43)
- **Вопрос из плана:** [предложение 0014](../proposals/0014-media-lifecycle-migrations-plan.md),
  Ф0.6.

## Краткий ответ

1. **Окно для TLC есть, и оно широкое.** Сторонний процесс открывает устройство
   драйва и читает MAM **при смонтированной ленте** и **во время выгрузки** —
   ни одного состояния «устройство недоступно» за 90 замеров через 0.2 с.
   `klipper-tlc` сможет и выгрузить картридж, и сверить метку.
2. **Флаг `put` у носителя работает**: снятый `put` заставляет Phobos отказывать
   в записи. **Но отказ приходит как `ENOSPC`**, а не как «запрещено» — это
   следствие для migrator'а, см. ниже.
3. `phobosd` **не держит** устройства драйвов открытыми в простое: среди его
   дескрипторов нет ни одного `/dev/st*` или `/dev/sg*`.

## 1. Окно TLC: можно ли открыть драйв, пока Phobos им пользуется

Это был главный вопрос, потому что по архитектуре `klipper-tlc` сам выдаёт драйву
Unload (Phobos её не даёт — M0-05) и сверяет метку по MAM при загрузке. Если бы
`phobosd` держал устройство монопольно всё время, манипулятор не смог бы работать
с драйвами вообще.

**`phobosd` в простое устройство не держит:**

```
$ ls -l /proc/<phobosd>/fd | grep -E "/dev/(st|sg|tape)"
(пусто; всего дескрипторов 16)
```

**При смонтированной ленте** сторонний процесс устройство открывает. Первый
запрос после загрузки получает `Unit attention` — штатное «носитель сменился,
повтори», — со второго атрибуты отдаются стабильно:

```
$ sg_read_attr /dev/sg4        # 1-й раз: Unit attention
$ sg_read_attr /dev/sg4
  Maximum capacity in partition [MiB]: 953
  Load count: 6
  Volume change reference: 0x1
```

**Во время выгрузки** зонд каждые 0.2 с (90 замеров) фиксировал состояние
плотности и доступность MAM. Переходов «доступно → недоступно → доступно» не было
вовсе, только смена содержимого привода:

```
.0515577   Density code 0x5e (LTO-8)     ← лента в приводе
.1132419   Density code 0x0 (default)    ← лента выехала
```

`mt -f /dev/st0 status` проходил в **обоих** состояниях.

**Вывод для M7/M8:** `klipper-tlc` может открывать устройство драйва в момент
Load/Unload. Правило для кода: после загрузки ожидать один `UNIT ATTENTION` и
повторять запрос; при `BUSY` (Phobos прямо сейчас работает с приводом) —
повторять с ограничением по числу попыток.

**Заодно закрывается Ф1.6.** Вариант «читать MAM до резервирования» оказался не
нужен: читать можно и после. `Load count` из MAM на mhVTL растёт с каждой
загрузкой (6), тогда как `phobos tape list -o stats.nb_load` показывает `0`
всегда — то есть счётчик загрузок для политик здоровья надо брать из MAM, а не
из Phobos.

## 2. Флаг `put` у носителя

Синтаксис (порядок аргументов важен, иначе команда молча не находит строку):

```bash
phobos tape set-access -L vtllib -- -P E01002L8     # снять put
phobos tape set-access -L vtllib -- +P E01002L8     # вернуть put
phobos tape list -f csv -o name,put_access          # проверить
```

Попытка задать флаги после имени ресурса даёт `No rows were updated by the
update` — и это не ошибка, код возврата нулевой.

**Проверка A/B на одной и той же ленте** (`E01002L8`, единственный носитель с
тегом `side:right`):

| `put_access` | `phobos put -T side:right` |
| --- | --- |
| `False` | `Cannot PUT ... (No space left on device)` |
| `True` | `PUT operation ... succeeded` |

### Следствие: отказ по политике неотличим от настоящего «нет места»

Phobos не говорит «носитель закрыт для записи» — он **исключает ленту из
выбора**, и migrator получает `ENOSPC`. Для нас это ровно та ловушка, из-за
которую мы уже ломали обработку ENOSPC: перепутать «полка заполнена» и «полка
закрыта политикой» нельзя, потому что первая лечится ожиданием и новой лентой, а
вторая не лечится ничем до правки политики.

Значит:

- **полагаться на код ошибки Phobos нельзя.** Различение держится на слое 2 —
  `read_only` в `media` и `writable: false` в конфиге поколений (Р5 из 0014),
  tapegw обязан сам знать, какие ленты закрыты, и не выбирать их целью;
- **проверка места в пулу обязана учитывать закрытые ленты**: «свободные байты
  есть» неверно, если все свободные байты на лентах с `put_access = false`.
  Иначе migrator уйдёт в бесконечные ретраи с лицом «кончилось место»;
- слой 3 при этом остаётся и нужен он против **ручного** `phobos put` мимо
  tapegw, а не как источник информации для нас.
