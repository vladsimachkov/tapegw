# M4: цикл migrator — приёмочные проверки

Документ — чек-лист ревьюера, перенесённый в репозиторий до реализации: пункты
проверяются тестом, а не обещанием. Нумерация С1…С10 — на них можно ссылаться в
отчёте о PR.

Контекст: [предложение 0013](../proposals/0013-copies-placement-media.md),
[ADR-0020](../adr/0020-tape-record-format.md),
[ADR-0021](../adr/0021-mover-protocol.md), [ADR-0022](../adr/0022-copies-as-separate-objects.md).

## Что выбирает migrator, а что — Phobos

**Носитель выбирает Phobos** по тегам копии, которые migrator передаёт в `put`.
tapegw ленту не выбирает: второй планировщик носителей поверх LRS расходится с
ним при первом же repack. Migrator выбирает **пул, спецификацию копии (теги) и
mover**.

Определение «доступна для записи» (#100) нужно не для выбора ленты, а для трёх
вещей: проверить место до отправки, классифицировать `ENOSPC`, считать свободное
место планировщику ёмкости.

## Приёмочные проверки

| # | Проверка | Чем доказана |
| --- | --- | --- |
| С1 | Два прохода сборки дают одну сумму: mover принимает пачку по объявленной `sha256`, без `checksum_mismatch` | `TestTwoPassSameSum` |
| С2 | Если между проходами участник изменился, mover **отказывает**, а не пишет | `TestChangedMemberIsRefused` |
| С3 | Место проверяется **до** `put` по единому определению, с учётом поколения копии и запретов; нет места → алерт, попытки нет | `TestNoSpaceAlertsWithoutPut` |
| С4 | `ENOSPC` различается на «нет места» и «ленты закрыты»: лента с местом, но со снятым `put` → алерт о закрытых лентах, без повторов | `TestClosedTapesAreNotNoSpace` |
| С5 | Все копии политики пишутся из одного буфера через `from_op`; `archived` только после всех копий | `TestArchivedOnlyAfterAllCopies` |
| С6 | При сбое одной копии остальные не пропадают, недостающая догоняется на повторе | `TestFailedCopyIsRetriedAlone` |
| С7 | Ожидаемая `sha256` сохраняется в `archive_copies` при первой записи — без неё reconciler нечем проверять чтения с ленты | `TestExpectedSHAStoredOnFirstWrite` |
| С8 | Правило 13 проверено тестом: во время вызова mover нет открытой транзакции. Fake-mover в момент `put` берёт блокировку той же строки и **не ждёт** | `TestNoTxnOpenDuringMoverCall` |
| С9 | Сборка пачки детерминирована (две сборки из тех же участников — побайтно равны) | `TestBuildIsDeterministic` (уже в `internal/pack`) |
| С10 | Батч = N отдельных операций `put`, а не один вызов на батч | `TestBatchIsNPutOperations` |

## Состояние (актуально на момент последнего сеанса)

Этот раздел — точка входа для нового сеанса. Он важнее памяти о прошлом
разговоре: здесь то, что реально в коде, а не то, что обсуждалось.

| # | Проверка | Состояние |
| --- | --- | --- |
| С1 | два прохода дают одну сумму | закрыто, `TestTwoPassSameSum` |
| С2 | участник изменился между проходами — отказ | закрыто, `TestChangedMemberIsRefused`, `TestChangedBytesSameLengthIsRefused` |
| С3 | место проверяется до `put` | закрыто, `TestPoolWriteSpace`, `TestWriteTargetsExcludesUnusableMedia` |
| С4 | `ENOSPC` различает «нет места» и «ленты закрыты» | закрыто, `TestPoolWriteSpace` (случай `closed`) |
| С5 | все копии пишутся из одного буфера, `archived` после всех | **не начато** |
| С6 | сбой одной копии не роняет остальные, недостающая догоняется | **не начато** |
| С7 | ожидаемая `sha256` пишется при первой записи копии | закрыто, `TestExpectedSHAStoredOnFirstWrite` |
| С8 | правило 13: во время вызова mover транзакции нет | закрыто, `TestNoTxnOpenDuringMoverCall` (проверяет SQLSTATE `55P03`) |
| С9 | сборка детерминирована | закрыто, `TestBuildIsDeterministic` в `internal/pack` |
| С10 | батч = N операций `put` | закрыто, `TestBatchIsNPutOperations` |

Рядом, вне чек-листа, но из той же работы: неизвестный итог `put` не выбрасывает
пачку (обрыв после записи не даёт дубль), `TestTransportBreakAfterWriteDoesNotDuplicate`,
`TestLostRegistryResendsSamePack`.

## Порядок следующего захода

1. **#101, срочная часть** — `EEXIST` отдельным кодом результата, который
   migrator **не** повторяет, а отмечает алертом «пачка существует в Phobos,
   итог требует проверки» с oid пачки. Сейчас `EEXIST` не входит в
   определённые отказы, поэтому после потери реестра mover'а цикл будет
   получать `EEXIST` вечно: объекты не станут `archived`, landing не
   освободится, сигнала не будет. Делается до С5/С6: они трогут ту же логику
   повторов, и строить их надо поверх кода, который на `EEXIST` не зацикливается.
2. **С5 и С6** — все копии политики пишутся из одного буфера через `from_op`
   (правила Ф0.4 в [ADR-0021](../adr/0021-mover-protocol.md): `sha256`
   обязательна, источник — только `done`, тот же клиент и тот же узел,
   освобождение по счётчику с `result_ttl`). Ожидаемая сумма из С7 — то, с чем
   сверяют чтение при `from_op` на `get`: посчитанная при чтении сумма замкнута
   сама на себя.
3. **#101, полная часть** — команда `stat` в протоколе mover (ADR-0021 её
   описывает): `complete` → успех, `incomplete` → удалить незавершённую копию и
   отправить снова, объекта нет → отправить. До закрытия M4.

## Почему разбито так

С3/С4 существуют независимо от цикла: они про то, что migrator решает **до**
того, как у него есть что отправлять. С5/С6 — про то, что происходит, когда
носителей несколько у одного объекта.

## Как проверять

* Мутации — только `make mutate` (`hack/mutate.sh`): он проверяет, что правка
  применилась, что базовый прогон что-то выполнил, и умеет `MODE=perl` для
  многрочного SQL и `DROP_SCHEMA` для миграций. Прерванная мутация подбирается и
  восстанавливается следующим запуском.
* Перед PR и перед мержем — смотреть **содержимое удалённой ветки**, а не код
  возврата `git push` (правило в `AGENTS.md`).
* Тесты на Postgres без `TAPEGW_TEST_DSN` пропускаются, а не падают: зелёный
  прогон без DSN ничего не проверяет.
