# ADR-0022. Копии объекта — самостоятельные объекты Phobos

- **Статус:** принято
- **Дата:** 2026-11-05
- **Этап плана:** M4 (миграция и migrator), частично M5 (restore) и M6 (удаление)
- **Связано:** [предложение 0013](../proposals/0013-copies-placement-media.md),
  [спайк M0-11](../spikes/M0-11-libraries-generations-copies.md),
  [ADR-0008](0008-object-medium.md), [ADR-0013](0013-tape-pools.md),
  [ADR-0020](0020-tape-record-format.md), [ADR-0021](0021-mover-protocol.md),
  `docs/ARCHITECTURE.md` — «Архивация», «Модель данных»

## Контекст

Предложение 0013 свело четыре сценария — две стороны библиотеки, ленивая миграция
поколений, переезд библиотеки, копия вне площадки — в один механизм: у пула есть
политика размещения, каждая копия описывается своим набором тегов, а фактическое
размещение сверяется с политикой.

Форма таблицы `archive_copies` зависела от ответа на блокирующий вопрос: **умеет ли
Phobos записать вторую копию того же объекта на носители с другим тегом.** Спайк
M0-11 дал три факта:

1. **Внутри одной операции `put` все реплики получают один набор тегов.**
   `pho_xfer_put_params.tags` — один список на операцию, и `raid_common.c`
   заполняет им каждый extent одними значениями. `raid1` с `repl_count = 2`
   физически не разложит реплики по разным сторонам.
2. **`phobos copy create` умеет** вторую копию с другим тегом (проверено:
   `left → E01001L8`, `right → E01002L8`), но для этого он **читает первую
   копию**, то есть поднимает данные с первой ленты и занимает два драйва
   одновременно.
3. **`put --overwrite -c <имя>` — ловушка**: рапортует успех, в таблице `copy`
   появляется строка `complete`, но это новая *версия* объекта. Прежняя версия с
   её копиями уходит в `deprecated_object` и перестаёт быть видна; `get -c left`
   отвечает `ENOENT`. Ни ошибки, ни предупреждения.

Дополнительно: буфер mover (staging на NVMe) — дефицитный ресурс, и по ADR-0021
данные передаются по протоколу, а не путями.

## Решение

**Каждая копия — самостоятельный объект Phobos, записанный отдельной операцией
`put` из одного и того же буфера mover.** Встроенными именованными копиями Phobos
не пользуемся.

- mover получает данные **один раз**, буферизует и выполняет столько `put`,
  сколько копий в политике пула. Каждый — со своим `oid`
  (`<uuid версии>.<имя спецификации>`, например `…a3f1.left` и `…a3f1.right`) и
  со своим набором тегов из политики;
- **лента ничего не читает**, только пишет. Каждая запись — отдельная операция
  протокола со своей идемпотентностью по UUID операции (ADR-0021), поэтому
  отказ на второй копии не откатывает первую и не требует переписывать её с
  другой ленты;
- буфер освобождается, когда записаны **все** копии политики. Ровно тогда же
  объект переходит в `archived` — это и есть правило «архивный = все копии
  записаны»;
- Phobos **не знает** о существовании связи между копиями. Связь хранит tapegw.

### Таблица `archive_copies`

Одна строка = одна копия одной сущности (пачки или крупного объекта вне пачки):

| Колонка | Смысл |
| --- | --- |
| `id` | `uuid`, первичный ключ |
| `pack_id` | пачка, если копия относится к пачке |
| `object_id` | версия крупного объекта, если копия вне пачки |
| `spec` | имя спецификации из политики пула (`left`, `right`, `offsite`) |
| `phobos_oid` | `oid` объекта Phobos для этой копии, уникален |
| `medium` | `text[]` — носители, на которых копия лежит (при `repl_count > 1` их несколько) |
| `state` | `pending` → `writing` → `done`, плюс `lost` (не читается) и `dead` (носитель потерян) |
| `attrs` | `jsonb` — сведения о копии, не участвующие в логике (например, результат `extent list`) |
| `created_at`, `written_at` | времена постановки и записи |

Ограничение: ровно один из `pack_id` / `object_id` непустой — копия всегда
принадлежит одной сущности и только одной.

`objects.phobos_medium` и `packs.medium` в схеме **не появляются**: одна колонка не
описывает несколько мест хранения, а после первой записи на ленту замена
колонки таблицей означала бы миграцию всего архива.

### Политика копий пула в конфиге

```yaml
pools:
  - name: standard
    library_write:
      copies:
        - name: left
          tags: [pool:standard, side:left]
        - name: right
          tags: [pool:standard, side:right]
```

Одна копия — частный случай списка из одного элемента: механизм тот же, что для
двух сторон и для копии вне площадки. Теги — жёсткий фильтр со семантикой И
(спайк M0-08), поэтому каждая запись тегирована обязательно (ADR-0013).

### Правило «архивный = все копии записаны»

`archived` наступает, только когда записаны **все** копии текущей политики пула.
До этого landing не очищается.

Без этого правила между записью первой и второй копии на ленте лежит одна
копия, а на диске уже ничего нет: единственный отказ второй ленты делает объект
потерянным.

Если политика пула изменилась **после** архивации, состояние `archived` не
откатывается: объект остаётся архивным, а недостающая копия становится
«не по политике» и дописывается reconciler'ом (после MVP). Иначе правка конфига
массово вернула бы архив в очередь без всякой аварии.

### Выбор копии при restore

- читается копия, чья лента уже смонтирована; иначе — с той стороны, где есть
  свободный драйв;
- при ошибке чтения берётся другая копия, а сбойная получает `lost` и уходит в
  reconciler на пересоздание;
- если у всех копий `state` не `done` и ни одна лента недоступна (`location` в
  `in_transit` / `offline` / `offsite` / `lost`) — запрос ждёт со статусом и
  алертом оператору, **без бесконечных повторов**.

### Атрибуты записи

В атрибуты Phobos добавляется имя спецификации копии — `tapegw.copy`. Нужен,
чтобы `rebuild-meta` после потери DSS понимал, какая из записей какая копия:
без него копии одного логического объекта сливаются в неразличимую кучу.
Стоимость — порядка 20 байт из бюджета 4079 (ADR-0020), запас покрывает.

### Удаление и уплотнение

Работают с каждой копией отдельно: удаление помечает `dead`/удаляет строки копий
и уменьшает `live_bytes` пачки в той же транзакции (механизм ADR-0011/0017),
уплотнение переносит ссылку участника в новую пачку и порождает копии заново.

## Последствия

**Что упрощается.**

- Архивация не порождает чтения с ленты: полный проход «буфер → лента» на
  каждую копию, предсказуемая нагрузка на драйвы.
- Отказ одной копии изолирован: это состояние одной строки, а не испорченная
  реплика внутри объекта Phobos, которую надо чинить средствами Phobos.
- Политика «копия вне площадки» не требует нового механизма — ещё одна строка в
  списке `copies`.

**Что усложняется.**

- `archive_copies` — обязательная таблица с самого начала, до первой записи на
  ленту. Отложить её нельзя: после первой записи это миграция всего архива.
- Migrator обязан понимать «все копии» как условие перехода состояния, а не как
  «последняя из N операций завершилась успешно»: между ними может быть сбой.
- `rebuild-meta` должен разбирать `tapegw.copy` и склеивать копии в логический
  объект.
- Буфер mover занят дольше: пока не записаны все копии. При политике из двух
  копий и последовательной записи это удваивает время удержания буфера на
  объект — размер буфера считается с этим.

  **Но удвоение — следствие порядка, а не модели.** По Ф0.4 из
  [предложение 0014](../proposals/0014-media-lifecycle-migrations-plan.md) буфер
  принадлежит **серверу библиотеки**, а не процессу mover. Тогда две копии можно
  писать **параллельно двумя драйвами из одного буфера**: данные приняты один раз
  и лежат на месте, каждый mover берёт свою спецификацию и свои теги. Время
  удержания при этом остаётся примерно тем же, что при одной копии, — буфер
  освобождается по факту последней записи, а не по сумме двух прогонов.

  Для двухкопийных пулов это вариант по умолчанию, а не оптимизация «на потом»:
  он меняет только планирование операций на стороне tapegw (две операции `put`
  отправляются одновременно, а не одна за другой), форма `archive_copies` и
  идемпотентность по UUID операции не меняются вовсе. Требует Ф0.4 — без
  локального буфера сервера второй mover читал бы данные с ленты.

**Что меняется в коде и тесте.**

- миграция: таблица `archive_copies` (одна миграция на PR, правило 11);
- `internal/mover`: `PutItem` получает спецификацию копии (теги + `oid`),
  батч = N·M операций `put` (N объектов × M копий);
- migrator: переход в `archived` по факту всех записанных копий; тест «упасть
  после записи копии 1 из 2» на `store/fake` (правило 7);
- атрибут `tapegw.copy` в формировании атрибутов записи (ADR-0020) и в
  `rebuild-meta`;
- `docs/ARCHITECTURE.md`: раздел «Архивация» — шаг с копиями вместо
  `phobos_medium`.

## Отклонённые альтернативы

### `phobos copy create` — встроенная вторая копия

Механически работает (проверено), но **читает первую ленту**, чтобы записать
вторую: лишнее чтение ленты на каждый объект и два драйва одновременно — один
читает, другой пишет. При четырёх драйвах это заметно мешает и архивации, и
restore. Кроме того, копию нельзя создать из локальных данных: путь «положить
ещё одну копию из файла» — это `put --overwrite`, а он запрещён ниже.

### `put --overwrite -c <имя>` — запрещено

Не добавляет копию: создаёт новую версию объекта, а прежняя версия с её копиями
уходит в `deprecated_object` и перестаёт быть видна. Ошибки нет, в таблице
`copy` статус `complete`. Это ровно то тихое поведение, которого мы избегаем:
оно молча разрушает инвариант «все копии записаны».

**Запрет явный и действует для всех, включая оператора** — в тот же раздел
документации, где запрещён прямой `phobos delete` вне контроля tapegw (ADR-0015).
Наши `oid` и так уникальны и `--overwrite` нам не нужен, но запрет должен быть
записан: он защищает от «починил» руками.

### Одна запись `raid1` с `repl_count = 2`

Не проходит по факту: все реплики одной операции получают один набор тегов
(см. контекст, п. 1). Разложить реплики по сторонам нельзя в принципе.

### Колонка «носитель» у объекта вместо таблицы

Одна колонка не описывает несколько мест хранения и не хранит принадлежность
копии к спецификации политики. Пока данных нет, замена бесплатна; после первой
записи на ленту — миграция всего архива.
