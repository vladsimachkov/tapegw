# ADR-0020. Формат записи на ленту: атрибуты, пачка, журнал

- **Статус:** принято
- **Дата:** 2026-11-05
- **Этап плана:** M4 (ADR обязан быть принят до первой строки кода `tapegw-mover`)
- **Связано:** [ADR-0019](0019-object-manifest-trailer.md) (манифест объекта),
  [ADR-0014](0014-encryption-per-tenant.md) (что попадает на ленту),
  [ADR-0008](0008-object-medium.md), [ADR-0007](0007-mover-worker.md),
  спайк [M2-01](../spikes/M2-01-phobos-attr-limit.md), раздел M4 в `ARCHITECTURE.md`.
  Протокол tapegw ↔ mover — **отдельный** [ADR-0021](0021-mover-protocol.md).

## Контекст

Всё, что записано на ленту, меняется только перезаписью. Формат манифеста уже
зафиксирован ADR-0019, но до M4 не зафиксированы четыре вещи, без которых mover
писать нечего: набор атрибутов, формат пачки мелких объектов, формат сегмента
журнала и формат снимка.

Давления тут несколько, и часть из них измерена, а не угадана.

**Бюджет атрибутов жёсткий и общий.** Phobos сериализует все пользовательские
атрибуты в один JSON в xattr `user.user_md`, а LTFS ограничивает одно значение
xattr 4096 байтами. Замерено в M2-01: значение **4079** байт проходит, **4080** —
`ENOSPC`; разница 17 байт — обёртка JSON. Значения обязаны быть валидным UTF-8 —
не-ASCII Phobos молча заменяет на U+FFFD, поэтому двоичное только в base64
(+33 %).

**Мелкие объекты нельзя писать отдельными файлами.** Каждый объект — запись в
индексе LTFS; на трафике бэкап-софта это раздувает индекс и делает запись
медленной. Отсюда пачки (`pack.threshold = 25MiB`), но пачка — это ещё один
формат, который надо зафиксировать.

**Индекс пачки открыт и общий для тенантов.** Данные внутри пачки зашифрованы
каждый своим DEK, а индекс — нет: иначе `rebuild-meta` не смог бы понять, где что
лежит, не имея ключей вообще. Открытые байты, которые определяют *порядок*
версий, — это дыра: порча их молча переставит версии при восстановлении.

**Часть метаданных правится после записи** (retention, legal hold, удаления), и
для этого есть журнал (M4). Сегменты журнала — тоже мелкие объекты, и у них те
же требования к формату.

## Решение

Четыре артефакта, у каждого своя версия формата. Протокол между процессами сюда
не входит — он в ADR-0021, потому что меняется вместе с обоими бинарями и не
требует миграции данных.

### 1. Файл крупного объекта (больше `pack.threshold`)

Файл — как описано в ADR-0019: шифротекст тела, шифротекст манифеста, 48-байтный
футер. Добавляется шестой атрибут.

| атрибут | значение | примечание |
| --- | --- | --- |
| `tapegw.version` | UUID версии | он же oid в Phobos |
| `tapegw.tenant` | int64 десятичное | по нему ищется TEK |
| `tapegw.dek` | base64 обёртки DEK | обёртка ключом TEK |
| `tapegw.kek` | десятичная версия KEK | |
| `tapegw.format` | `1` | **версия формата файла объекта** |
| `tapegw.seq` | `version_seq`, десятичное | новый: порядок версий |

`tapegw.seq` нужен потому, что `version_seq` назначает Postgres при вставке, уже
после записи файла, и время сборки манифеста этот порядок не воспроизводит
(две параллельные записи одного ключа). К ключам номер отношения не имеет.

### 2. Пачка мелких объектов

Один объект Phobos на пачку. Внутри — **поток tar в формате pax**, затем индекс,
затем футер:

```
[ tar(pax): member_1 … member_N ][ индекс ][ футер ]
```

Имя участника tar — UUID версии объекта, содержимое — шифротекст этого объекта
как есть (те же сегменты AES-GCM, что и в отдельном файле). pax выбран не
ради совместимости с `tar(1)`, а ради свойства: поток читается по заголовкам
слева направо **без индекса**.

**Атрибуты пачки** (свои, не те же шесть):

| атрибут | значение |
| --- | --- |
| `tapegw.pack.format` | `1` — **версия формата пачки** |
| `tapegw.pack.count` | число участников |
| `tapegw.pack.index_off` | смещение индекса |
| `tapegw.pack.index_len` | длина индекса |
| `tapegw.tenant` | пуст, если пачка смешанная; id — если одно-тенантная |
| `tapegw.kek` | версия KEK для обёрток в индексе |

**Индекс** — бинарные записи фиксированной длины, по одной на участника, в порядке
`version_seq` внутри каждого тенанта:

| поле | размер |
| --- | --- |
| `version` (UUID) | 16 |
| `tenant` | 8 |
| `version_seq` | 8 |
| `plain_len` | 8 |
| `cipher_off` | 8 |
| `cipher_len` | 8 |
| `dek_len` | 2 |
| `wrapped_dek` | ≤ 255 (обычно 60) |
| `flags` | 1 (маркер удаления и т. п.) |

Бинарный, а не JSON: размер записи предсказуем, а отлаживаемость индекса
обеспечивает утилита печати, а не `cat`. Открытым остаются только UUID, номера,
смещения и обёрнутые DEK — имён нет ни в каком виде (ADR-0014).

**Футер пачки** — 64 байта:

| поле | размер |
| --- | --- |
| `magic` | 4 (`TPKF`) |
| `format` | 1 — версия формата пачки, **дублирует атрибут** |
| `index_sha256` | 32 |
| `index_len` | 8 |
| `count` | 8 |
| `reserved` | 11 |

**Целостность индекса — обязательна.** MAC на ключе тенанта не подходит: индекс
открытый и смешанный, у участников разные DEK и у разных тенантов разные TEK.
GCM защищает только содержимое участников — подмена смещения в индексе дала бы
ошибку расшифровки, но подмена `version_seq` или `tenant` не даёт ничего, кроме
молча переставленных версий. Поэтому `index_sha256` — SHA-256 от байтов индекса,
и несовпадение есть ошибка восстановления, а не предупреждение.

### 3. Сегмент журнала

Один объект Phobos на сегмент. Содержимое — шифротекст (AES-GCM, ключ TEK
тенанта) списка событий; AAD — UUID сегмента, чтобы сегмент нельзя было вставить
в другой тенант.

| поле заголовка сегмента | размер |
| --- | --- |
| `magic` | 4 (`TPJL`) |
| `format` | 1 — **версия формата журнала** |
| `tenant` | 8 |
| `seq_first`, `seq_last` | 8 + 8 |
| `sha256_body` | 32 |

`seq_first`/`seq_last` по `journal_seq` и дают тот самый контроль пропуска:
`rebuild-meta` при восстановлении проверяет непрерывность цепочки и на дырке
останавливается с алертом, а не применяет неполный журнал молча.

Сегменты едут в **пачки журнала**, отдельные от пачек данных (`journal.pack.max_wait
= 1h`): окно «событие → лента» не должно зависеть от того, насколько бойко идёт
архивация данных.

### 4. Снимок

Тот же контейнер, что сегмент журнала, с `format = 2` и другим содержимым:
состояние блокировок и конфигурация бакетов на момент снимка. Своя версия формата,
чтобы снимок можно было менять, не трогая журнал событий.

### Версии формата — раздельные

| артефакт | где версия |
| --- | --- |
| файл крупного объекта | `tapegw.format` + байт в футере манифеста |
| пачка | `tapegw.pack.format` + байт в футере пачки |
| сегмент журнала | байт `format` в заголовке сегмента |
| снимок | байт `format` в заголовке снимка |

Раздельные — чтобы менять их независимо: изменение формата индекса не должно
требовать трогать формат манифеста, и наоборот. Читатель обязан отказать на
неизвестной версии, а не пытаться угадать.

### Что лежит открыто — правило

Открыто лежат **только**: UUID (версии, сегмента), id тенанта, числа (`version_seq`,
`journal_seq`, смещения, длины), версия KEK, версии форматов, обёрнутые DEK и
обёрнутые TEK. Не лежат открыто нигде: имена бакетов и ключей, content-type,
пользовательские метаданные, теги, значения retention. Это ADR-0014, и правило
должно проверяться таблицей полей этого ADR, а не внимательностью: ни одна
таблица выше не содержит поля-имени.

### Бюджет `user_md` — худший случай

Лимит — 4079 байт на весь JSON наших атрибутов (M2-01). Считаем худший случай
файла крупного объекта:

| атрибут | ключ | значение, худший случай |
| --- | --- | --- |
| `tapegw.version` | 14 | 36 (UUID строкой) |
| `tapegw.tenant` | 13 | 19 (int64 целиком) |
| `tapegw.dek` | 10 | 80 (base64 от 60 байт) |
| `tapegw.kek` | 10 | 5 |
| `tapegw.format` | 13 | 1 |
| `tapegw.seq` | 10 | 19 |
| служебное JSON (`"`, `:`, `,`, `{}`) | | 6 пар × 6 + 2 = 38 |
| **итого** | | **≈ 268 байт** |

Запас — пятнадцатикратный. Атрибуты пачки того же порядка (≈ 250 байт).
Практическое следствие: **в атрибуты нельзя класть ничего, что растёт с размером
объекта** — таблица частей в атрибуты не влезает уже на 84 частях (M2-01), и
никакой запас это не спасает.

### Последовательное чтение без индекса — требование к `rebuild-meta`

Если индекс пачки повреждён (`index_sha256` не сошёлся), `rebuild-meta` обязан
не бросить пачку целиком, а пройтись по tar-потоку по заголовкам: имена участников
— UUID версий, метаданные версии берутся из манифеста в хвосте каждого участника.
Восстановится хуже (без `version_seq` порядок версий не восстановить — он
упорядочивается по `Created` с явной пометкой в отчёте), но данные вернутся.
Это свойство и есть причина выбрать pax, а не произвольную склейку.

## Последствия

- **Проще:** формат каждого артефакта проверяется тестом отдельно; битый индекс
  перестаёт быть молчаливой подменой порядка; повреждение индекса не стоит
  потерянных данных.
- **Сложнее:** четыре версии формата вместо одной; утилита печати индекса
  (иначе бинарный индекс не отладить); `rebuild-meta` обязан уметь читать пачку
  без индекса — отдельный путь и отдельные тесты.
- **Надо посчитать в спайке:** накладные расходы pax на мелких участников.
  Заголовок ustar — 512 байт, плюс расширенный заголовок pax и выравнивание,
  то есть на объект в 1 КиБ накладные расходы сопоставимы с самим объектом.
  Это всё равно дешевле отдельного файла в индексе LTFS (файлmark + запись
  индекса + стоимость перемотки), но порог `pack.threshold` сверху эту картину
  не ограничивает: снизу он ничего не даёт, и цифры надо иметь до выбора
  `pack.target_size`.

## Отклонённые альтернативы

- **JSON вместо бинарного индекса.** Человекочитаемо, но размер записи
  непредсказуем, а индекс и так нельзя читать «глазами» без утилиты — он
  бинарный и с UUID.
- **MAC на ключе тенанта для индекса.** Не работает: индекс смешанный и открытый,
  ключей у читающего может не быть вовсе.
- **Хранить `index_sha256` в атрибутах.** Поместилось бы, но атрибуты — про
  пачку целиком, а контрольная сумма обязана читаться вместе с тем, что
  проверяется, иначе «проверили не то» становится возможным.
- **Свой компактный формат вместо tar.** Меньше накладные расходы, но теряется
  единственное, ради чего он нужен, — чтение потока стандартным обходным
  способом при повреждённом индексе.
- **Один ADR на формат и протокол mover.** Протокол — граница между процессами,
  она меняется вместе с обоими бинарями без миграции данных; в одном документе он
  либо раздувал бы ревью формата, либо проходил бы ту же строгость, которая
  оправдана только для неизменяемого формата. Поэтому ADR-0021.
