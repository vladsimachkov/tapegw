# M0-03 — потокобезопасность libphobos

**Статус: вывод по исходникам Phobos `2e3311f` (pkg 3.4.1); стендовая проверка не
выполнена.** В этом окружении нет ни сборки Phobos, ни ленточного стенда, поэтому
ниже — разбор кода, а не прогон. Он достаточен, чтобы зафиксировать проектное
решение, но не достаточен, чтобы считать спайк закрытым.

## Что проверяли

Можно ли вызывать `phobos_put`/`phobos_get` из нескольких горутин одновременно, и
какое из этого следует значение `phobos.max_inflight`.

## Что получилось

### 1. Контекст — глобальная переменная процесса

`src/core/common/global_state.c`:

```c
static struct phobos_global_context *PHO_CONTEXT;
static __thread struct phobos_thread_context *PHO_THR_CONTEXT;
static pthread_mutex_t PHO_CONTEXT_LOCK = PTHREAD_MUTEX_INITIALIZER;
```

Инициализация — `int phobos_init(void)` (`src/store/store.c:104`), без аргументов
и без возвращаемого хендла: `phobos_context()` отдаёт единственный экземпляр на
процесс.

### 2. В слое данных мьютексов нет

`grep -c pthread_mutex` по каталогам:

```
src/store/*.c                 0
src/core/communication/*.c    0
```

Единственные мьютексы в дереве — инфраструктурные: `global_state.c` (рефкаунт
инициализации контекста и `config.lock`), `type_utils.c` (универсальная
потокобезопасная очередь), `lrs/*` (отдельный планировщик ресурсов со своими
потоками), `ldm_lib_scsi.c`, `module-loader` (`modules_rwlock`).

### 3. Есть прямые указания в комментариях

`src/core/cfg/cfg.c:87`:

> This is NOT thread safe and must be called before any call to other

`src/module-loader/module_loader.c:218`:

> In case it does, one may not assume thread-safety, so we report this error
> instead of previous ones.

### 4. API батчевый, а не параллельный

```c
int phobos_put(struct pho_xfer_desc *xfers, size_t n,
               pho_completion_cb_t cb, void *udata);
```

Параллелизм заложен **внутри** вызова: `n` дескрипторов и колбэк на каждый
перенос. `src/store/store.c:2124` показывает, что внутри одного вызова уже
используется `phobos_locate` по списку. То есть модель Phobos — «один вызов,
много объектов, параллельность внутри», а не «много вызовов из своих потоков».

## Вывод для tapegw

**libphobos считать однопоточной.** Все вызовы слоя данных сериализуются одним
процессным мьютексом; параллелизм достигается размером батча `n` внутри одного
вызова, а не числом потоков внутри библиотеки. Зафиксировано в
[ADR-0006](../adr/0006-libphobos-linkage.md).

Два возражения, которые часто приводят против этого вывода, не работают:

- **cgo не мешает сериализации.** Мьютекс ложится поверх cgo-обёртки так же
  хорошо, как поверх чистой Go-функции. Более того, он же становится точкой
  измерения «времени внутри Phobos».
- **LGPL не мешает динамической линковке.** Правило 12 это допускает; статической
  линковки в плане никогда не было.

Отдельно: `phobos.max_inflight` при таком решении — **не** «сколько горутин лезет в
libphobos». Что именно за ней стоит (размер батча или число процессов-воркеров со
своим контекстом у каждого) — определяет спайк 2, а не этот разбор.

## Что осталось проверить стендом

1. Формально подтвердить однопоточность: `N` потоков делают `phobos_put` по разным
   объектам на разных драйвах, искать повреждение метаданных и гонки под TSan.
2. Главный вопрос спайка 2, который здесь остался без ответа: **использует ли один
   вызов `phobos_put` с `n` объектами несколько драйвов параллельно.** Если нет,
   одна горутина ограничивает пропускную способность одним драйвом, и тогда
   воркеров должно быть несколько процессов, каждый со своим контекстом Phobos.
