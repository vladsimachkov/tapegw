# ADR-0003. Семантика класса STANDARD

- **Статус:** ожидает решения владельца (блокирует M1)
- **Дата:** 2026-11-02
- **Этап плана:** M1, влияет на M2 и M4
- **Связано:** `docs/ARCHITECTURE.md`, «Модель данных» (`objects.storage_class`),
  `spool.default_storage_class`;
  [`docs/reviews/2026-11-02-architecture-review.md`](../reviews/2026-11-02-architecture-review.md) §M4

## Контекст

`objects.storage_class` по умолчанию `GLACIER`, в конфиге `default_storage_class: GLACIER`.
При этом клиент волен прислать `x-amz-storage-class: STANDARD` — это делают rclone и aws
cli по умолчанию для части путей.

Документ не определяет, что с таким объектом происходит. Варианты ведут в разные стороны:

- Если `STANDARD` означает «живёт на диске навсегда», это второй режим хранения: свои
  переходы конечного автомата, своя политика вытеснения, свои тесты. В «Не цели MVP»
  такого пункта нет, а по объёму работы это как раз отдельное решение.
- Если класс игнорируется, клиент получает 200 и уверенность, что у него быстрый класс,
  которого нет. Через полгода это всплывает как «почему мой бэкап читается с ленты».
- Если класс отвергается, часть клиентов падает на первой же загрузке.

Связанное отклонение уже допущено молча: в HEAD/LIST объект показывает `STANDARD`, пока
не ушёл на ленту, и `GLACIER` после. В AWS объект класса GLACIER выглядит как GLACIER
сразу после PUT. Клиенты, которые по storage class решают, можно ли объект читать,
ошибаются в обе стороны.

## Решение

Не принято. Ниже два кандидата, нужен выбор владельца: он влияет на схему, автомат и
набор S3-операций в e2e, поэтому его нельзя отложить до M4.

### Кандидат A — единственный класс, всё на ленту

Любой входящий `x-amz-storage-class` принимается и игнорируется, все объекты архивируются.
В `HEAD`/`LIST` всегда `GLACIER`, независимо от состояния объекта.

- Плюс: автомат остаётся как спроектирован, кода нет, поведение предсказуемо.
- Минус: молча игнорируем явное намерение клиента.

### Кандидат B — отвергать чужие классы

Принимается только `GLACIER` (и пустой заголовок), остальное — `NotImplemented` через
`BackendUnsupported`-подобный путь, как это делает versitygw для неподдерживаемых операций.

- Плюс: никакого тихого расхождения ожиданий; клиент узнаёт о ограничении сразу.
- Минус: часть типовых клиентов (rclone с явным `STANDARD`) требует настройки. Нужно
  написать в инструкции развёртывания, какую опцию rclone/aws cli выставить.

Рекомендация: **B**. Тихое игнорирование в системе, где цена несоответствия — потерянные
часы на чтение с ленты, хуже явного отказа. Плюс B согласуется с правилом 4:
неподдерживаемое выражается явно.

В любом случае надо решить и второй вопрос: показывать ли `GLACIER` уже в состоянии
`pending` (тогда совпадение с AWS полное) или оставить `STANDARD` до архивации (тогда
нужен ADR про отклонение).

## Последствия

Пока решение не принято, M1 не может зафиксировать миграцию `objects.storage_class` и
валидацию заголовков в `internal/backend`.

## Отклонённые альтернативы

- **Полноценный `STANDARD` = «только диск».** Отклонено как объём за пределами MVP:
  нужен отдельный слой вытеснения, иначе landing кончится. Если решение понадобится —
  отдельный ADR после MVP, в списке «После MVP».
