# ADR-0016. Решения под тысячи тенантов

- **Статус:** принято 2026-11-03 (решение владельца: клиентов тысячи и больше)
- **Дата:** 2026-11-03
- **Этап плана:** **T1** (IAM-кэш), **T3** (планировщики, квоты), **T4** (учёт, админ-API)
- **Связано:** [ADR-0009](0009-tenant-model.md), [ADR-0011](0011-quotas.md),
  [ADR-0012](0012-fair-scheduling.md)

## Контекст

Ожидаемое число независимых клиентов — тысячи и больше. Это не «масштабирование
потом»: несколько решений в T1–T4 выглядят безобидно на десятке клиентов и становятся
проблемой на тысяче, а переделывать их после написания дорого.

## Решение

- **Пулы:** все тенанты в общих пулах; выделенный пул — исключение по запросу
  ([ADR-0013](0013-tape-pools.md)).
- **Метрики:** только агрегаты **без метки тенанта**. Учёт по клиенту — в
  `tenant_usage_daily`, выгрузка через админ-API.
- **Регистрация клиентов** — через админ-API: создание тенанта, ключей и квот одной
  операцией. CLI `tapegw admin tenant ...` — обёртка над ним. Ручных шагов оператора при
  подключении клиента нет.
- **IAM:** кэш аккаунтов в памяти с TTL и сбросом при изменении через `LISTEN/NOTIFY`
  Postgres.
- **Планировщики:** round-robin только по тенантам с непустой очередью
  (`DISTINCT ON (tenant_id)` в выборке батча), а не перебор всех тенантов.
- **Квоты:** строка `tenant_usage` на тенанта, без глобальных горячих строк.
- **Удаление тенантов** — штатный поток, а не редкая ручная операция: уничтожение TEK
  ([ADR-0014](0014-encryption-per-tenant.md)) делает его дешёвым; repack общих лент —
  фоновая задача по порогу доли мёртвых данных на ленте.

## Последствия

- **Метрики.** Метка `tenant` у Prometheus-серии при тысячах клиентов — это кардинальность,
  которая съедает память и замедляет каждый запрос. Агрегаты без метки дают «система в
  целом», а вопрос «как живёт конкретный клиент» решается выгрузкой из `tenant_usage_daily`,
  где для этого и есть строка на клиента.
- **Кэш IAM обязан сбрасываться, а не только истекать.** TTL в 30 секунд означает, что
  отозванный ключ работает 30 секунд. `LISTEN/NOTIFY` по таблице `accounts` делает отзыв
  мгновенным; TTL остаётся страховкой на случай потерянного уведомления.
- **Индексы под round-robin** заложены в миграции T0 (`objects_tenant_queue`,
  `restores_tenant_queue`) — иначе планировщик на тысяче тенантов будет перебирать пустые
  очереди.
- **Удаление тенанта как штатный поток** требует, чтобы оно было идемпотентным и
  возобновляемым после падения: оно идёт пачками через `deleting`, той же фоновой задачей,
  что и одиночные удаления.

## Отклонённые альтернативы

- **Метка `tenant` у метрик.** Соблазн понятен — сразу видно проблемного клиента. Но
  цена ложится на всю систему наблюдения, а точные данные есть в учёте.
- **Ручная регистрация клиента набором команд CLI.** На десятке клиентов терпимо, на
  тысяче — источник расхождений между клиентами. Поэтому CLI тонкий и над тем же API.
- **Глобальные счётчики «занято ли место».** Одна горячая строка на всю систему — точка
  спора всех транзакций; по тенанту спор только внутри тенанта.
