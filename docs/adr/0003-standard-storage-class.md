# ADR-0003. Классы хранения: входящие отвергаем, исходящие всегда GLACIER

- **Статус:** принято 2026-11-02
- **Дата:** 2026-11-02
- **Этап плана:** M1 (конфиг), M2 (проверка заголовка и заголовки ответов)
- **Связано:** `docs/ARCHITECTURE.md`, «Модель данных» (`objects.storage_class`),
  «Потоки запросов → HeadObject / ListObjects»;
  [`docs/reviews/2026-11-02-architecture-review.md`](../reviews/2026-11-02-architecture-review.md) §M4

## Контекст

tapegw — лента. Другого носителя в MVP нет, поэтому «быстрый класс хранения»
клиенту пообещать нечем. Вопрос в том, что делать, когда клиент класс всё-таки
присылает.

Проверено по исходникам клиентов: и `aws s3 --storage-class`, и rclone
`--s3-storage-class` передают заголовок **только при явной опции**, дефолта ни у
того, ни у другого нет. Утверждение предыдущей версии этого ADR, что клиенты
шлют `STANDARD` по умолчанию, неверно. Значит отказ почти ничего не стоит
на практике: молча сломается только тот, кто опцию выставил осознанно.

Второй конец того же вопроса — что показывать в ответах. Прежний план отдавал
`STANDARD`, пока объект не уехал на ленту, и `GLACIER` после. Это отклонение от
AWS в худшую сторону: клиент, который по storage class решает, можно ли объект
читать, видит `STANDARD` и читает, а через минуту тот же объект становится
`GLACIER` и читаться перестаёт.

## Решение

**Входящие.** Принимаем только те классы, которые честно означают «на ленту»:

- пустой заголовок — клиент намерение не выражал, пишем `GLACIER`;
- `GLACIER` — он и есть;
- `DEEP_ARCHIVE` — принимаем как синоним: разница с Glacier только в SLA,
  которого в MVP нет, а отказывать бэкап-софту незачем;
- всё остальное — `NotImplemented` (правило 4).

Для софта, жёстко прошитого на `STANDARD`, — явный список алиасов
`s3.accept_as_glacier: [STANDARD]`. Молча проигнорировать чужой класс хуже
отказа: клиент решит, что у него быстрый класс, и придёт читать с ленты.

**Исходящие.** В `HEAD` и `LIST` **всегда `GLACIER`**, независимо от состояния
объекта. Отклонение «STANDARD до архивации» убирается совсем.

**Онлайн-копия показывается как восстановленная — по одной колонке `objects.online_until`.**

Если копия объекта лежит на диске (в landing или в cache по restore), `HEAD`
отдаёт `x-amz-restore: ongoing-request="false", expiry-date=<online_until>`.
Так же делает scoutfs-бэкенд versitygw для онлайн-файлов, но у него дата
фиктивная и, как пишет его собственный комментарий, «not used». Настоящая дата
нужна потому, что обещание должно выполняться.

Первая версия этого ADR предлагала фиктивную дату `2 Dec 2050` для объектов в
состоянии `pending`/`archiving`. Это ломалось само:

1. PUT → объект `pending`, `HEAD` обещает доступность до 2050;
2. migrator архивирует объект, `HEAD` больше заголовка не отдаёт;
3. janitor вытесняет landing-копию;
4. GET через час → `InvalidObjectState`.

Клиент даты не трогал, а состояние поехало само — ровно то отклонение, от
которого ADR и уходил. Обратная странность той же схемы: `archived` с живой
landing-копией показывался без заголовка (то есть «нужен restore»), хотя GET у
него работал.

Решение — одна колонка, а не два механизма:

| Событие | `online_until` |
| --- | --- |
| PUT / CompleteMultipartUpload | `now() + spool.landing_min_retention` |
| переход в `archived` | `max(online_until, archived_at + spool.landing_min_retention)` |
| RestoreObject / продление restore | `max(online_until, now() + days)` |
| вытеснение последней дисковой копии | остаётся как есть, заголовка уже нет |

Правила поверх неё:

- `HEAD`/`LIST`: если дисковая копия есть (`landing=true` или `restores` в
  `restored`) — `expiry-date = online_until`; копии нет — заголовка нет.
- Пока объект в `pending`/`archiving`, показываем
  `max(online_until, now() + landing_min_retention)`: архивация ещё не
  закончилась, и дата не должна «усыхать» под глазами клиента.
- **janitor вытесняет копию (любую: landing или cache) только при
  `state = 'archived' AND online_until < now()`.** Одно условие заменяет и
  ограничение на `pending`/`archiving`, и сверку с `restores.expires_at`.

Инвариант «объекты `pending` и `archiving` с диска не удаляются ни при каком
watermark» остаётся в силе, но **держится он на условии `state = 'archived'`, а
не на дате**. Дата тут не защитник: при задержке migrator дольше
`landing_min_retention` у ещё не заархивированного объекта `online_until`
успевает уйти в прошлое, и проверка по одной только дате вытеснила бы единственную
копию данных, за которые клиент уже получил 200. Условие по состоянию —
обязательное, убирать его «раз дата всё равно защищает» нельзя.

`restores.expires_at` никуда не девается — это срок жизни конкретной
восстановленной копии по запросу клиента. Но показанная дата теперь всегда
`online_until`, и она не может быть раньше реальной даты удаления файла.

## Последствия

- `objects.storage_class` перестаёт быть переменной величиной в пределах MVP:
  в метаданные пишем канонический `GLACIER`, колонку оставляем под будущие
  классы.
- Проверка входящего класса — одна функция `config.StorageClassAction`, уже есть.
- В `HEAD`/`LIST` нужен общий помощник «показывать ли объект восстановленным»,
  иначе логика разъедется по двум обработчикам.
- Миграция `0003_online_until`: колонка `objects.online_until` и частичный
  индекс `objects_evictable (online_until) WHERE state = 'archived'` — по нему
  janitor ищет кандидатов на вытеснение.
- Настройка `spool.landing_min_retention` (по умолчанию 24h). Это не «политика
  кэша», а величина обещания клиенту, поэтому она валидируется как обязательная.
- В `test/e2e`: отказ на `STANDARD`, `DEEP_ARCHIVE` проходит, алиас из конфига
  проходит, `x-amz-restore` во всех состояниях.
- Отдельный сценарий на «обещание не должно усыхаться»: PUT → `HEAD` (запомнить
  дату) → архивация → вытеснение по watermark → `HEAD` ещё раз. Дата обязана
  быть не раньше первой, а до неё GET обязан работать.
- Правило 6 (fsync → commit) получает оговорку: при вытеснении файла порядок
  обратный, см. ADR-0004.

## Отклонённые альтернативы

- **Молча игнорировать любой входящий класс.** Дёшево, но это тихое расхождение
  ожиданий: клиент уверен в быстром классе, которого нет.
- **Отвергать и `DEEP_ARCHIVE` too.** Тоже честно, но отказывает клиентам,
  которые по смыслу просят ровно то, что мы умеем.
- **Полноценный `STANDARD` = «навсегда на диске».** Отдельный слой вытеснения и
  своя политика — за пределами MVP, осталось в списке «После MVP».
- **Показывать `STANDARD` до архивации** (как планировалось раньше). Худший
  вариант: состояние клиента меняется само, без его действий.
