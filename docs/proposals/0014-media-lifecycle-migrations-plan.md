# Жизненный цикл носителей, копии и миграции: порядок разработки

- **Статус:** решения владельца 2026-11-05, собраны в один план
- **Куда положить:** `docs/proposals/0014-media-lifecycle-migrations-plan.md`
- **Дополняет:** 0011 (repack), 0012 (разделение серверов), 0013 (копии, размещение,
  реестр носителей). Где 0014 уточняет 0013, действует 0014.
- **Затрагивает:** ADR-0020 (формат), ADR-0021 (протокол mover), ADR по копиям (новый),
  M4, M5, M7–M9, работы после MVP

## Зачем документ

За последние обсуждения появилось много сценариев работы с лентами. Все они держатся на
одной основе — политика размещения пула, реестр носителей и фоновая сверка (reconciler)
из 0013 — но предъявляют к ней разные требования, и часть требований меняет то, что
**фиксируется первой записью на ленту**. Документ собирает их и задаёт порядок: что
обязательно до кода migrator, что входит в MVP, что после.

## Сценарии, которые должна поддерживать система

| # | Сценарий | Пример |
| --- | --- | --- |
| С1 | Две копии в одной библиотеке | Одна копия на левой стороне, другая на правой |
| С2 | Ленивая миграция поколения | К двум LTO-7 добавили два LTO-8: новое пишется на LTO-8, старое переезжает постепенно |
| С3 | Запрет записи на устаревшее | После появления LTO-8 на ленты LTO-7 ничего не пишется; то же для старых версий нашего формата |
| С4 | Слив носителей по месту | MSL4048, 4 магазина по 12 лент LTO-7, всё занято. Освободить магазин 4, вынуть, поставить магазин с LTO-8 |
| С5 | Переезд на другую библиотеку | 24 слота → 48: физический перенос картриджей или копирование через драйвы |
| С6 | Миграция через чтение и запись | Новый формат пачки, уплотнение, новая библиотека без совместимости |
| С7 | Перекодирование | Новая версия формата сегментов или манифеста (нужны ключи) |
| С8 | Восстановление потерянной копии | Копия оказалась нечитаемой — пересоздать из живой |
| С9 | Копия вне площадки (Б4) | Третья копия с `site:vault`, лента физически вывезена |

**Сквозной приёмочный сценарий — С4** (MSL4048). Он задействует почти всё: запрет записи
на LTO-7, слив по месту, проверку ёмкости, чтение на LTO-7 и запись на LTO-8, выгрузку
лент и уплотнение. Если С4 проходит на стенде от начала до конца, основа готова.

---

## Принятые решения

**Р1. Копии — отдельные объекты Phobos из одного буфера.** Данные идут в буфер mover один
раз; mover выполняет по `put` на каждую копию политики, со своими тегами и своим oid
(`<uuid>.<имя копии>`). Ленту при этом ничего не читает. Встроенные копии Phobos не
используются:
- `phobos copy create` читает первую ленту, чтобы записать вторую, и занимает два драйва;
- `raid1` пишет все реплики с одним набором тегов и не разводит их по сторонам;
- **`put --overwrite` запрещён:** он создаёт новую версию объекта и молча делает старые
  копии недоступными (спайк M0-11). Вносится в список запрещённых операций рядом с
  прямым `phobos delete`.

**Р2. Объект архивный, когда записаны все копии текущей политики.** До этого landing не
очищается.

**Р3. Версия формата — у каждой копии**, а не одна на систему. Во время миграции живут
копии в разных форматах; читатель выбирает декодер по версии копии.

**Р4. Правило поддержки форматов.** Код чтения формата удаляется, только когда в установке
не осталось ни одной живой копии в нём. Проверка — запросом к `archive_copies`.

**Р5. Запись на устаревшее блокируется в три слоя:**
1. политика пула (теги поколения);
2. флаг `writable: false` у поколения в конфиге tapegw: ленты получают `read_only`,
   политика со ссылкой на запрещённое поколение отклоняется при старте, migrator и
   reconciler не выбирают такие ленты целью;
3. в Phobos у лент запрещённого поколения снимается разрешение на запись (флаг `put`
   носителя), чтение и удаление остаются.

`tapegw admin verify` и проверка при старте сверяют слои между собой. Так же для
нашего формата: одна текущая версия для записи, старые — только чтение.

**Третий слой надо перепроверять после `repack` и `tape format`.** Не проверено,
сбрасывают ли эти операции флаги доступа носителя (в [спайке
M0-12](../spikes/M0-12-write-flag-mailslots.md) осталось в «не закрыто»), а
молча вернуть себе право записи на ленту запрещённого поколения — ровно тот
сценарий, ради которого третий слой и нужен: он прикрывает ручной `phobos put`
мимо tapegw. Поэтому процедура вывода поколения (`drain`) заканчивается сверкой
`put_access` у всех лент поколения, а не только переводом в `read_only`.
`tapegw admin verify` это и так поймает при следующей сверке, но узнать на шаге
вывода дешевле, чем через неделю из отчёта.

**Р6. Слив носителей — по любому признаку:** магазин, диапазон слотов, список лент,
поколение. Слитые ленты — источник для переноса, но не цель записи.

**Р7. Контейнерный перенос — без ключей, на сервере библиотеки.** Участник пачки и крупный
объект переносятся побайтно; mover ключей не получает (ADR-0007). При переносе между
драйвами одного сервера данные **не ходят через сервер S3**: прочитанное одним mover
передаётся другому локально (см. Ф0.4).

**Р8. Перекодирование — с ключами, на сервере S3.** Данные читаются в служебный буфер
tapegw, расшифровываются, шифруются заново и уходят на ленту новой копией.

**Р9. Миграция не видна клиенту.** Версия, `versionId`, ETag, контрольные суммы,
блокировка не меняются. Миграционное чтение не трогает `online_until`, не показывает
`x-amz-restore`, не занимает клиентский кэш и не входит в квоты тенантов.

**Р10. Старая копия умирает только после проверки новой.** Для контейнерного переноса —
SHA-256 участника или объекта; для перекодирования — расшифровка новой копии и сверка
MD5/ETag с исходным объектом.

**Р11. Метка ленты уникальна во всей установке.** Библиотека — где лента сейчас, а не часть
её имени.

## Порядок разработки

### Фаза 0. До кода migrator (обязательно)

То, что фиксируется формой таблиц, форматом на ленте и протоколом. После первой записи
на ленту меняется только миграцией всего архива.

### Фаза 1. MVP (вместе с M4, M5, M7–M8)

| # | Что | Этап |
| --- | --- | --- |
| Ф1.1 | Migrator пишет копии по политике пула (по `put` на копию из одного буфера), объект `archived` после всех копий | M4 |
| Ф1.2 | Выбор копии при restore: смонтированная лента, свободный драйв; при ошибке — другая копия, сбойная получает `lost` | M5 |
| Ф1.3 | Состояние «носитель недоступен»: запрос ждёт со статусом и алертом, без бесконечных повторов | M5 |
| Ф1.4 | Запрет записи на устаревшее поколение и формат — все три слоя (Р5) и проверка согласованности | M4 |
| Ф1.5 | **Добавление ленты одной операцией tapegw:** проверка уникальности метки, теги пула, поколения и стороны, форматирование, запись в `media` | M4 |
| Ф1.6 | **Сбор атрибутов MAM при каждой загрузке** в `media.attrs` и `media_events` — с первого дня, иначе истории для политик здоровья не будет. Читать только в окнах Load/Unload, где LTFS в драйве нет, и только из MAM: `phobos`-овский `stats.nb_load` на стенде вечно ноль, а `Load count` из MAM растёт. Проверка поведения на реальном драйве — M8 | M7/M8 |
| Ф1.7 | Сторона слота из геометрии и проверка «лента не меняет сторону» при каждой выгрузке | M7/M8 |

**Критерий завершения фазы 1:** С1 работает (две копии на разных сторонах; restore
при `lost` одной копии); С3 работает (запись на LTO-7 невозможна ни через политику, ни
через ручной `phobos put`).

### Фаза 2. После MVP

| # | Что | Сценарии |
| --- | --- | --- |
| Ф2.1 | **Ядро reconciler:** сравнение фактических копий с политикой; дописывание недостающих; восстановление `lost`; приоритеты, окна простоя, лимиты драйвов | С8 |
| Ф2.2 | **Ленивая миграция поколения:** смена тега поколения в политике; чтение на старых драйвах, запись на новых; перенос при restore | С2 |
| Ф2.3 | **Слив по месту** (Р6): `tapegw admin media drain --magazine N / --slots / --labels / --generation`; ленты → `evacuating`; уведомление «магазин можно вынимать» | С4 |
| Ф2.4 | **Планировщик ёмкости:** сколько живых данных надо перенести, сколько места в целевом размещении, сколько лент добавить; прогноз окончания по фактической скорости; отказ начинать слив без места с готовым планом действий | С4, С2 |
| Ф2.5 | **Выгрузка лент:** через почтовые слоты (SCSI-библиотеки) или манипулятор; лента → `retired` / `offline` | С4, С9 |
| Ф2.6 | **Контейнерная миграция** через чтение и запись: новый формат пачки, уплотнение (заменяет часть 3 из 0011) | С6 |
| Ф2.7 | **Перекодирование** на стороне S3 (Р8) | С7 |
| Ф2.8 | **Переезд библиотеки:** физический перенос с `phobos tape rename --new-library`; копирование через драйвы — тот же reconciler | С5 |
| Ф2.9 | **Копия вне площадки:** спецификация копии `site:vault`, учёт вывезенных лент, ввоз для restore | С9 |
| Ф2.10 | **Политики здоровья:** вывод лент по истории (загрузки, ошибки, TapeAlert); проверка целостности (scrubber) с записью в `media_events` | С8 |

**Порядок внутри фазы 2:** Ф2.1 → Ф2.4 → Ф2.3 + Ф2.5 → Ф2.2 → Ф2.6 → Ф2.8 →
Ф2.10 → Ф2.7 → Ф2.9. Сначала ядро и планировщик ёмкости, потому что без них любой
слив или миграция — это «непонятно когда и хватит ли места». Сценарий С4 — первая
приёмка фазы 2.

## Сценарий С4 по шагам (приёмочный)

Исходно: MSL4048, 4 магазина × 12 лент LTO-7, все заняты; драйвы 2× LTO-7 + 2× LTO-8.

1. `LTO-7: writable: false` — новые данные идут только на LTO-8 (Р5).
2. `tapegw admin media drain --magazine 4 --dry-run` — отчёт планировщика: живых данных
   X ТБ, свободно в `gen:lto8` Y ТБ, нужно вставить K лент LTO-8, прогноз Z дней.
3. Если вставить некуда — слив начинается с лент магазина 4 с наименьшим объёмом живых
   данных: их данные уходят в мёртвое место других лент (уплотнение). Освободившаяся
   лента выгружается, на её место ставится LTO-8 (Ф1.5). Каждая LTO-8 вдвое ёмче LTO-7,
   дальше процесс ускоряется сам.
4. Слив в фоне: чтение на драйвах LTO-7, запись на LTO-8, данные между ними передаются
   локально на сервере библиотеки (Ф0.4); приоритет ниже клиентских операций.
5. Лента без живых данных → `retired`.
6. Магазин 4 без живых данных → уведомление «можно вынимать».
7. Замена магазина, пересканирование инвентаря, добавление новых лент LTO-8 (Ф1.5).

Проверки: на всех шагах restore клиентов работает; ни одна копия не удалена до
проверки новой; после шага 6 `tapegw admin verify` чист; запись на LTO-7 за всё время —
ноль.

## Тесты по фазам (выборка, к реализации)

- **Ф0:** в схеме нет колонок носителя вне `archive_copies`; копия без версии формата
  не вставляется; политика пула со ссылкой на `writable: false` отклоняется при старте.
- **Ф1:** две копии на разных сторонах; `archived` только после второй копии; restore
  при `lost`; ручной `phobos put` на ленту LTO-7 отклоняется Phobos; повторная метка
  ленты отклоняется.
- **Ф2:** слив магазина на стенде mhVTL от начала до уведомления; отказ слива без места
  с планом; старая копия не умирает при несовпадении SHA-256 новой; миграция не меняет
  ETag, `versionId`, блокировку и квоту тенанта.
