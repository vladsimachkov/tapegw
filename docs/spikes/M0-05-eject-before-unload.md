# M0-05 — кто выгружает ленту из драйва перед unload

**Статус: закрыт по исходникам Phobos `2e3311f` (pkg 3.4.1).**

## Что проверяли

`TLC Unload` приказывает робототехнике переложить картридж из драйва в слот.
Если в этот момент лента затянута в головку драйва, экстрактор хватает её силой
— это механическое повреждение и картриджа, и привода. Значит перед MOVE MEDIUM
лента должна быть разгружена из механики драйва (rewind + eject/offline).
Вопрос: кто это делает в штатном потоке Phobos.

## Что получилось

### 1. В TLC-разгрузке шага eject нет

`src/tlc/tlc_library.c:897`, `tlc_library_unload()` делает ровно четыре вещи:
проверяет, что драйв не пуст; сверяет `expected_tape` с `vol`; ищет свободный
слот; перекладывает:

```c
PHO_RETRY_LOOP(rc, tlc_library_retry_func, lib,
               cfg_tlc_max_device_retry(lib), scsi_move_medium,
               lib->fd, 0, drive_element_status->address,
               target_element_status->address, log.message);
```

Ни rewind, ни LOAD UNLOAD, ни eject. Функция предполагает, что лента уже
готова к захвату.

### 2. Сам Phobos rewind не выдаёт никогда

Поиск по всему `src/` не находит `MTOFFL`, `MTNOP`, `LOAD UNLOAD` ни в одном
исходнике. Единственное вхождение «offline» — про состояние элемента в
`src/tlc/scsi/scsi_common.c:141`, не про команду драйву.

### 3. Разгрузку драйва делает libltfs, через слой LDM

Жизненный цикл LTFS живёт в `src/ldm-modules/ldm_fs_ltfs.c`, и он не встроенный,
а **настраиваемые shell-команды** (`cfg_ltfs`):

```c
[PHO_CFG_LTFS_cmd_mount]  = "…/pho_ldm_helper mount_ltfs \"%s\" \"%s\""
[PHO_CFG_LTFS_cmd_umount] = "…/pho_ldm_helper umount_ltfs \"%s\" \"%s\""
```

А `scripts/pho_ldm_helper` — это bash:

```bash
function mount_ltfs {
    ltfs -o devname="$dev" "$mnt" -o sync_type=unmount
}

function umount_ltfs {
    # находит pid процесса ltfs по /proc/$pid/fd, затем
    umount "$mnt" || exit 1
    # и ждёт выхода процесса ltfs (shutdown_timeout=300)
}

function release_ltfs {
    ltfs -o release_device -o devname="$drive"
}
```

То есть разгрузка драйва — это выход процесса `ltfs`: при размонтировании он
сматывает ленту и разжимает механику. `release_ltfs` (`ltfs -o release_device`)
— отдельная операция «отпусти устройство», если размонтирования не было.

### 4. Порядок, который из этого следует

```
запись/чтение в точку монтирования LTFS
  → setxattr(root, "user.ltfs.sync", 1)      # сброс индекса на ленту
  → umount <mnt>                             # cmd_umount
  → дождаться выхода процесса ltfs           # rewind + eject внутри libltfs
  → TLC Unload                               # теперь можно MOVE MEDIUM
```

Пропуск любого шага перед `TLC Unload` — это MOVE MEDIUM по ленте, затянутой в
головку.

## Вывод для tapegw

**Процесс, который вёл ввод-вывод, обязан владеть всем жизненным циклом LTFS
этого драйва и довести его до конца до запроса Unload.** Это не «желательно,
чтобы не рассинхронизироваться», а требование физической безопасности: tapegw или
klipper-tlc не имеют права попросить Unload, пока держат монтирование.

Практические следствия:

- **Нужен хранитель монтирований на каждый драйв** — тот, кто монтирует, размонтирует
  и ждёт выхода `ltfs`. Если монтирование живёт в tapegw, а Unload отправляет
  klipper-tlc, порядок никто не гарантирует: два процесса должны договориться о
  том, кто первый. Однозначный вариант — **и mount, и Unload отправляет один и тот
  же процесс** (klipper-tlc), а tapegw только просит и ждёт.
- **Таймаут разгрузки не может быть коротким.** Хелпер ждёт выхода `ltfs` до 300
  секунд, и это не зависание: сматка ленты занимает минуты. В `config` нужна
  отдельная настройка на ожидание разгрузки, заметно больше `db.lock_timeout`, и
  в ней нет ошибки.
- **`pgrep ltfs` + разбор `/proc/$pid/fd` — хрупкое место.** Хелпер ищет процесс
  по совпадению имени устройства в дескрипторах; при нескольких драйвах и
  неаккуратных симлинках возможны ложные совпадения. На стенде M0-07 стоит
  проверить это на двух драйвах сразу, а не на одном.
- **Правило 13 из `AGENTS.md` здесь не просто гигиена.** Транзакция Postgres,
  открытая на время mount/umount, виси бы минуты и держала advisory-лок ключа.

## Что остаётся проверить на стенде

Что libltfs при `umount` действительно отдаёт ленту (offline) на виртуальных
драйвах mhVTL, и что `ltfs -o release_device` идемпотентен при повторе после
упавшего процесса `ltfs`. Это M0-07.
