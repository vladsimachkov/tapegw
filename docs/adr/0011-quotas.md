# ADR-0011. Квоты: резерв в транзакции, коды из versitygw

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** **T3** (вместе с M4–M5)
- **Связано:** [ADR-0005](0005-key-rewrite-advisory-lock.md),
  [ADR-0016](0016-thousands-of-tenants.md)

## Контекст

Всё общее — landing, кэш, очереди restore, драйвы — делится между клиентами. Без
явных лимитов один тенант с большим бэклогом останавливает остальных: забивает landing,
и PUT других клиентов начинают получать `SlowDown`, которого у них по их объёму быть не
должно.

Ключевое требование: **`SlowDown` получает только тот, кто превысил свою долю**, а не
все, у кого есть несчастье работать в тот же момент.

## Решение

| Лимит | Что защищает | Где проверяется | Ответ |
| --- | --- | --- | --- |
| `storage_bytes`, `objects` | ёмкость лент | PutObject, CompleteMultipartUpload | `QuotaExceeded`, 403 |
| `landing_bytes` (pending + archiving + части multipart) | общий landing | PutObject, UploadPart | `SlowDown`, 503 — только этому тенанту |
| `restore_queue_bytes`, `restore_inflight` | очередь recaller | RestoreObject | запрос принимается, стоит в очереди тенанта |
| `cache_bytes` | общий кэш | recaller перед выдачей | ждёт освобождения кэша тенанта |
| `requests_per_second` | CPU и соединения | middleware `s3api.WithMiddleware` | `SlowDown`, 503 |
| `buckets` | — | CreateBucket | `TooManyBuckets` |

Значения по умолчанию — в конфиге (правило 9), переопределения — в `tenants.limits`.

**Механика.** Счётчики — таблица `tenant_usage`, по строке на тенанта. Резерв на PUT —
атомарный

```sql
UPDATE tenant_usage
   SET storage_bytes = storage_bytes + $n
 WHERE tenant_id = $1 AND storage_bytes + $n <= $limit
RETURNING ...
```

в **той же транзакции**, что вставка объекта, после advisory-лока
[ADR-0005](0005-key-rewrite-advisory-lock.md). Ноль затронутых строк означает «не
прошло квоту» — отказ. Освобождение — в той же транзакции, что перевод объекта в
`deleting`.

Раз в сутки — сверка счётчиков с фактической суммой по `objects` и **метрика
расхождения**. Метрика, а не молчаливое исправление: расхождение означает баг в учёте,
и чинить его надо по алерту, а не пересчётом, который спрягает проблему.

## Последствия

- Коды брать из versitygw, своего писать не нужно: `ErrQuotaExceeded` (403,
  `QuotaExceeded`) и `ErrSlowDown` уже есть в `s3err`. Для `TooManyBuckets` кода нет —
  если лимит на число бакетов делается, код свой.
- Резерв в той же транзакции, что и вставка, — иначе между проверкой и вставкой влезает
  параллельный PUT, и квота превращается в рекомендацию.
- Строка `tenant_usage` — точка конкуренции транзакций одного тенанта. Для тысяч
  тенантов это приемлемо, потому что спор идёт только внутри тенанта; глобальных
  строк-счётчиков сознательно нет (см. [ADR-0016](0016-thousands-of-tenants.md)).
- Некурентные версии и delete markers **тоже** считаются в `storage_bytes` и `objects`
  — иначе бакет с историей выглядел бы дешёвым, а ленты были бы забиты
  ([ADR-0015](0015-versioning-and-object-lock.md)).

## Отклонённые альтернативы

- **Считать объём запросом `SELECT sum(size)` при каждом PUT.** Точнее по определению,
  но на полной таблице в горячем пути. Суточная сверка даёт ту же точность с алертом.
- **Квота «на бакет».** Клиент управляет тенантом, а не бакетом; бакетов у тенанта
  много, и квота на бакет заставила бы клиента дробить данные ради лимита.
- **Отдельный сервис квот.** Ещё одна точка отказа и ещё один источник правды.
