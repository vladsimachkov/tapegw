# Хвост ревью PR #1 — взять в M2

Ревью `4afc7ac` закончилось approve и мержем (`82809aa`). Четыре замечания
ревьюер отнёс к M2, потому что там появляется PUT и эти поля начинают реально
использоваться. Здесь они зафиксированы, чтобы не потерялись.

## 1. `objects.online_until` сделать NOT NULL

Сейчас колонка nullable. `NULL < now()` в SQL даёт `NULL`, то есть условие
`state = 'archived' AND online_until < now()` для строки с `NULL` никогда не
выполнится. Любой путь записи, который забудет заполнить дату — `CopyObject`,
`CompleteMultipartUpload`, — породит объект, который janitor не вытеснит никогда,
и landing будет тихо заполняться до отказа.

В M2:

- `ALTER TABLE objects ALTER COLUMN online_until SET NOT NULL` — первой
  миграцией M2, пока таблица пуста и переписывание не нужно;
- `SET NOT NULL` без `DEFAULT` сознательно: дата вычисляется из
  `spool.landing_min_retention` в коде, а `DEFAULT now()` в схеме развязал бы
  эту логику и сделал бы её разной в разных путях записи.

## 2. Сузить `objects_evictable`

Предикат `WHERE state = 'archived'` индексирует все архивные объекты, а у
подавляющего большинства дисковой копии уже нет — индекс разрастается и содержит
в основном строки, которые выборке не подходят.

Для вытеснения landing лучше `WHERE state = 'archived' AND landing`. Копии из
cache janitor может находить через `restores` — там и так есть `restores_expired`
по сроку жизни.

Заодно в M2 стоит решить, нужен ли второй частичный индекс под `restores`-сторону
или существующего `restores_expired` достаточно.

## 3. Отсчёт срока restore от завершения, а не от запроса

В таблице ADR-0003 написано, что RestoreObject даёт
`max(online_until, now() + days)` в момент запроса. В AWS `Days` считается от
**завершения** восстановления. У нас очередь recaller стоит на ленту и может
ждать часы: если отсчитывать от запроса, клиент, заказавший `Days=1` при
задержке очереди в сутки, получит объект со сроком, истёкшим раньше, чем он его
увидел.

В M2: при переходе restore в `restored` recaller обязан ещё раз вычислить
`online_until = max(online_until, restored_at + days)`. `restores.days` для этого
уже хранится, отдельной колонки не нужно.

Формулировку в ADR-0003 поправить вместе с кодом, чтобы таблица и реализация не
разъехались.

## 4. Неточность в тексте ADR-0003 — исправлено в этом же подходе

Было сказано, что инвариант «`pending`/`archiving` не трогать» следует из того, что
у них `online_until` в будущем. Это неверно: при задержке migrator дольше
`landing_min_retention` дата уходит в прошлое у ещё не заархивированного объекта.
Инвариант держится на условии `state = 'archived'`.

Код был правильный, но формулировка приглашала потом убрать проверку состояния,
«раз дата всё равно защищает». Исправлено в ADR-0003 и в `ARCHITECTURE.md`
(там тот же абзац был продублирован).
