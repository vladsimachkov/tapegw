# M2-01: лимит пользовательских атрибутов Phobos и где хранить таблицу частей

- **Статус:** закрыт
- **Дата:** 2026-11-04
- **Phobos:** 3.4.1 (сборка из исходников, тег `3.4.1`), стенд `tapegw-vm` (AlmaLinux 9.8, mhVTL)
- **Вопрос от ревьюера:** есть ли в Phobos 3.4.1 ограничение на размер пользовательских
  метаданных. От ответа зависит, где хранить таблицу частей (`object_parts`: номер,
  открытый размер, смещение шифротекста, соль) при восстановлении объекта с ленты без
  нашей БД — в атрибутах Phobos или манифестом в конце файла.

## Краткий ответ

**Ограничение есть, и оно убивает вариант «атрибуты».** Одно значение xattr в LTFS
ограничено **4096 байтами**, а Phobos сериализует **все** пользовательские атрибуты
в один JSON в xattr `user.user_md`. Бюджет таблицы частей — весь этот JSON целиком.

Замеренный предел: значение **4079** байт проходит, **4080** — `ENOSPC`. Двоичной
записью в такой бюджет входит **84 части**. S3 допускает **10 000** — то есть в
119 раз больше. Вариант 1 не работает даже для объекта среднего размера, а не только
для предельного.

**Решение — вариант 2, манифест в конце файла.** Манифест на 10 000 частей весит
360 КБ, то есть 0,0007% от 50 ТБ объекта, и не упирается ни в какой лимит. Атрибутам
остаётся то, что действительно должно быть в атрибутах: обёрнутый DEK, версия KEK,
UUID версии, тенант, бакет, ключ, ETag — это десятки байт.

## Что именно ограничивает

Phobos кладёт каждое служебное поле отдельным xattr, а наши атрибуты — одним JSON:

```
$ getfattr -d -m - /mnt/phobos-sg2/01/c3/t_one.5b376908-...
user.copy_name="source"
user.extent_offset="0"
user.layout="raid1"
user.md5="3089750fadabf7eb59fc64d2a74c5432"
user.object_size="8388608"
user.object_uuid="3ef f94fa-101c-4938-86c0-65d9a66cc932"
user.raid1.extent_index="0"
user.raid1.repl_count="2"
user.user_md="{}"            <-- сюда попадает весь наш pho_attrs
user.version="1"
```

Значит лимит LTFS на одно значение xattr (4096) — это лимит на **наш JSON целиком**,
а не на каждый ключ. Проверено: 2 ключа по 2000 байт (сумма 4000) проходят, а
2 ключа по 2039 (сумма 4078) уже `ENOSPC`; 4 ключа по 1000 проходят, 4 по 1019 — нет.
Лимит именно суммарный.

Служебные поля Phobos в `user_md` не занимают наш бюджет — `phobos_getmd` вернул
только наши ключи.

## Замеры

### 1. Граница по размеру значения (семейство tape, библиотека `vtllib`)

Бинарный поиск по размеру одного значения, каждый зонд — своим `oid`
(повторный put того же объекта отвечает `EEXIST`, и первая версия пробника
деградировала в проверку существования):

```
probe  2560 -> ok
probe  3328 -> ok
probe  3712 -> ok
probe  3904 -> ok
probe  4000 -> ok
probe  4048 -> ok
probe  4072 -> ok
probe  4078 -> ok
probe  4079 -> ok
probe  4080 -> No space left on device (28)
MAX_VALUE_BYTES=4079
```

Разница 4096 − 4079 = 17 байт — обёртка JSON (`{"tapegw.md":"…"}\0`).

При 65536 и больше Phobos отвечает `E2BIG` (7, «Argument list too long») — то есть
свой предел есть и выше, но до него дело не доходит: LTFS отказывает раньше.

### 2. Значения обязаны быть валидным UTF-8

Не-ASCII байты **молча** заменяются на U+FFFD — и на входе API, и в документации CLI:

```
-m METADATA   Comma-separated list of key=value. Keys and values must be valid
              UTF-8: invalid bytes are silently replaced with the Unicode
              replacement character (U+FFFD). To store raw data in a value,
              encode it first (e.g. hexadecimal or base64)
```

Для таблицы частей это отдельная плата: двоичную запись пришлось бы кодировать
base64, **+33%**. В манифесте на ленте такой проблемы нет — там можно писать
двоичные структуры как есть.

### 3. CLI как измерительный инструмент не годится

`phobos put -m` не передаёт больше ~128 KiB — `execve` упирается в `ARG_MAX`:

```
value=65536B  b64=87384   -> rc=2
value=131072B b64=174764  -> Argument list too long
```

Настоящий лимит хранилища меряется только через `libphobos_store` (`pho_attr_set` +
`phobos_put`), чем и был сделан пробник на C.

### 4. Что стоит в DSS

`object.user_md` в DSS — это **`jsonb`**:

```
 objects | obj_table_total | max_user_md_bytes
---------+-----------------+-------------------
      28 | 144 kB          |              4096
```

DSS сам по себе столько не съест, но jsonb переставляет ключи и хранит бинарную
форму — то есть байт в байт исходный JSON не вернёт. Для таблицы частей это
означает: **атрибуты Phobos не могут быть каналом, по которому мы что-то
восстанавливаем байт-в-байт** (тот же урок, что и с `buckets.policy`, который мы
уже перевели из jsonb в text).

### 5. Бюджет таблицы частей

Запись части в компактном двоичном виде: номер 4 байта, открытый размер 8,
смещение шифротекста 8, соль 16 = **36 байт**.

| частей | размер в атрибутах (base64) | влезает в 4076? | манифест в конце файла | доля объекта |
| --- | --- | --- | --- | --- |
| 1 | 48 B | да | 52 B | ~0% |
| 10 | 480 B | да | 376 B | ~0% |
| 100 | 4800 B | **нет** | 3616 B | 0,0007% от 500 GiB |
| 1000 | 48000 B | **нет** | 36016 B | 0,0007% от 5 TiB |
| 10000 | 480000 B | **нет** | 360016 B | 0,0007% от 50 TiB |

**Предельное число частей в атрибутах — 84.** Минимальная часть S3 — 5 MiB, так что
объект в 420 MiB уже ломает вариант 1. Это не экзотика, а объект меньше гигабайта.

## Вывод для tapegw

1. **Таблица частей живёт в манифесте в конце файла объекта**, а не в атрибутах
   Phobos. Формат и размещение — [ADR-0019](../adr/0019-object-manifest-trailer.md).
2. **В атрибутах Phobos только то, что нужно для поиска и обёртки ключа**: обёрнутый
   DEK (base64), версия KEK, UUID версии, id тенанта, бакет, ключ, ETag. Это
   десятки байт, до лимита 4079 далеко, и ни один из этих полей не зависит от числа
   частей.
3. **Любые двоичные данные в атрибутах — только base64.** Молчаливая санитизация
   UTF-8 иначе испортит значение без единого признака ошибки. Это правило нужно и
   для DEK: 48 байт в base64 = 64 символа.
4. **Размер манифеста не нужен в конфиге.** 36 байта на часть, 10 000 частей —
   360 КБ; при `migrator.batch_max_bytes` это погрешность. Отдельного лимита на
   число частей вводить не нужно, S3 его уже задаёт (10 000).
5. **Что осталось немереным:** размер индекса LTFS. `ltfsck` требует размонтировать
   cartridge, а стенд занят `phobosd`; измерение отложено как `M2-01b`. На решение
   оно не влияет — лимит 4096 стал отказом варианту 1 сам по себе. Ориентир без
   замера: сейчас xattr объекта занимает ~100 байт значений, при переносе таблицы
   частей в атрибуты добавилось бы до 4 КБ на объект, то есть индекс вырос бы
   примерно в 40 раз на мелких объектах.

## Как воспроизвести

Пробники на C лежат вне репозитория (код спайков в основную ветку не попадает),
сборка на стенде:

```bash
cd /root/phobos
gcc -o /tmp/attr_edge /tmp/attr_edge.c -I src/include -I /usr/local/include \
  $(pkg-config --cflags glib-2.0 jansson) \
  -L/usr/local/lib -L/usr/lib64/phobos -lphobos_store -lpho_core \
  $(pkg-config --libs glib-2.0 jansson) -Wl,-rpath,/usr/lib64/phobos
LD_LIBRARY_PATH=/usr/lib64/phobos:/usr/local/lib /tmp/attr_edge
```

`-lpho_core` обязателен: без него линковка падает на `pho_attr_get`
(«DSO missing from command line»).
