# ADR-0001. RestoreObject всегда отвечает 200

- **Статус:** принято 2026-11-02
- **Дата:** 2026-11-02
- **Этап плана:** M5
- **Связано:** `docs/ARCHITECTURE.md`, раздел «Потоки запросов → RestoreObject»;
  спайк M0 №6; [`docs/reviews/2026-11-02-architecture-review.md`](../reviews/2026-11-02-architecture-review.md) §0.3

## Контекст

Архитектура обещает поведение AWS Glacier: `202 Accepted` на новый `RestoreObject`,
`200 OK` на продление уже существующего restore, `409 RestoreAlreadyInProgress`, если
восстановление идёт.

Проверено по versitygw v1.10.0:

- `backend.Backend.RestoreObject` объявлен как
  `RestoreObject(context.Context, *s3.RestoreObjectInput) error` — только `error`,
  кода успеха в сигнатуре нет;
- контроллер `s3api/controllers/object-post.go` возвращает
  `&Response{MetaOpts: &MetaOptions{BucketOwner, EventName}}, err`, поле
  `MetaOptions.Status` не заполняет;
- `ProcessController` при `Status == 0` подставляет `http.StatusOK`.

Код ошибки бэкенд задать может (через `s3err.S3Error`), код успеха — нет. Значит 409
работает, а различие 202/200 — нет. Спайк M0 №6 на эту тему больше не нужен.

## Решение

`RestoreObject` в tapegw во всех успешных случаях возвращает `200 OK`. Различия
«новый запрос / продление» клиент определяет по `x-amz-restore` в последующем `HEAD`,
как и в AWS. Отклонение от AWS фиксируем как известное и документированное.

## Последствия

Дополнение по итогам ревью: SDK AWS считают успехом любой 2xx, поэтому риск от
«200 вместо 202» ограничен самописными клиентами, которые сверяют ровно 202.
Это не меняет решения, но снижает его приоритет.

- В `docs/ARCHITECTURE.md` убрать обещание 202 и сформулировать: «успех — всегда 200;
  состояние restore клиент читает заголовком `x-amz-restore`».
- Пункт M0 «Может ли бэкенд versitygw влиять на код ответа RestoreObject» закрывается
  досрочно, без спайка.
- В `test/e2e` проверяем 200 и заголовки, а не 202. Клиентам, которые сверяют
  `StatusCode == 202`, это надо сообщить заранее.
- Код `409 RestoreAlreadyInProgress` остаётся как спроектировано.

## Отклонённые альтернативы

- **Перехватить `POST /{bucket}/{key}?restore` через `s3api.WithRoute`.** 202 достигается,
  но приходится заново реализовывать разбор тела `RestoreRequest`, проверку ACL и
  `s3:RestoreObject` — то есть дублировать логику контроллера versitygw и поддерживать её
  при каждом обновлении зависимости. Цена выше, чем польза от одного кода ответа.
- **Патч versitygw** (добавить `Status` в путь RestoreObject). Прямо противоречит правилу 3:
  исходники versitygw не патчатся.
- **Молча оставить 200 без ADR.** Ровно то, к чему документ шёл сейчас: расхождение
  обнаруживается только на клиенте, который на него наткнулся.
