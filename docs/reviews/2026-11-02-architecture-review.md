## 0. Что в документе устарело или неверно (проверено по upstream)

### 0.1 `major` — versitygw не отдаёт Prometheus

Раздел «Наблюдаемость»: *«S3: запросы по операции и коду ответа (если versitygw отдаёт
свои метрики — использовать их, не дублировать)»*, плюс `metrics: {listen: ":9464"}`.

В versitygw v1.10.0 **нет Prometheus вообще**: в `go.mod` нет ни одной
`github.com/prometheus/*`, а `metrics/` содержит только `statsd.go` и `dogstats.go`.
Единственный способ отдать метрики шлюза — `embedgw.Config.StatsdServers` /
`DogstatsServers`.

Практический вывод: счётчик «запросы по операции и коду ответа» из versitygw в Prometheus
не появится сам. Нужно выбрать один из путей и записать его в документ:

- **A.** tapegw поднимает свой `promhttp` на `:9464` и считает S3-операции сам — через
  middleware, см. 0.2. Тогда фраза «не дублировать» неактуальна.
- **B.** tapegw включает versitygw StatsD, а Prometheus получает данные через
  `prometheus-statsd-exporter`. Меньше кода, но метки и именование диктует versitygw.

Сейчас в документе написан вариант A с портом `:9464`, но оговорка про versitygw
создаёт ложное ожидание. Оговорку убрать, выбор зафиксировать.

### 0.2 `major` — шов для middleware на S3-порту есть, и он меняет два решения

В разделе «Наблюдаемость»: *«При landing выше high + запас PUT получает SlowDown (503)»*.
Ранее я утверждал, что `embedgw.RunVersityGW` владеет listener и шва для обёртки нет.
**Это неверно для v1.10.0.** В `embedgw.Config` есть поле

```go
// S3Options are appended to the internally built s3api options before the
// S3 server is created. This allows callers to inject custom behavior such
// as request middleware.
S3Options []s3api.Option
```

а в `s3api/server.go` — `WithMiddleware(prefix string, handler fiber.Handler)` и
`WithRoute(method, path string, handlers ...fiber.Handler)`; оба монтируются *после*
rate limiter и *до* таблицы S3-маршрутов.

Что из этого следует и надо внести в документ:

- `SlowDown` при переполнении landing **делается middleware-ом** через
  `S3Options: []s3api.Option{s3api.WithMiddleware("", ...)}`. Патчить versitygw не нужно,
  правило 3 не нарушается.
- Тот же шов закрывает `/health/ready` на S3-порту, если не хочется отдельный порт.
  Кроме того, в `embedgw.Config` уже есть поле `HealthPath` → `s3api.WithHealth`.
  В конфигу документа этого поля нет, добавить.
- Для админ-API тоже не нужен свой сервер: `Config.AdminPorts` +
  `s3api.WithAdminRoute`. Документ говорит «отдельный порт или префикс AdminPathPrefix» —
  это ровно штатный механизм, стоит назвать явно.

### 0.3 `major` — RestoreObject всегда отвечает 200, 202 недостижим

Раздел «Потоки запросов → RestoreObject» обещает: 202 для нового запроса, 200 для
продления, 409 при `RestoreAlreadyInProgress`. Спайк M0 №6 спрашивает, может ли бэкенд
влиять на код ответа.

Ответ: **нет**. `backend.Backend.RestoreObject` объявлен как

```go
RestoreObject(context.Context, *s3.RestoreObjectInput) error
```

— только `error`. Контроллер `s3api/controllers/object-post.go` вызывает бэкенд и
возвращает `&Response{MetaOpts: &MetaOptions{BucketOwner, EventName}}, err`, не заполняя
`MetaOptions.Status`. В `ProcessController` пустой `Status` заменяется на `http.StatusOK`.
Код ошибки бэкенд задать может (через `s3err.S3Error`), код успеха — нет.

Значит: 409 `RestoreAlreadyInProgress` работает, а различие 202/200 — нет. AWS на новый
restore отдаёт 202. Клиенты, которые проверяют `resp.StatusCode == 202`, отвалятся.

Варианты (нужен ADR):

- **принять 200 всегда** — дёшево, но это отклонение от AWS и его надо записать;
- перехватить `POST /{bucket}/{key}?restore` целиком через `WithRoute` и отвечать
  самому — 202 достигается, но вся логика SigV4/ACL/парсинга тела duplicated;
- патч versitygw — противоречит правилу 3.

Рекомендация: принять 200, пункт M0 №6 закрыть заранее, в M5 не исследовать.

### 0.4 `minor` — `RunVersityGW` один на процесс

`embedgw.RunVersityGW` использует атомарный guard `gatewayRunning` и возвращает ошибку
при повторном вызове. Для tapegw это безопасно (один вызов из `main`), но в документ стоит
записать как ограничение: **нельзя поднять второй S3-листенер через второй вызов
`RunVersityGW`**. Все дополнительные порты — только через `Config.AdminPorts` /
`WebuiPorts` / `WebsitePorts` или свои серверы поверх `WithRoute`.

### 0.5 `nit` — есть готовый референс Glacier-семантики в versitygw

Правило 5: *«Поведение, которое уже есть в posix-бэкенде versitygw, повторяется по его
коду»*. Для Glacier-части правильный референс другой — `backend/scoutfs/scoutfs_compat.go`:
там уже реализованы `RestoreObject`, offline/online-состояния, `x-amz-restore`
(`ongoing-request`, `expiry-date`) и подстановка storage class `GLACIER` в листинге.
Добавить в правило 5 второй адрес: posix — для обычных операций, scoutfs — для Glacier.

### 0.6 `nit` — `go 1.26` подтверждено

В `go.mod` versitygw v1.10.0 стоит `go 1.26.0`. Правило 1 верно. Уточнить в AGENTS.md,
что тулчейн подтягивается автоматически через `GOTOOLCHAIN` и ставить Go 1.26 руками не
нужно.

## 1. Блокеры

### B1. Гонка `GetObject` ↔ вытеснение landing-копии

Раздел «Потоки запросов → GetObject» закрывает только одну половину окна:

> Файл открывается до ответа, поэтому вытеснение во время чтения безопасно: Linux держит
> inode до закрытия дескриптора.

Это верно для удаления **после** `open()`. Не закрыт промежуток между чтением состояния и
`open()`:

1. GET читает строку, видит `landing = true`;
2. janitor вытесняет копию (объект уже `archived`, watermark превышен);
3. GET делает `open("landing/ab/<uuid>")` → `ENOENT`.

Клиент получает `500 InternalError` вместо корректного `InvalidObjectState`, либо —
хуже — пустое тело, если заголовок уже отправлен.

Что сделать:

- `open` → `ENOENT` означает «состояние устарело», перечитать строку и повторить решение
  (cache → `restored`, иначе `InvalidObjectState`), с ограничением на число повторов;
- janitor перед `unlink` должен помечать вытеснение в БД (`landing = false`) **до**
  удаления файла, а не после. Тогда GET, увидевший `landing = false`, за файлом не пойдёт.
  Порядок «снять флаг в транзакции → удалить файл» — обратный тому, что описан в правиле 6,
  и это надо оговорить явно: здесь файл удаляется, а не создаётся, поэтому порядок
  противоположный и безопасный.
- в `test/e2e` добавить сценарий «GET и evict одновременно».

### B2. Строки `deleted` никем не удаляются

`objects.state` имеет терминальные значения `deleted`, `failed`, но ни janitor, ни
что-либо ещё эти строки не удаляет. Таблица растёт всю жизнь системы, а по ней строятся
индексы очередей и уникальный индекс листинга. При перезаписи ключей каждый цикл создаёт
новую строку.

Нужно: политика хранения терминальных строк (`deleted` старше N дней → физический удалённый
или помеченный ряд), периодическая чистка в janitor, метрика числа таких строк. И решить,
что делает `admin verify` с рядом `deleted`, у которого остались файлы на диске.

## 2. Major

### M1. Перезапись одного ключа двумя параллельными PUT

Правило: «Перезапись ключа = новая строка `objects` с новым UUID; в той же транзакции
старая получает `is_current=false, state='deleting'`».

Два конкурентных PUT одного ключа: обе транзакции читают текущую версию, обе вставляют
свою. Частичный уникальный индекс `objects_current (bucket_id, key) WHERE is_current`
одну из них отклонит — с `unique_violation`. В текущей формулировке это уйдёт в
`500 InternalError`.

AWS semantics: оба PUT должны завершиться 200, победил последний по времени. Нужно
описать поведение: ретрай транзакции при `unique_violation` (1–2 повтора) либо
`SELECT … FOR UPDATE` на строке бакета/ключа как сериализатор. И тест на два параллельных
PUT одного ключа.

### M2. `restores` не чистится при удалении объекта

`restores.object_id` — PK и FK на `objects(id)`. Строка `objects` при удалении не
исчезает (только `is_current=false`), поэтому FK не каскадирует и запись `restores`
переживает объект. Janitor удаляет только истёкшие по `expires_at`.

Итог: сиротские `restores` в состояниях `requested`/`in_progress`/`restored` у
удалённого объекта висят вечно, recaller может пытаться их обрабатывать, метрики очередей
restore врут. Нужен переход «объект ушёл в `deleting` → удалить строку `restores`» в той
же транзакции. В таблице конечного автомата есть строка «любое → нет записи | backend |
объект ушёл в deleting» — но она про `objects`, а не про `restores`; формулировку уточнить.

### M3. Окно невосстановимой потери данных не названо

Диск — «только буфер», но между `PUT` (уже вернули 200) и `archived` данные существуют
**только** на landing-диске. Авария landing-тома в этом окне = безвозвратная потеря,
причём клиент получил 200.

Это не баг, а следствие D6, но в документе оно не сформулировано. Нужно:

- явно записать RPO = содержимое landing, то есть `migrator.batch_max_wait` (15 минут в
  примере) — это ползунк RPO, а не только производительности;
- рекомендовать зеркалирование/снапшоты landing-тома в разделе развёртывания;
- алерт «число объектов в `pending`/`archiving` старше N» — уже есть как «самый старый
  pending старше SLA», хорошо, но стоит назвать его индикатором риска потери, а не
  только лага.

### M4. Класс `STANDARD` не определён

`objects.storage_class` по умолчанию `GLACIER`, в конфиге `default_storage_class`.
Не описано, что происходит, если клиент явно шлёт `x-amz-storage-class: STANDARD`
(а rclone и aws cli иногда шлют). Возможны две семантики:

1. `STANDARD` = «навсегда на диске, на ленту не писать» — тогда это второй режим
   хранения: нужны свои переходы автомата, своя политика вытеснения, свои тесты, и
   «Не цели MVP» это не описывает;
2. `STANDARD` игнорируется либо отвергается — тогда надо решить, игнорировать (дешевле,
   но клиент думает, что у него быстрый класс) или вернуть `NotImplemented`.

Сейчас документ не выбирает ни то, ни другое. Это влияет на схему, автомат и M2, поэтому
лучше решить до M1.

### M5. Нет индексов для периодических задач janitor

Запросы janitor в текущей схеме работают full scan:

- `restores WHERE expires_at < now()` — индекса на `expires_at` нет;
- `uploads WHERE initiated < now() - mpu_ttl` — индекса на `initiated` нет.

На пустой БД не видно, на большой — janitor тормозит основную нагрузку и держит
транзакции. Добавить частичные индексы (`WHERE state IN (...)`, `WHERE initiated IS NOT
NULL`) в миграцию M1, чтобы не мигрировать потом.

### M6. `cache/tmp` обязан быть на той же ФС, что `cache`

Recaller пишет в `cache/tmp/<uuid>` и делает `rename` в `cache/<2 hex>/<uuid>`.
`rename` через точки монтирования — `EXDEV`. Для landing/mpu требование «одна XFS с
reflink» зафиксировано, для cache — нет. Зафиксировать в разделе «Диски» и проверить на
старте (`statfs` по `st_dev`), с внятной ошибкой при старте вместо падения на первом
restore.

## 3. Minor

1. **`phobos_ver` нигде не используется.** Поле объявлено, migrator его пишет, но зачем —
   не сказано. Либо описать применение (сверка при `verify`, отладка), либо убрать.
2. **Валидация `RestoreObject.Days`.** AWS принимает 1–30 и отдаёт `InvalidRequest`
   вне диапазона; `tier` вне {Expedited, Standard, Bulk} — тоже. В разделе RestoreObject
   проверки нет.
3. **`user_meta` в атрибутах Phobos.** Размер атрибутов LTFS/Phobos ограничен, а
   `x-amz-meta-*` клиент может наслать много (AWS лимит 8 KiB). Нужна проверка размера и
   поведение при превышении: не писать атрибут целиком и потерять часть, или отказать.
   Иначе `rebuild-meta` (M9) восстановит метаданные неполно.
4. **Два источника истины по inventory.** DSS Phobos в Postgres, inventory `klipper-tlc`
   в SQLite. Расхождение — основной способ потерять ленту глазами. `verify` в CLI есть,
   но нет периодической сверки и метрики «число расхождений». Добавить в раздел
   «Наблюдаемость».
5. **SQLite + несколько горутин.** `klipper-tlc` сериализует команды робота мьютексом,
   но `status`/`stat` читают inventory параллельно. Указать режим WAL и `busy_timeout`,
   иначе `SQLITE_BUSY` под нагрузкой.
6. **`storage_class` = `STANDARD` пока объект `pending`.** Отклонение от AWS (там GLACIER
   сразу). Осознанное, но требует ADR: часть клиентов решает по storage class, можно ли
   объект читать. Связано с M4 выше.
7. **`admin verify` не описан как инструмент CI.** В разделе «Тестирование» он упоминается
   как тестовый и продуктовый. Стоит зафиксировать контракт выхода (код возврата, формат
   отчёта), иначе в e2e его будут парсить по-разному.
8. **Отсутствует `docs/adr/` и `docs/spikes/`.** Документ на них ссылается как на
   существующие. Каталоги созданы в этом же PR.
9. **`region` в конфиге vs `Config.Region`.** `embedgw` подставляет `us-east-1` при
   пустом значении; валидация в `internal/config` должна сверять значение с тем, что
   реально подписывают клиенты, иначе `SignatureDoesNotMatch` с невнятной причиной.

## 5. Что в документе хорошо (не менять)

- Раздел «Тестирование»: приоритет тестов на падения над покрытием строк, таблица
  инвариантов `admin verify`, обязательный тест «убить после шага N» для каждого воркера.
  Для проекта, где главный риск — потеря или удвоение объекта, это правильная структура.
- Правило «fsync → commit, никогда наоборот» и переходы через
  `UPDATE … WHERE state = <ожидаемое>` с молчаливым пропуском при нуле затронутых строк —
  идиоматично и корректно.
- D3 (UUID вместо `bucket/key` как ID в Phobos) снимает сразу несколько классов проблем с
  кодированием ключей и перезаписью.
- D4 (манипулятор как отдельный TLC-демон вместо патча Phobos) — правильный способ
  сохранить обновляемость Phobos.
- M0 честно выносит все неизвестные в спайки до начала основной разработки.
- Ограничение `phobos.max_inflight = 1` «до подтверждения потокобезопасности» сформулировано
  как требование, а не как оптимизация. Редко и правильно.
