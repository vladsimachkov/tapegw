# Стратегия repack и уплотнения пачек

- **Статус:** предложение, принято владельцем 2026-11-05 в части «что заложить в M4»
- **Куда положить:** `docs/proposals/0011-repack-strategy.md`
- **Связано с:** ADR-0008 (носитель объекта), ADR-0013 (пулы), ADR-0014 (шифрование),
  ADR-0020 (формат записи на ленту), спайк M0-07 (`phobos tape repack`)

## Зачем документ

Сейчас repack упоминается в шести местах, и везде одинаково: «после MVP». С появлением
пачек отложить его целиком нельзя. Часть решений входит в модель данных и формат
записи M4, а формат после первой записи на ленту меняется только перезаписью.

Документ делит repack на три части:

1. **Что заложить в M4 сейчас** — модель данных и требования к формату. Обязательно.
2. **Спайк M0-10** — поведение `phobos tape repack`. До ADR-0020.
3. **Планировщик repack и уплотнения** — отдельный ADR и этап после MVP.

---

## Принципы

**Сборка мусора двухуровневая.** `phobos tape repack` работает на уровне объектов
Phobos: живой объект копируется, удалённый отбрасывается. Пачка для Phobos — один
объект; пока в ней жив хоть один участник, Phobos скопирует её целиком, вместе с
мёртвыми участниками. Поэтому:

- **уплотнение пачек — наше:** прочитать пачку, записать новую из живых участников,
  перенести ссылки в БД, удалить старую пачку в Phobos;
- **repack ленты — Phobos:** когда пачки на ленте уплотнены, `phobos tape repack`
  переносит оставшиеся живые объекты, лента переформатируется и возвращается в пул.

**Уплотнению не нужны ключи.** Участник пачки — самодостаточный зашифрованный объект
(шифротекст + манифест + футер, ADR-0019). Обёрнутый DEK, тенант и `version_seq`
переносятся в индекс новой пачки как есть. Уплотнение выполняет mover, который по
ADR-0007 развёрнутых ключей не получает. Участники удалённых тенантов отбрасываются:
строк о них в БД нет.

**Repack нужен ради места и здоровья лент, а не ради удаления.** Конфиденциальность
после удаления даёт уничтожение ключа (ADR-0014), выделенный пул удалённого тенанта
переформатируется целиком без repack.

| Причина | Как выполняется | Срочность |
| --- | --- | --- |
| Освободить место | Уплотнение пачек, затем repack ленты | По экономике пула |
| Плохое здоровье ленты (TapeAlert, ошибки чтения) | Эвакуация всей ленты | Высокая, обходит все лимиты |
| Смена поколения LTO | Repack пула на новые ленты | Плановая |
| Перевод тенанта в другой пул | Перенос объектов тенанта | По запросу оператора |
| Удаление тенанта с выделенным пулом | Переформатирование лент, repack не нужен | — |
| Конфиденциальность после удаления | Не нужен: ключ уничтожен | — |

**Repack оправдан, когда кончаются свободные ленты, а не когда на ленте много мусора.**
Полное чтение и запись ленты занимают два драйва на многие часы. Пока в пуле есть
свежие ленты, они дешевле времени драйвов.

## Часть 1. Заложить в M4 (обязательно)

### 1.1. Модель данных: учёт живого и мёртвого

Новая таблица `packs`:

| Колонка | Смысл |
| --- | --- |
| `id uuid` | = oid пачки в Phobos |
| `pool_id`, `kind` | пул; `data` или `journal` |
| `total_bytes`, `live_bytes` | размер пачки и сумма живых участников |
| `members_total`, `members_live` | число участников всего и живых |
| `medium text[]` | носитель(и) пачки (ADR-0008), массив под `repl_count = 2` |
| `state` | `open` → `sealed` → `archived` → `compacting` → `retired` |
| `created_at`, `archived_at`, `retired_at` | |

Объект ссылается на место хранения:

- `objects.pack_id` + `objects.pack_offset` + `objects.pack_length` — для участника пачки;
- `objects.phobos_medium` (уже есть по ADR-0008) — для крупного объекта.

Правила:

- удаление версии (переход в `deleting`, физическое удаление маркера, удаление по
  `versionId`) **в той же транзакции** уменьшает `live_bytes` и `members_live` её пачки;
- ссылка объекта на пачку и смещение **изменяемая**: уплотнение переносит её в новую
  пачку одной транзакцией вместе со сменой состояния старой пачки;
- инвариант, проверяемый тестом и `tapegw admin verify`: `live_bytes` пачки равен
  сумме `pack_length` её живых участников.

### 1.2. Носитель обновляется после repack

После `phobos tape repack` данные лежат на другой ленте. Колонки `objects.phobos_medium`
и `packs.medium` должны обновляться, иначе группировка restore по лентам начнёт ошибаться.
Источник — `phobos extent list -f json` (ADR-0008), один вызов на пакет oid. До
обновления устаревший носитель — не ошибка корректности, а только неоптимальный порядок
restore. Это нужно записать, чтобы не принимать его за порчу.

### 1.3. Требования к формату (в ADR-0020)

- **Дубли при восстановлении.** Авария посреди уплотнения оставляет на лентах и старую,
  и новую пачку с одними и теми же участниками. `rebuild-meta` схлопывает участников по
  UUID версии и не создаёт две строки. Содержимое участников побайтно одинаково, выбрать
  можно любую копию; в отчёт пишется число схлопнутых дублей.
- **Индекс пачки** содержит всё, что нужно перенести участника в новую пачку без
  ключей: UUID версии, тенант, `version_seq`, обёрнутый DEK, версия KEK, смещение,
  длина. Ничего, что требует расшифровки.
- **Пачки журнала уплотняются по тем же правилам**, но снимки состояния (ADR-0020) делают
  старые сегменты ненужными целиком. Сегменты старше последнего снимка тенанта считаются
  мёртвыми.

### 1.4. Тесты M4

- удаление участника уменьшает `live_bytes` и `members_live` пачки в той же транзакции,
  мутация «не уменьшать» ловится;
- инвариант `live_bytes` = сумма живых участников держится после перезаписи, удаления
  версии, удаления маркера и удаления тенанта;
- `rebuild-meta` с двумя пачками, содержащими одних и тех же участников: одна строка на
  версию, число дублей в отчёте.

## Часть 2. Спайк M0-10: `phobos tape repack` (до ADR-0020)

На стенде mhVTL, с двумя пулами (теги) и картриджами по 4 ГБ.

1. **Соблюдает ли repack теги пулов.** Данные ленты пула A при repack не должны оказаться
   на ленте пула B. После находки M0-08 (теги защищают только в одну сторону) это не
   очевидно. Если repack тег не соблюдает, нужен способ указать целевой тег, иначе repack
   общего пула ломает изоляцию выделенных пулов.
2. **Как обновляются DSS и `phobos extent list`** после repack: откуда брать новый
   носитель и как быстро он виден.
3. **Жизненный цикл ленты после repack:** можно ли её переформатировать и вернуть в пул
   штатно, нужен ли ручной шаг.
4. **Поведение с объектами, удалёнными в Phobos (deprecated).** Отбрасываются ли они при
   repack или копируются.
5. **Время repack** ленты 4 ГБ при заполнении 50 % и 90 % живыми данными — чтобы оценить
   масштаб для реальных лент.

Результат — `docs/spikes/M0-10-phobos-repack.md`. Если пункт 1 не проходит, это блокер
для выделенных пулов, и ADR-0013 надо пересматривать до M4.

## Часть 3. Планировщик (отдельный ADR, после MVP)

Набросок, чтобы не потерять. Детали — в своём ADR.

**Уплотнение пачки** запускается, если `live_bytes / total_bytes` ниже порога
(стартово 50 %) и пачка не содержит участников, которые нельзя переносить. Участники под
Object Lock переносятся, а не теряются: уплотнение — это копирование, а не удаление.

**Repack ленты** запускается по правилу:

- свободной ёмкости пула по прогнозу осталось меньше чем на `repack.free_weeks` недель
  приёма;
- кандидаты — ленты с наибольшей долей мёртвых данных, жадно;
- перед repack ленты уплотняются её пачки с долей живых ниже порога;
- приоритет ниже restore и архивации, только в окна простоя драйвов, не больше одного
  repack на пул одновременно (`repack.max_concurrent`);
- **эвакуация по здоровью ленты** обходит все эти правила.

**Смена поколения LTO** — тот же механизм, только цель — пул на лентах нового поколения.

**Метрики:** доля мёртвых данных по пулу и по ленте, прогноз дней до исчерпания ёмкости
пула, очередь уплотнения, время последнего repack.

## Брошенные байты прерванных записей (замер 2026-11-06)

Прерванная запись на `dir` не оставляет строк экстента в DSS (проверено
прямым запросом), но на носителе остаётся частичный файл — и `delete` его не
убирает. Носитель при этом **неизвестен**: Phobos выбирает его сам и сообщает
только через экстент, которого у такой записи нет.

Отсюда разделение учёта:

- **записи mover о прерванных операциях** дают оценку «брошенные байты по
  пулу» — метрику для решения «пора ли repack». Точного места они назвать не
  могут, и не должны этого обещать;
- **точное место** выясняется сверкой содержимого носителя с DSS: файлы,
  которых нет среди экстентов, — брошенные. Делать это надо во время repack
  или проверки целостности, когда лента уже смонтирована; отдельный проход по
  носителям только ради учёта не нужен — на ленте это лишнее монтирование;
- **ожидается**, что брошенные файлы исчезают при repack: переносятся только
  живые экстенты, а исходная лента затем форматируется. Это вывод по
  построению, а не наблюдение — repack ещё ни разу не запускался. **Проверить
  в спайке M0-10.**

Вопрос на будущее (не решение): Phobos хранит у экстента `md5` и `xxh128`
(видно в `-o` у `phobos extent list`). Возможно, часть проверки целостности
лент (Б2) умеет делать сам Phobos, сверяя прочитанное со своей суммой. Это
стоит проверить отдельным спайком, прежде чем строить свою сверку с нуля.
