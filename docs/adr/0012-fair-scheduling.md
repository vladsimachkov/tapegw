# ADR-0012. Справедливое планирование очередей между тенантами

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** **T3** (migrator — с M4, recaller — с M5)
- **Связано:** [ADR-0011](0011-quotas.md), [ADR-0013](0013-tape-pools.md),
  [ADR-0016](0016-thousands-of-tenants.md)

## Контекст

Очереди сейчас FIFO: `SELECT ... FOR UPDATE SKIP LOCKED` по `state, next_try_at`. При
одном клиенте это правильно. При десятках — один тенант с многотерабайтным бэклогом
занимает драйвы и очередь так, что остальные ждут часы. Хуже того, у архивации есть
срок: чужой бэклог отъедает у тенанта окно `online_until`, и его данные уходят на ленту
позже, чем обещано.

## Решение

**Recaller:** round-robin между тенантами с непустой очередью; внутри тенанта — по tier
и времени запроса. Плюс `restore_inflight` на тенанта, чтобы один клиент не занял все
процессы-воркеры. Expedited — опция тарифа тенанта, по умолчанию выключена.

**Migrator:** архивация не критична к задержке, но батч набирается с ограничением «не
больше K объектов или B байт одного тенанта», остаток — следующим батчам. Иначе
многотерабайтный бэклог одного клиента превращается в N батчей подряд.

**Пулы** ([ADR-0013](0013-tape-pools.md)) дают батчу естественное разделение: батч всегда
в пределах одного пула, поэтому планирование по пулам и по тенантам не конфликтуют.

## Последствия

- Выборка батча перестаёт быть простым `ORDER BY next_try_at`. Нужен `DISTINCT ON
  (tenant_id)` — см. индекс `objects_tenant_queue (tenant_id, next_try_at) WHERE
  state = 'pending'`, заложенный в миграции T0 именно под этот запрос.
- **Перебирать всех тенантов нельзя**: их тысячи и большинство с пустой очередью
  ([ADR-0016](0016-thousands-of-tenants.md)). Round-robin строится только по тем, у кого
  очередь непустая, — это и делает `DISTINCT ON` по частичному индексу.
- Появляется метрика «время ожидания самого старого запроса restore по тенанту»: без неё
  нечестность планирования видна только когда клиент пожалуется.
- Тест обязательный: «тенант A забивает landing и очередь restore» — тенант B продолжает
  писать и получать restore без деградации сверх заданной доли.

## Отклонённые альтернативы

- **Оставить FIFO.** Не требует кода, но превращает одного клиента в источник отказа для
  всех — а это ровно то, от чего мы уходим введением тенантов.
- **Веса тарифов вместо round-robin.** Правильно в долгосрочной перспективе, но пока нет
  тарифов; round-robin — нижняя граница, веса поверх него добавляются без переделки
  выборки.
- **Отдельная очередь на тенанта (свой список таблиц/шардов).** Реально изолирует, но
  усложняет SKIP LOCKED и наблюдение ради проблемы, у которой есть решение дешевле.
