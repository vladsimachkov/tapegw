# tapegw — правила для агента

Источник истины — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Этот файл — краткая
выжимка плюс команды. При любом расхождении выигрывает `ARCHITECTURE.md`, а отступление
оформляется ADR в `docs/adr/`.

## Команды

```bash
go build ./...                 # сборка всего (без cgo, Phobos не нужен)
go test ./...                  # юнит-тесты (без cgo, без Postgres для чистых пакетов)
go test -race ./...            # проверка гонок, обязательно для изменений очередей
go vet ./...
staticcheck ./...              # требует go install honnef.co/go/tools/cmd/staticcheck@latest
gofmt -l .                     # должен печатать пусто

# Сборка с реальным Phobos (только стенд ci-dir / контейнер EL9)
go build -tags phobos ./...

# Миграции применяются при старте tapegw, отдельно запускать не нужно
```

Тесты, которым нужен Postgres, пропускаются сами, если `TAPEGW_TEST_DSN` не задан.
Чтобы они всё-таки прогнаться:

```bash
docker run -d --name tapegw-pg -p 55432:5432 \
  -e POSTGRES_USER=tapegw -e POSTGRES_PASSWORD=tapegw -e POSTGRES_DB=phobos \
  postgres:16-alpine

TAPEGW_TEST_DSN='postgres://tapegw:tapegw@localhost:55432/phobos?search_path=tapegw_test' \
  go test -race -count=1 ./...
```

E2E-тесты (`test/e2e`) пропускаются без `TAPEGW_E2E_ENDPOINT`. Полный прогон:

```bash
# 1. поднять tapegw (см. readme.md «Быстрый старт»)
# 2
go build -o /tmp/tapegw ./cmd/tapegw && /tmp/tapegw -config /tmp/tapegw.yaml &
# 3
TAPEGW_E2E_ENDPOINT=http://127.0.0.1:7070 \
TAPEGW_E2E_ACCESS=testaccess TAPEGW_E2E_SECRET=testsecret \
  go test -count=1 ./test/e2e -v
```

Проверки доступа требуют **обычного** ключа: root и admin в versitygw идут мимо
политик и ACL, поэтому e2e на root ничего про них не говорит. Для них в стенде
нужен файловый IAM — `s3.iam_dir` с `users.json`, и **две** учётки одного
клиентского тенанта: одна создаёт бакет и выдаёт права, вторая читает только
если политика разрешила (ADR-0018).

```bash
mkdir -p /tmp/iam
cat > /tmp/iam/users.json <<'JSON'
{"accessAccounts":{
  "userplus":{"access":"userplus","secret":"usersecret","role":"userplus","userID":1001,"groupID":1001,"projectID":2},
  "userplain":{"access":"userplain","secret":"userplainsecret","role":"user","userID":1002,"groupID":1002,"projectID":2}
}}
JSON
# в конфиг tapegw: s3.iam_dir: /tmp/iam

# projectID — тенант учётки. Нужен клиентский тенант (2), а не 0 и не 1:
# нуль страж (ADR-0017) читает как «тенанта нет» и отказывает до политики,
# а в системном тенанте 1 не-admin учётку отсекает ADR-0018. В обоих случаях
# тест «политика разрешает» проверял бы отказ стража вместо политики.
# Миграция заводит только системный тенант, поэтому стенд добавляет свой сам:
psql "$TAPEGW_TEST_DSN" -c "INSERT INTO tenants (id, name, status, pool_id) \
  VALUES (2, 'e2e-client', 'active', 1) ON CONFLICT (id) DO NOTHING"

# Роль владельца — userplus: бакеты без identity-политик может создавать только
# она (auth/access-control.go:597), а роль user — нет.
TAPEGW_E2E_USER_ACCESS=userplain TAPEGW_E2E_USER_SECRET=userplainsecret \
TAPEGW_E2E_OWNER_ACCESS=userplus TAPEGW_E2E_OWNER_SECRET=usersecret \
  go test -count=1 ./test/e2e -run Policy -v
```

Без этих переменных тесты доступа **пропускаются**, а не падают — поэтому в CI они
заданы обязательно, иначе проверки тихо перестанут запускаться.

Оба набора с DSN и endpoint гоняет CI (`.github/workflows/ci.yml`) — локально
прогонять их не обязательно, но перед PR по очередям и транзакциям стоит.

## Железные правила

Нумерация совпадает один в один с разделом «Репозиторий и правила для агента» в
`docs/ARCHITECTURE.md` — на эти номера можно ссылаться в отчётах и в описаниях PR.

1. **Go — версия закреплённой версии versitygw** (сейчас `go 1.26.0`). versitygw
   фиксируется точной версией в `go.mod`, обновление — отдельный PR.
2. **`go build ./... && go test ./...` проходят на любом Linux** без Phobos и без
   cgo. Всё, что требует Phobos, — под build tag `phobos` и в стенд `ci-dir`.
3. **Исходники Phobos и versitygw не патчатся.** Ни патчей, ни форков, ни `replace`
   в `go.mod` на свою ветку. Если без патча нельзя — сначала ADR и вопрос ревьюеру.
4. **Неподдерживаемые S3-операции — `NotImplemented`** через встраивание
   `backend.BackendUnsupported`, а не «молча делаем что-то».

   Уточнение по ловушке из PR #6: `NotImplemented` — про **операцию**, которую
   бэкенд не умеет. «Операция умеема, но у бакета ничего не включено» — это
   другой ответ, и отдавать надо его. Ловушка в том, что versitygw сам обращается
   к таким операциям по пути обычных запросов: `auth.loadObjectLockState` дергает
   `GetObjectLockConfiguration` перед записью любого объекта и терпит только
   `ObjectLockConfigurationNotFound`. Оставь его в `BackendUnsupported` — и
   полностью реализованный `PutObject` отвечает 501.

   Так же с `GetBucketVersioning`: posix возвращает пустую конфигурацию (200),
   потому что GUI-клиенты опрашивают её при просмотре бакета. Прежде чем оставить
   операцию в `BackendUnsupported`, проверьте, не дёргает ли её versitygw сам.

   И обратная сторона той же ловушки, строже: **заглушка, возвращающая `NotFound`,
   опаснее отсутствия метода, если от этого ответа зависит проверка безопасности.**
   Пример — Object Lock: `loadObjectLockState` при
   `ObjectLockConfigurationNotFound` считает бакет разблокированным и пропускает
   все проверки, а `GetObjectRetention` с `NoSuchObjectLockConfiguration` отключает
   сверку retention. Заглушка «отвечаю NotFound на всё» не ломает запрос — она молча
   отключает неизменяемость: всё проходит, ошибок нет, блокировка не работает. Такие
   методы пишутся сразу вместе с проверкой и покрываются тестом на каждый код
   контракта (см. [ADR-0015](docs/adr/0015-versioning-and-object-lock.md)).
5. **Поведение S3 берём из кода versitygw, не выдумываем.** Для обычных операций —
   posix-бэкенд, для Glacier-семантики (`x-amz-restore`, storage class,
   RestoreObject) — `backend/scoutfs/scoutfs_compat.go`.
6. **Сначала файл на диске с `fsync`, потом commit транзакции Postgres. Никогда
   наоборот.** Любая смена состояния объекта — одна транзакция. Исключение с
   обратным порядком: вытеснение файла (снять флаг в БД → `unlink`), см. ADR про
   гонку GET и eviction.
7. **Каждый воркер идемпотентен.** Переход состояния —
   `UPDATE … WHERE state = <ожидаемое>`; ноль затронутых строк означает «опередили»,
   воркер молча пропускает. Для каждого нового шага воркера обязателен тест
   «упасть после шага N» на `store/fake`.
8. **Ошибки** через `fmt.Errorf("…: %w", err)`, **логи** через `log/slog` (JSON),
   `panic` только в `main`.
9. **Числа — в конфиг, не константами в коде**: таймауты, размеры батчей, watermark,
   `max_attempts`. Любое поле переопределяется переменной `TAPEGW_*` (имя
   выводится из пути в YAML: `migrator.batch_max_wait` → `TAPEGW_MIGRATOR_BATCH_MAX_WAIT`).
10. **Один PR — один пункт плана** из раздела «План разработки» в `ARCHITECTURE.md`.
    В описании PR: что сделано, как проверено, отступления от документа со ссылкой
    на ADR.
11. **Миграции БД — только вперёд**, одна миграция на PR, уже слитые не правим.
    Up и Down проверяются **текстом файла**, а не пересказом, и прогоняются
    Down → Up **на таблице с данными, а не на пустой схеме**: на пустой порядок
    шагов (`nullable` → бэкфилл → `SET NOT NULL`) не важен, и миграция, которая
    падает на живой базе, здесь зелёная.
    **Проверяются выполнением текста из файла, а не его пересказом.** Up и Down
    извлекаются из `.sql` программно и исполняются как есть: переписанный от руки
    SQL проверяет вашу память, а не файл. Так Down 0006 прошёл вручную набранным
    `NULLIF(policy, '')` и упал настоящим `NULLIF(b.policy, '')` из файла.
    **Миграцию проверяют по каталогу БД, а не по таблице версий goose.** Goose
    умеет записать миграцию применённой (`is_applied = t`), не выполнив ни одного
    шага: так вышло с обходом отключением транзакции, когда миграция добавляла
    значение enum и тут же употребляла его в CHECK (55P04). Проверка дешёвая и
    обязательная: после Up смотреть `pg_enum` / `information_schema.columns`, а
    не ноль в код возврата. Второе: goose считает аннотацией **любую** строку
    комментария, в которой встретится префикс его директивы, — поэтому название
    директивы в тексте миграций не пишут. Третье: новое значение enum и его
    CHECK/частичный индекс разводятся по разным миграциям (образец — 0010 и 0011).
    Четвёртое: goose считает версию по **номеру** файла, поэтому переименование
    уже применённой миграции (номер тот, содержимое другое) означает «уже
    применена» — на стенде с живой схемой это молчаливый пропуск.

12. **Лицензия — Apache-2.0.** Файлы, перенесённые из Phobos (в т.ч. `.proto`),
    сохраняют LGPL-заголовок.

13. **Ни одна транзакция Postgres не открыта во время вызова Phobos.** Воркер
    коммитит переход состояния, отпускает транзакцию и advisory-лок ключа, и
    только потом вызывает `phobos_put`/`phobos_get`; результат пишется отдельной
    транзакцией. Батч на 200 GiB идёт минуты, и висящая в это время транзакция
    держит и строки, и локи ключей — параллельный PUT тех же ключей упрётся в
    `db.advisory_lock_timeout`. Таймаут лока — вторая линия защиты, а не замена
    правила.

Правила, которые в `ARCHITECTURE.md` не пронумерованы, но обязательны (список
растёт вместе с ошибками, поэтому счётчик в заголовке не ведётся):

- **Всё про настройку ленточной библиотеки — в [`docs/ops/tape-library.md`](docs/ops/tape-library.md).**
  Обязательство, а не рекомендация: работали со стендом (mhVTL, `phobos_tlc`,
  `phobosd`, заведение лент и драйвов, теги, копии, форматирование) — допишите
  найденное туда же в этом же PR. Тонкости настройки не видны из кода и не
  воспроизводятся тестом: `Format failed … No such device` одинаково означает
  «том без размера», «носитель под admin lock» и «драйв держит остаточный LTFS».
  Формат записи — симптом → причина → что делать; каждая запись либо
  воспроизведена, либо помечена как непроверенная. Отчёт спайка при этом живёт в
  `docs/spikes/`, а в этот документ попадает то, что пригодится тому, кто
  настраивает библиотеку руками.
- **cgo изолирован** в `internal/store/phobos`. Вызовы Phobos — только в пуле
  `phobos.max_inflight`, `runtime.KeepAlive` для `os.File`, C-строки в `defer`,
  структуры через `pho_xfer_desc_clean`.
- **Прежде чем ослаблять инвариант (CHECK, ограничение, обязательство формата)
  или заводить второй источник правды, проверь, не даёт ли нужного уже принятое
  обязательство.** Ослабление инварианта — только через ADR. Костыль «снимем
  ограничение и добавим колонку/состояние/флаг» почти всегда значит, что не
  посмотрели, что уже следует из принятого. В этом репозитории так было минимум
  трижды: смещения участников даёт детерминированность сборки (ADR-0020), а не
  ослабленный `objects_pack_member`; проверку копии при локальной передаче даёт
  ожидаемая сумма, записанная при первой записи (С7), а не посчитанная при
  чтении — та замкнута сама на себя; «лента в слоте» и «лента вывезена» — два
  независимых поля (0013), а не один смешанный enum, где «эвакуируется и сейчас
  в драйве» не выразить.

- **Перед проверкой ветки — сверка списка договорённостей с тем, что реально в
  коде. До мутаций.** Мутации проверяют то, что заявлено в отчёте, а отчёт может
  молчать о несделанном: на PR#2a исполнитель честно проверил ротацию KEK, root и
  кэш, но два договорённых пункта (отзыв как `UPDATE`, неизменяемый тенант) в
  ветке отсутствовали, и ни один зелёный тест об этом не сказал.
- **Если свойство про нескольких параллельных участников, тест запускает
  нескольких параллельных участников, а не одного с другим именем.** Один
  «чужой» участник с другим id проверяет только то, что id различаются, — а
  гонка живёт между участниками, которые различаются чем-то ещё или, наоборот,
  совпадают в том поле, на которое завязано различение. Пример из репозитория:
  тест «чужой процесс не заберёт пачку» проходил, потому что сравнивались разные
  хосты, а ошибка была между слотами одного хоста — воркерами одного процесса.
  Свойство «параллельные не мешают друг другу» требует двух живых участников
  одновременно: одного, который держит ресурс, и второго, который к нему лезет.

- **При настройке окружения — `make hooks`.** Хук `.githooks/pre-push` гоняет
  `make check` и не пускает красное в удалённую ветку. Коммит с красной проверкой
  сам по себе безвреден — это рабочая запись; дорого другое: красное в удалённой
  ветке, где его увидит ревьюер, и красный прогон CI, которого можно было не
  тратить. `make commit` вместо хука не сделали намеренно: он обходится обычным
  `git commit`, а проверка, которую можно обойти по невнимательности, не проверка.
  Обход `--no-verify` допустим только с объяснением в описании PR.

- **Описание PR содержит только проверенное.** Не писать прогнозов результата
  («CI скорее всего зелёный», «должно работать»). Если что-то не проверено или не
  разобрано, так и писать: «локально не проходит по неразобранной причине,
  решение — по CI». Зелёный тест, который ничего не проверил, и прогноз в
  описании одинаково не являются проверкой: первый создаёт ложную уверенность в
  коде, вторая — ложную уверенность в том, что код уже проверен.

- **Мутации проверяются `make mutate` (`hack/mutate.sh`), а не самодельным
  скриптом.** Механизм один, и в него встроены четыре способа соврать «зелёным», на
  которые наступали в этом репозитории: мутация не применилась (опечатка в
  выражении — в отчёте «поймана», хотя ничего не меняли); мутация ломает сборку
  (`go test` падает с `[build failed]`, и это зачитывалось как «поймана», хотя
  проверка логики не запускалась вовсе — теперь отдельный код возврата 6);
  базовый прогон ничего
  не выполнил (без `TAPEGW_TEST_DSN` тесты на Postgres пропускаются, а не
  падают); мутация файла миграции не дошла до теста (goose держит применённую
  версию — нужен `DROP_SCHEMA`). Если механизму чего-то не хватает,
  **дорабатывайте его, а не пишите второй**: в двух скриптах проверка всегда
  остаётся в том, о котором вспомнили. Откат — копированием сохранённого файла,
  а не `git checkout`: правок до коммита в git нет, и `git checkout <файл>`
  стирает всю работу в этом файле.
- **Покрытие `testdb.Clean` проверяется тестом, а не памятью.** `CleanTables`
  сверяется с `pg_tables` в `TestCleanCoversEveryTable`: новая таблица миграцией
  без записи в `testdb.CleanTables` (или в `testdb.SeedTables`, если её
  наполняют миграции) уронит тест сразу. Молчание здесь стоило того, что тест
  начал проходить или падать в зависимости от предыдущего прогона (`accounts_pkey`).
- **Проверка безопасности обязана быть закрытой при сомнении.** Если она не
  смогла выполниться (ошибка, таймаут, неизвестное состояние), разрушительное
  действие запрещено. Тест на каждую такую проверку включает случай «проверка
  упала». Размыкающаяся при сбое проверка — не проверка: `delete` в mover'е
  удалял объект, когда `Stat` не ответил, потому что проверка «целый ли?» стояла
  в ветке `else`. Третья разновидность того же греха — после «зелёного, который
  ничего не проверил» и «теста не по той оси».

- **Проверяя гипотезу, сначала убери уже известные неисправности.** Иначе
  отрицательный результат ничего не говорит: гипотеза могла быть верной, но её
  закрыл другой дефект. Чистое окружение — лучший контроль.
  Пример: `raid1` по умолчанию требует два устройства, и гипотеза про
  `repl_count` была верна с самого начала, но проверка на ВМ пришлась на момент,
  когда устройство стояло в `failed`, — показала «не то» и увела ещё на заход.
  На чистом контейнере тот же `-P repl_count=1` прошёл с первого прогона
  (`docs/ops/tape-library.md`).

- **Перед PR и перед мержем — проверять содержимое **удалённой** ветки, а не код
  возврата `git push`.** `git push origin <ветка>`, когда HEAD стоит на другой
  ветке, печатает `Everything up-to-date` и завершается нулём: коммит остаётся
  локальным и висит на чужой ветке, а вы читаете успешный пуш как факт. На PR#46
  так потерялась правка формата на ленте: коммит был сделан на ветке предложения,
  а запушена ветка ADR, и ревьюер обнаружил это по `git log --all -S "<строка>"`.
  Проверка дешёвая: `git log --oneline -1 origin/<ветка>` и `git show
  origin/<ветка>:<файл> | grep "<ожидаемая строка>"` — одна строка вместо
  «я это уже делал».
- **Сам себе PR не мержится.** Порядок: исправил → прислал → подождал повторного
  `approve` ревьюера → мержишь. Прошлый `approve` не распространяется на
  пришедшие после него коммиты, даже если «тут мелочь». Для PR, которые меняют
  **формат данных или ключи**, это обязательно: на PR#38 блокер про переиспользование
  nonce нашёлся именно при повторном просмотре, а мерж произошёл до него — по
  инерции прошлого `approve`. Формат на ленте обратно не поменять, и второй взгляд
  тут важнее, чем где-либо ещё.

## Чего нет в MVP

Lifecycle, S3 Select, несколько узлов, освобождение места на лентах после удалений.
Всё это — отдельные ADR.

**Упаковка мелких объектов там больше не числится** — она вошла в M4 (порог
`pack.threshold`, формат пачки в ADR формата записи). Причина простая: формат
пачки нельзя добавить задним числом, он меняется только перезаписью уже
заархивированного.

**Версионирование бакетов и Object Lock там больше не числятся** — решением владельца
от 2026-11-03 они обязательны в первый год (клиенты — бэкап-софт, неизменяемые бэкапы
в AWS работают только поверх версий). Это этап V, он идёт вместе с M2 и T1: листинг,
удаление и перезапись пишутся сразу с версиями и delete markers. Шифрование с ключом на
тенанта — этап T2, до M4. См. `docs/proposals/0010-owner-decisions.md`.
