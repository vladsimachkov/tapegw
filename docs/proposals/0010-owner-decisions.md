# Решения владельца: шифрование, версионирование и Object Lock, масштаб

- **Статус:** решения приняты владельцем 2026-11-03; ADR оформить по этому документу
- **Куда положить:** `docs/proposals/0010-owner-decisions.md`
- **Дополняет:** [0009-multitenancy-and-gaps.md](0009-multitenancy-and-gaps.md) —
  закрывает его четыре вопроса и добавляет два направления, которых в том
  предложении не было: версионирование и совместимость с бэкап-софтом.

## Ответы владельца

| Вопрос | Решение |
| --- | --- |
| Шифрование с уничтожением ключа | **Да**, вариант C: программное шифрование, ключ на тенанта |
| Регуляторные требования к криптографии | **Нет.** AES-256-GCM допустим |
| Число независимых клиентов | **Тысячи и больше** |
| Нужно в первый год | **Object Lock**; клиенты — бэкап-софт (Veeam и подобные), нужна совместимость с AWS |
| Вторая копия вне площадки | В первый год **не нужна**; механизм `repl_count` в пулах остаётся |
| Выделенные пулы с первого дня | **Нет**, все тенанты в общих пулах; выделенный пул — исключение по запросу |

## Главное следствие, которое меняет больше всего

**Object Lock для бэкап-софта требует версионирования бакетов.** В AWS блокировка
работает только при включённом версионировании, и бэкап-софт проверяет это при
настройке неизменяемых бэкапов. Упрощённый режим versitygw (блокировка без версий)
нам не подходит.

**Версионирование переходит из «не целей MVP» в обязательные.** Это самое дорогое из
всех принятых решений: оно меняет смысл перезаписи ключа, удаления и листинга — то
есть ровно тех трёх операций M2, которые ещё не написаны.

## ADR-0014. Шифрование данных, ключ на тенанта

**Решение.** tapegw шифрует тело объекта при записи в landing. На ленту, в landing и
в кэш попадает только шифротекст.

**Иерархия ключей.**

- **KEK** — мастер-ключ системы, хранится вне БД (файл с правами 0400 или Vault).
- **Ключ тенанта (TEK)** — 256 бит, хранится в `tenants.wrapped_key`, зашифрован KEK.
- **Ключ объекта (DEK)** — 256 бит, **свой для каждой версии объекта**, хранится в
  `objects.wrapped_dek`, зашифрован TEK.
- Смена KEK перешифровывает только TEK (тысячи строк, секунды).

**Формат данных.** Сегменты по 64 KiB открытого текста, каждый — AES-256-GCM с тегом
16 байт. Nonce строится детерминированно из UUID версии, номера части multipart
(0 для обычного PUT) и номера сегмента; повтор nonce при одном DEK исключён, потому
что DEK свой у каждой версии.

- Range-чтение: вычислить диапазон сегментов, прочитать, расшифровать, обрезать.
- Каждый сегмент проверяется тегом: порча на ленте даёт ошибку, а не мусор.
- ETag и `x-amz-checksum-*` считаются по открытым данным.
- HEAD и GET отдают `x-amz-server-side-encryption: AES256` (как SSE-S3).
- SSE-C и SSE-KMS по-прежнему `NotImplemented`.

**Multipart.** Части шифруются при записи каждой части (номер части входит в nonce),
итоговый файл собирается reflink без перешифрования. Размеры частей хранятся
**навсегда** в `object_parts(version_id, part_number, plain_size, cipher_offset)`:
без них Range-чтение не найдёт нужный сегмент.

**CopyObject** внутри тенанта — расшифровка и шифрование новым DEK. Reflink для
копии не применяется.

**Восстановление после катастрофы.** Обёрнутый DEK и номер версии KEK пишутся также
в атрибуты объекта Phobos. Тогда из лент, DSS и KEK восстанавливается всё даже при
полной потере схемы tapegw (`rebuild-meta`). Обёрнутые TEK входят в экспорт
`rebuild-meta` и в бэкап Postgres.

**Удаление тенанта** — уничтожение TEK после удаления всех объектов. Исключение —
Object Lock: пока у тенанта есть версии с неистёкшим `retain_until` или
`legal_hold`, TEK **не уничтожается**, а удаление тенанта отклоняется (ADR-0015).

**Процедура KEK** (часть деплоя, без неё запуск в прод запрещён):

- минимум две копии вне сервера, у разных людей или в разных местах;
- проверка восстановления KEK из копий раз в квартал на стенде;
- KEK версионируется: старая версия хранится, пока на неё ссылается хоть один TEK.

**Тесты, обязательные для закрытия:**

- Range-чтение на границах сегментов и частей multipart (таблица случаев);
- порча одного байта шифротекста → ошибка чтения, не мусор;
- уничтожение TEK → GET, restore и `rebuild-meta` дают ошибку;
- смена KEK → все объекты читаются.

## ADR-0015. Версионирование и Object Lock, совместимые с AWS

**Решение.** Бакеты поддерживают версионирование (`Enabled`, `Suspended`) и Object
Lock (`GOVERNANCE`, `COMPLIANCE`, legal hold, retention по умолчанию на бакет).
Поведение повторяет AWS и posix-бэкенд versitygw с включённым версионированием на
уровне шлюза.

**Модель данных.** Текущая схема почти готова: каждая запись — уже новая строка с UUID.

- `versionId` = UUID строки `objects`.
- Новые колонки `objects`: `is_delete_marker`, `retention_mode`, `retain_until`,
  `legal_hold`, `wrapped_dek`.
- Новые колонки `buckets`: `versioning` (`unversioned`/`enabled`/`suspended`),
  `object_lock_enabled`, `default_retention`.
- `Suspended` и версия `null`: при записи в приостановленный бакет предыдущая
  null-версия заменяется, остальные версии сохраняются.
- Перезапись ключа в бакете с `enabled`: старая версия **остаётся**
  (`is_current=false`, состояние не меняется), а не уходит в `deleting`.
- `DeleteObject` без `versionId` в бакете с версиями создаёт delete marker.

**Новые операции:** `ListObjectVersions`, GET/HEAD/DELETE по `versionId`,
`PutBucketVersioning`, `Get/PutObjectLockConfiguration`, `Get/PutObjectRetention`,
`Get/PutObjectLegalHold`. `CopyObject` с `x-amz-copy-source` на конкретную версию.

### Что уже делает versitygw, и где из-за этого тихая дыра

Проверено по исходникам v1.10.0 — это сужает нашу часть работы, но добавляет
ловушку строже любой из найденных в PR #6.

**Правила изменения retention проверяет versitygw, не мы.** В
`auth.IsObjectLockRetentionPutAllowed` (`auth/object_lock.go:246`) уже реализовано:
продление срока в любую сторону доступно всем; **COMPLIANCE нельзя ни укоротить, ни
понизить до GOVERNANCE — никому и даже с заголовком bypass**; для GOVERNANCE
ослабление требует `x-amz-bypass-governance-retention` и права на обход. В бэкенд
`PutObjectRetention` приходит уже проверенный XML, параметра bypass там нет. Дублировать
эти правила в `meta` не нужно.

**Но вся эта проверка берёт данные из нашего бэкенда.** `loadObjectLockState`
(`auth/object_lock.go:481`) читает `GetObjectLockConfiguration`, а `checkObject`
(`:524`) — `GetObjectRetention`. Контракт кодов возврата такой:

| Что вернём | Как это поймёт versitygw |
| --- | --- |
| `GetObjectLockConfiguration` → `ObjectLockConfigurationNotFound` | бакет считается разблокированным, **все проверки пропускаются** |
| `GetObjectRetention` → `NoSuchKey` / `NoSuchVersion` | «защищать нечего», пропуск |
| `GetObjectRetention` → `MethodNotAllowed` | «это delete marker», пропуск |
| `GetObjectRetention` → `NoSuchObjectLockConfiguration` | retention не проверяется, legal hold — да |
| любая другая ошибка | запрос отклоняется (fail closed, правильно) |

Отсюда обязательное требование к этапу V: **заглушка, которая отвечает
`NoSuchObjectLockConfiguration` на всё, молча отключает неизменяемость** — запросы
проходят, ошибок нет, Object Lock «не работает» без единого признака. Поэтому
`GetObjectRetention`/`GetObjectLegalHold`/`GetObjectLockConfiguration` пишутся
одновременно с проверкой и покрываются тестом на каждый код из таблицы, а не
оставляются заглушкой «на потом».

Ещё одно следствие из `checkObject`: при включённом версионировании удаление **без**
`versionId` блокировку не проверяет — оно создаёт delete marker. Значит пока
delete markers не реализованы, Object Lock выглядит сломанным: версия остаётся
живой под маркером, а клиент считает её удалённой. Реализация маркеров и блокировки
обязана быть в одном этапе, не в двух.

### Где проверяем мы

Одна функция, тест-перебор всех путей:

- `DeleteObject` и `DeleteObjects` **с** `versionId`;
- `deleter`: версия под блокировкой не удаляется, даже если попала в `deleting`;
- удаление тенанта и уничтожение TEK (ADR-0014);
- admin-API `tapegw`. Оператор в COMPLIANCE удалить версию не может; прямое
  `phobos delete` — вне контроля tapegw, фиксируется в эксплуатационной
  документации как запрещённая операция.

**Архивные версии и блокировка.** Продление срока (`PutObjectRetention`) — операция
только над метаданными, лента не нужна. Бэкап-софт регулярно продлевает
неизменяемость, и это не должно вызывать restore.

**Квоты:** некурентные версии и delete markers учитываются в `storage_bytes` и
`objects` тенанта.

**Готово когда:** проходят тесты versitygw для версионирования и Object Lock в
применимой части, и проходит спайк совместимости с бэкап-софтом (ниже).

## Спайк M0-09. Совместимость с бэкап-софтом — как можно раньше

Это главный риск проекта, и проверять его надо до T2 и M4.

Бэкап-софт на объектном хранилище читает часть объектов **не только при
восстановлении**: служебные метаданные, проверки состояния, контрольные точки. У нас
после вытеснения из landing GET даёт `InvalidObjectState`. Если софт рассчитан на то,
что любой объект читается сразу, он сломается, и никакая Glacier-совместимость этого
не исправит.

**Что сделать:**

1. По документации Veeam (и других целевых продуктов) выписать требования к
   S3-совместимому хранилищу с неизменяемостью: набор операций, версионирование,
   Object Lock, Content-MD5, SOSAPI и т. п. Отдельно — поддерживает ли продукт
   хранилище с семантикой Glacier (restore перед чтением) как **основной** репозиторий
   или только как архивный уровень.
2. Прогнать реальный продукт против tapegw на этапе без ленты (M2 + версии), с
   журналом всех S3-запросов: какие операции, какие объекты читаются, как часто,
   какого размера.
3. Отдельно — сценарий «через сутки после бэкапа»: что софт читает, когда объекты уже
   вытеснены бы были.

> **Уточнение владельца от того же числа (после отчёта агента).** Veeam и конкретный
> бэкап-софт **не целевые**: разбора их документации не требуется, отдельного продукта,
> под который подгоняется семантика, нет. **Эталон совместимости — поведение AWS S3**
> (Glacier, версионирование, Object Lock) и тесты versitygw. Поэтому спайк M0-09 в
> нынешнем виде снимается и переформулируется в **набор тестов совместимости с AWS**
> внутри этапа V: применимые группы тестов versitygw на версии и Object Lock; e2e на
> aws-sdk-go-v2 для полного Glacier-цикла; Object Lock в COMPLIANCE с продлением срока
> на архивном объекте без restore. Список исключений с причинами — `test/e2e/EXCLUDED.md`.
>
> ADR-0003 при этом **не меняется**: класс «всегда онлайн» сейчас не вводится, а
> возможность такого клиента остаётся в ADR-0003 разделом «Открытый вопрос». Схему под
> это заранее не закладываем.

**Возможные исходы и что они меняют:**

- Софт читает только при восстановлении — архитектура как есть.
- Софт регулярно читает мелкие служебные объекты — нужен класс **«всегда онлайн»**:
  объекты меньше порога или по префиксу/правилу бакета не вытесняются из landing (на
  ленту всё равно пишутся). Решается настройкой бакета и условием в janitor;
  учитывается в квоте `landing_bytes` тенанта отдельно. Отдельное ADR: это меняет
  ADR-0003, где GLACIER отдаётся всегда.
- Софт требует мгновенного чтения всего — tapegw подходит только как **архивный
  уровень** этого продукта, и это меняет позиционирование, а не код.

## ADR-0016. Решения под тысячи тенантов

- **Пулы:** все тенанты в общих пулах; выделенный пул — исключение по запросу.
- **Метрики:** только агрегаты без метки тенанта. Учёт по клиенту — в
  `tenant_usage_daily`, выгрузка через админ-API.
- **Регистрация клиентов** — через админ-API (создание тенанта, ключей, квот одной
  операцией), CLI — обёртка над ним. Ручных шагов оператора при подключении нет.
- **IAM:** кэш аккаунтов в памяти с TTL и сбросом при изменении через
  `LISTEN/NOTIFY` Postgres.
- **Планировщики:** round-robin только по тенантам с непустой очередью
  (`DISTINCT ON (tenant_id)` в выборке батча), а не перебор всех тенантов.
- **Квоты:** строка `tenant_usage` на тенанта, без глобальных горячих строк.
- **Удаление тенантов** — штатный поток, а не редкая операция: уничтожение TEK делает
  его дешёвым; repack общих лент — фоновая задача по порогу доли мёртвых данных на
  ленте.

## Что проверено по исходникам до внесения в план

| Утверждение | Итог |
| --- | --- |
| Методы версионирования и Object Lock есть в `backend.Backend` | есть: `PutBucketVersioning`, `GetBucketVersioning`, `ListObjectVersions`, `Put/GetObjectLockConfiguration`, `Put/GetObjectRetention`, `Put/GetObjectLegalHold` (`backend/backend.go:44–102`) |
| Бэкенд узнаёт, что бакет создан с Object Lock | да: `be.CreateBucket` получает `*s3.CreateBucketInput` с `ObjectLockEnabledForBucket` (`controllers/bucket-put.go:701`) |
| Правила COMPLIANCE/GOVERNANCE при смене retention | проверяет `auth.IsObjectLockRetentionPutAllowed`, в бэкенд bypass не передаётся |
| Откуда `auth` берёт состояние блокировки | из наших `GetObjectLockConfiguration` / `GetObjectRetention`; см. таблицу кодов выше — заглушка отключает проверки молча |
| Удаление без `versionId` при включённых версиях | блокировку не проверяет, создаётся delete marker (`auth/object_lock.go:536`) |

## Изменения плана разработки

**T0 расширяется** (до продолжения M2):

- [ ] ADR-0014, 0015, 0016 по этому документу.
- [ ] Спайк M0-09 (бэкап-софт), шаг 1 — сразу; шаги 2–3 — как только будет
  версионирование.
- [ ] Миграция T0 сразу включает колонки версионирования, блокировки и шифрования
  (`is_delete_marker`, `retention_mode`, `retain_until`, `legal_hold`, `wrapped_dek`,
  `tenants.wrapped_key`, `buckets.versioning`, `buckets.object_lock_enabled`,
  `object_parts`). Таблицы пустые — `NOT NULL` и ограничения сразу.

**Новый этап V** (версионирование и Object Lock) — вместе с T1, до закрытия M2:
листинг пишется сразу как `ListObjects` + `ListObjectVersions`, удаление — сразу с
delete markers и проверкой блокировки. Иначе тот же код пришлось бы переписывать
второй раз.

**Что уже написанное в M2 нужно править под V.** PutObject из PR #6 при перезаписи
ключа переводит прежнюю версию в `deleting` безусловно. Для бакета без версий это
верно, для бакета с `enabled` — уничтожение истории и обход Object Lock. Переход
`deleting` обязан стать условным от `buckets.versioning`, и это пункт этапа V, а не
«мелочь потом».

**T2 вырастает:** шифрование — 3 PR (формат и спул; multipart и `object_parts`;
ключи, KEK, атрибуты Phobos и `rebuild-meta`). M4 стартует только после T2.

**M6 и T4:** `deleter` и удаление тенанта проверяют блокировку через общую функцию
ADR-0015; уничтожение TEK — последний шаг удаления тенанта.

**Новый порядок:** M0 → M1 → T0 (+M0-09 шаг 1) → M2 + T1 + V (+M0-09 шаги 2–3) →
M3 → T2 → M4 + T3 → M5 + T3 → M6 + T4 → M9 + T4; параллельно M7 → M8.
