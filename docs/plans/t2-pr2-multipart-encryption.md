# T2 PR#2 — multipart с шифрованием частей и `object_parts`

- **Этап:** T2 (второй из трёх PR) + закрывает M3 по части multipart
- **Ветка:** `t2-pr2-multipart-encryption`
- **Связано:** [ADR-0014](../adr/0014-encryption-per-tenant.md),
  [ADR-0005](../adr/0005-key-rewrite-advisory-lock.md),
  [план T2 PR#1](t2-pr1-encryption-format.md)

## Почему вместе с M3

Multipart раньше не был реализован вовсе (методы приходили из
`BackendUnsupported`). Делать его в два захода — сначала без шифрования, потом
переписывать — значит дважды решать вопрос «как части складываются в один файл».
Формат на ленте после первой записи не меняется, поэтому multipart пишется сразу
с шифрованием частей.

## Как устроены части

**Один DEK на загрузку.** DEK заводится при `CreateMultipartUpload` и хранится в
`uploads.wrapped_dek`, обёрнутый с AAD = `upload_id`. При `Complete` он
переоборачивается с AAD = UUID версии и переезжает в `objects.wrapped_dek`.
Переоборачивание, а не новый ключ: данные частей уже зашифрованы этим DEK, а
привязка обёртки к версии нужна, чтобы обёртку нельзя было переставить между
объектами.

**Номер части входит в nonce и в AAD** (ADR-0014), поэтому часть №3 одной версии
криптографически не равна части №3 другой и не равна куску открытого текста той же
длины в другой части.

**Размер части входит в AAD** — то же правило, что для объекта целиком: усечение
части по границе сегмента не должно проходить проверку. Размер части лежит в
`upload_parts.size` при жизни загрузки и в `object_parts.plain_size` навсегда.

**Части не перешифровываются при `Complete`.** Итоговый файл — конкатенация
файлов частей (как в posix: `io.Copy` с copy_file_range, posix.go:2975-2990).
Шифротексты частей просто склеиваются: каждый был зашифрован тем же DEK и со своим
номером части.

После склейки `object_parts` хранит для каждой части `plain_size` и
`cipher_offset` — смещение её шифротекста в итоговом файле. Без них Range по
зашифрованному multipart не вычислит, в какой части и на каком сегменте лежат
запрошенные байты. Хранить придётся навсегда.

## Чтение: Reader по таблице частей

`encrypt.Reader` переписывается на таблицу частей:

```go
type Part struct {
    Number       uint32 // входит в nonce и AAD
    PlainSize    int64  // входит в AAD
    CipherOffset int64  // смещение шифротекста части в файле
}
```

`ReadAt` для открытого смещения находит часть (накопленные `PlainSize`), затем
сегмент внутри части, и шифротекст читает по `CipherOffset + seg*CipherSegmentSize`
с AAD `(version, part.Number, part.PlainSize)`.

Односегментный объект — это таблица из одной части `{0, size, 0}`, поэтому второго
пути чтения нет: то, что работает для multipart, работает и для обычного PUT.
`NewReader` остаётся обёрткой над этим случаем.

## Миграция 0014

- `uploads.wrapped_dek bytea NOT NULL` — DEK загрузки;
- `upload_parts.file_id uuid NOT NULL` — файл части в спуле;
- `upload_parts.size` — размер открытого текста части (он уже есть, уточняется
  комментарием);
- `object_parts.cipher_offset` → `NOT NULL`: T2 его заполняет, NULL означал бы
  «не знаю, где читать», а это не состояние, а ошибка.

## Методы

| Метод | Что делает |
| --- | --- |
| `CreateMultipartUpload` | страж, проверка бакета и Object Lock, DEK, строка `uploads`. Возвращает UploadId |
| `UploadPart` | страж, шифрование в отдельный файл (`part = part_number`), `upload_parts` |
| `UploadPartCopy` | страж на источник и на загрузку: расшифровать диапазон исходной версии, зашифровать новым DEK загрузки |
| `CompleteMultipartUpload` | проверка списка частей (порядок, наличие, ETag, минимальный размер кроме последней), склейка файлов, `objects` + `object_parts` в одной транзакции, удаление загрузки |
| `AbortMultipartUpload` | удалить строку и файлы частей |
| `ListParts` | по загрузке, с маркером |
| `ListMultipartUploads` | по бакету, с маркером |

Порядок `Complete` и правило 6: файлы склеены и `fsync`-нуты **до** транзакции,
вставляющей объект. Упавшая между склейкой и коммитом операция оставит файл без
строки — безвредного сироту, его подберёт janitor. Обратный порядок дал бы строку
без файла.

## Не входит

janitor для `mpu_ttl` (M5), `UploadPartCopy` между тенантами (запрещён стражем),
`ListMultipartUploads` с ключевыми маркерами дальше простого case.

## Что выяснилось при реализации

**UUID версии заводится на Create, а не на Complete.** nonce и AAD каждого
сегмента строятся от UUID версии, а части грузятся до того, как версия
появится. Первая версия брала для частей UUID файла части — собранный объект
читался под UUID строки и падал на GCM. Поэтому у загрузки есть
`uploads.object_id`, который становится `objects.id`. Побочный плюс: имя файла
объекта известно заранее, и перешифрование при Complete не нужно по построению.

**Курсор `RETURNING` держит соединение.** Вставка частей и колбэк `InTx` внутри
транзакции `PutObject` падали с `conn busy`, пока курсор `INSERT … RETURNING`
оставался открытым. Закрыт сразу после `scanObjectRow`; `defer` при повторном
`Close` не мешает, он идемпотентен.

**Чужая загрузка — AccessDenied, а не NoSuchUpload.** `uploadId` ничего не
говорит о бакете, поэтому ориентир — бакет из запроса: свой бакет → загрузки
действительно нет, чужой → AccessDenied. Иначе по коду «загрузки нет» клиент
узнавал бы о существовании чужого `uploadId`. Разборка — `uploadErr`, по образцу
`bucketErr`/`objectErr`.

**Complete в этом SDK не несёт заголовков Object Lock и Tagging.** Они приходят
на CreateMultipartUpload, поэтому `lockAtComplete` знает только про правило
баkета: ветка «явное важнее правила» отсутствует сознательно, а не забыта.

**У `UploadPartCopyInput` нет `CopySourceVersionId`** (оно есть только у
`CopyObjectInput`), так что копировать конкретную версию источника нечем —
копируется текущая.

**Минимальный размер части нельзя проверить на трёх частях.** Маленькая часть №3
стоит последней, а попытка поставить её первой падает на порядке, а не на
размере. Для кейса EntityTooSmall нужна четвёртая часть.

**Тест привязки размера к AAD обязан уменьшать ровно на сегмент.** На единицу
отказывает конструктор читателя («части дают N, объявлено M»), на неполный
сегмент — сам GCM (тег считается по всему сегменту). В обоих случаях тест
проходит, но проверяет не AAD. Ровно целый сегмент — единственный случай, когда
без привязки размера читатель вернул бы усечённый объект молча.

## e2e

`test/e2e/multipart_test.go` — то же самое через контроллер versitygw: разбор
XML списка частей, номера частей, составной ETag и коды ошибок считает он, а не
мы. Три сценария: цикл с Range через границу части, список загрузок и частей с
Abort, маленькая не-последняя часть (отказ и объекта нет).

Тест заглушек переведён с multipart на CopyObject — по тому же правилу, что и
юнит-версия: проверяемый метод обязан оставаться заглушкой.
