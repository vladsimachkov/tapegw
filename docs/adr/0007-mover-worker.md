# ADR-0007. Вызовы Phobos вынесены в отдельный бинарь tapegw-mover

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** M4 (migrator), M5 (recaller)
- **Связано:** [ADR-0006](0006-libphobos-linkage.md),
  [`docs/spikes/M0-02-libphobos-api.md`](../spikes/M0-02-libphobos-api.md),
  правила 2 и 13 в `AGENTS.md`

## Контекст

ADR-0006 зафиксировал: линкуемся с `libphobos_store` динамически, вызовы слоя
данных сериализуем одним мьютексом. Спайк
[M0-02](../spikes/M0-02-libphobos-api.md) показал, что этого мало:

- **один `phobos_put` пишет на один носитель**, сколько бы объектов в батче ни
  было;
- два процесса с собственными `phobos_init` берут разные носители.

Значит одна горутина (и даже один процесс с несколькими горутинками,
сериализованными мьютексом) ограничивает пропускную способность **одним
драйвом**. Реальный параллелизм по драйвам дают только отдельные процессы.

Если делать это внутри `tapegw`, основной бинарь приобретает cgo, а вместе с ним:
зависимость от заголовков и библиотек Phobos на сборку и на тесты S3-слоя,
риск утащить падение внутри libphobos в процесс, который держит HTTP-соединения
клиентов.

## Решение

**Отдельный бинарь `tapegw-mover`, который `tapegw` запускает дочерними
процессами.**

- Один процесс mover = один `phobos_init` = одна операция за раз.
- `tapegw` общается с mover по unix-сокету или через stdin/stdout простыми
  командами: «put батч UUID», «get батч UUID».
- Mover сам открывает файлы по путям, которые вычисляются из UUID. **Передавать
  fd между процессами не нужно.**
- Основной `tapegw` — **без cgo вообще**.

### Что это даёт

- **Правило 2 соблюдается само**: `go build ./... && go test ./...` проходят на
  любой Linux без Phobos и без cgo. Тесты S3-слоя не требуют ни сборки Phobos,
  ни стенда.
- **Падение или зависание внутри libphobos убивает только mover.** Супервизор
  перезапускает его, а батч уходит на перепроверку. Основной процесс с
  клиентскими соединениями не затронут.
- **Мьютекс сериализации из ADR-0006 больше не нужен**: в процессе mover один
  поток вызовов. ADR-0006 остаётся в силе в части «линкуемся динамически», но
  пункт про мьютекс отменяется этим ADR.
- Правило 13 («транзакция Postgres не открыта во время вызова Phobos»)
  становится естественным: mover вообще не подключается к Postgres, у него в
  протоколе только UUID и пути.

**Mover не получает развёрнутых ключей и TEK.** Обёрнутый DEK — **да**, он часть
атрибута объекта и для moverа это просто данные; без TEK он бесполезен. Развёрнутые
DEK, TEK и KEK — **никогда**: mover переносит шифротекст, в протоколе только UUID,
пути и обёртки. Это не «пока не понадобилось», а ограничение архитектуры: mover —
единственный компонент с cgo и libphobos, и попади туда материал ключа, ключи
оказались бы в процессе, который крутится рядом с драйверами и переживает падение
основного процесса. Отдельная причина — лента: mover пишет атрибуты объекта, и у
него в руках легко оказывается то, что потом ляжет в индекс LTFS и переживёт
крипто-уничтожение тенанта (см. правило ADR-0014 про то, что попадает на ленту).
Если понадобится «проверить, что читается» — проверку делает основной процесс,
mover передаёт только байты.

### Два пула вместо одного числа

```
phobos.movers.migrator:  N
phobos.movers.recaller:  M
```

- **`N + M` не больше числа драйвов.** Иначе лишние процессы будут стоять в
  очереди LRS и только держат картриджи в приводах.
- **`M >= 1` всегда.** Restore не должен ждать архивацию: иначе ночная
  архивация большой партии задержит выдачу восстановленных объектов клиентам.
- Раздельные пулы были в архитектуре и раньше — теперь они раздельны и на уровне
  процессов, а не только очередей в одном процессе.

### Случай одного драйва

Два правила выше вместе требуют минимум два драйва, а стенд и небольшая
установка могут быть с одним. Исключение формулируется явно:

**при одном драйве допустимо `N = 1, M = 1`.** Процессы встанут в очередь LRS на
один привод, и restore подождёт не дольше одного батча migrator.

Из этого следует важная граница, которую иначе обязательно нарушат:
**`migrator.batch_max_bytes` — это верхняя граница задержки restore на
однопользовательском стенде и на любом стенде с одним драйвом.** Батч размером с
целую ленту означает, что запрос на восстановление будет ждать всю запись ленты.
Поэтому `batch_max_bytes` ограничивается не только памятью mover'а, но и
допустимым временем ожидания restore — и в конфиге это надо подписать, а не
оставлять «настройкой производительности».

### Конфиг

Добавляется `phobos.library` (наряду с `phobos.family` и `phobos.layout`).
Причина не стилистическая: спайк M0-02 показал, что `xd_params.put.profile`
библиотека **не читает** — профиль разбирает CLI у себя. Через API без явных
`family` / `library` / `layout` вызов падает с `-ENODEV`, и из текста ошибки это
не понять.

## Последствия

- Появляется второй бинарь и протокол между процессами. Протокол должен быть
  минимальным и версионируемым: версия mover'а проверяется при старте
  супервизора.
- Супервизор — новая ответственность: запуск, health-check, перезапуск после
  падения/зависания, таймаут на операцию. Таймаут обязан учитывать, что сматка
  ленты и `umount` LTFS занимают минуты (см.
  [M0-05](../spikes/M0-05-eject-before-unload.md)), и быть заметно больше
  `db.lock_timeout`.
- Прерванная запись оставляет на носителе осиротевший файл (замер в
  [M0-02](../spikes/M0-02-libphobos-api.md)), поэтому перезапуск mover'а сам по
  себе не приводит носитель в порядок — чистка на janitor'е.
- Перепроверка после сбоя обязана смотреть **статус копии**, а не только
  наличие: `getmd` возвращает объект и при `copy_status = incomplete`.
- `phobos.max_inflight` как единая настройка исчезает; её заменяют
  `phobos.movers.migrator` и `phobos.movers.recaller`.

## Отклонённые альтернативы

**Несколько горутин в одном процессе с мьютексом.** Не решает главную задачу:
один контекст Phobos пишет на один носитель, поэтому горутинки всё равно
выстроятся в очередь на один драйв.

**Несколько копий tapegw за балансировщиком.** Реализовало бы параллелизм, но
каждый экземпляр тащил бы HTTP-слой, Postgres-пул и cgo, а «упал mover»
превратилось бы в «упал весь узел».

## Поправка (после спайка M0-03): владение вызовами — горутина-владелец, а не мьютекс

Формулировка «вызовы слоя данных сериализуем одним мьютексом» недостаточна.
Мьютекс гарантирует **последовательность**, но не гарантирует, что все вызовы
идут из одного потока ОС: горутина между вызовами вправе переехать на другой
поток. Спайк M0-03 показал, что libphobos непотокобезопасна, но не проверял,
держит ли она состояние, привязанное к потоку (thread-local). Если держит —
последовательные вызовы из разных потоков сломают её так же, как параллельные,
а ошибка будет плавающей и воспроизведётся в самом неудобном месте.

Вместо мьютекса — **одна горутина-владелец** всех вызовов libphobos в процессе,
включая `phobos_init` и `phobos_fini`:

- в начале этой горутины — `runtime.LockOSThread()`, и она этот захват никогда
  не снимает;
- остальной код отправляет ей запросы по каналу и ждёт ответ;
- «один вызов за раз» и «всегда один и тот же поток ОС» следуют из построения, а
  не из дисциплины вызывающего.

Проверка на стенде: несколько горутин одновременно засыпают store запросами, а
обёртка на стороне C пишет `gettid()` каждого вызова. Ожидаем ровно один tid на
всё время прогона и ни одного пересечения по времени. Тест под тегом `phobos`,
потому что без настоящей библиотеки он ничего не утверждает.

Смысл ADR при этом не меняется: параллелизм по драйвам дают отдельные процессы, а
не горутины. Меняется способ, которым внутри процесса обеспечивается одиночность
вызовов.

## Поправка (2026-11-07): соответствие ролей mover'а и клиентов

Реализовано в S1 (PR #116): mover принимает только клиентов той роли, которая
соответствует его пулу — `migrator` принимает `scheduler`, `recaller` принимает
`restorer`. Соответствие задаётся при сборке mTLS-контекста сервера
(`phobos.mover.role` → список разрешённых SAN-URI), роль клиента берётся из
подтверждённого сертификата, а не из hello.

Следствие, которое иначе всплывёт на первом же однодрайвном стенде: **драйв,
отданный пулу записи, не обслуживает restore** — подключение restorer'а к
migrator- mover'у отвергается на рукопожатии. Для случая одного драйва
(раздел «Два пула вместо одного числа»: `N = 1, M = 1`) это значит **два
процесса mover на одном драйве**: один с `role: migrator`, другой с
`role: recaller`, с разными адресами `listen` и одним именем драйва в SAN-URI
сертификатов.

Один mover с обеими ролями не сделан намеренно: смысл раздельных пулов в том,
что restore не ждёт архивацию, а один процесс сериализовал бы обе очереди на
одном `phobos_init` (спайк M0-02) — разделение стало бы номинальным.
