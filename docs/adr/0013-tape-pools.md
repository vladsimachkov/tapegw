# ADR-0013. Пулы лент через теги Phobos; тег обязателен на каждой записи

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** **T2** (до M4)
- **Связано:** [ADR-0008](0008-object-medium.md),
  [спайк M0-08](../spikes/M0-08-phobos-tags.md),
  [ADR-0014](0014-encryption-per-tenant.md)

## Контекст

Нужно физически разделять данные клиентов: чтобы выделенный набор лент можно было
отдать клиенту целиком или изъять, чтобы ёмкость и алерты «заканчиваются ленты» считались
по клиенту, а не по библиотеке в целом.

Средство в Phobos есть — теги: `struct phobos_xfer_desc::put.tags` (`struct
string_array`, «Tags to select a media to write»), CLI `-T`. Но из заголовка было
непонятно, жёсткий это фильтр или предпочтение, и спайк
[M0-08](../spikes/M0-08-phobos-tags.md) это проверял на Phobos 3.4.1.

**Результат — хороший и плохой одновременно.**

Хорошо: тег — **жёсткий фильтр со семантикой И**. Запись с тегом, которого нет ни на
одной ленте, падает с ENOSPC и не оставляет ни объекта в каталоге, ни осиротевших
extents. Запись с двумя тегами, которые не собираются на одной ленте, тоже падает.
Даже под `no_split` объект объёмом 1,287 GiB не перелился на ленту чужого пула, где
места было достаточно, — Phobos честно вернул ENOSPC.

Плохо: **изоляция односторонняя**. Когда обе ленты помечены тегами разных пулов, запись
**без** тега успешно легла на помеченную ленту. Тег ограничивает выбор при запрошенном
теге и никак не защищает помеченную ленту от чужой записи.

## Решение

**Пул — набор лент Phobos с общим тегом.**

```
pools(id, name, phobos_tag, repl_count, kind)   -- kind: shared | dedicated
tenants.pool_id                                 -- по умолчанию общий пул
objects.pool_id                                 -- фиксируется на PUT, дальше не меняется
```

Migrator группирует батчи по пулу и передаёт в `phobos_put` тег пула и `repl_count`
пула.

### Обязательное следствие из спайка: тег на каждой записи

Чтобы «выделенный пул» не был фикцией:

1. **Каждая запись несёт тег пула.** Общий пул — не «без тега», а со своим тегом
   (`pool:shared`). Пул фиксируется объекту на PUT, значит тег всегда известен, и
   ситуации «некуда поставить тег» в коде не бывает.
2. **Каждая лента вводится в Phobos с тегом ровно одного пула.** `pools.phobos_tag` —
   `NOT NULL UNIQUE CHECK (<> '')`.
3. **Migrator на старте проверяет:** ни одной ленты без тега пула и ни одной с тегом
   неизвестного пула. Иначе требование 1 теряется при первой же доработке, и объект
   клиента из общего пула оказывается на ленте чужого выделенного пула.

### Побочное следствие: ENOSPC двусмысленен

«Нет ленты с таким тегом» и «лента кончилась» для Phobos выглядят одинаково — `ENOSPC`,
rc=28. Отличить по коду нельзя. Это ломает страховку из M4 («при ENOSPC делим батч
пополам вплоть до одного объекта»): при неверном теге она будет крутить цикл и в конце
выдаст «нужны новые ленты», хотя лент полно — просто не тех.

Поэтому перед делением батча уточняется, есть ли свободное место у лент **этого пула**
(`phobos tape list -T <tag> -o name,stats.phys_spc_free`). Нет — это «пул исчерпан»,
алерт по пулу. Есть, но батч не влезает — тогда делить.

## Последствия

- Выделенный пул можно отдать клиенту целиком: LTFS читается без tapegw, а атрибуты
  объекта (bucket, key, etag) лежат рядом с данными.
- Ёмкость, свободное место и алерты — по пулам.
- **Теги нельзя прочитать у ленты**: в списке выводимых полей `phobos tape list` нет
  `tags`, только фильтр `-T`. Аудит «какие теги развешаны» = перебор кандидатов.
  Учитывать в админ-API и CLI.
- Смена пула объекта = repack, то есть есть только на словах: менять пул у существующих
  объектов мы не планируем.

## Отклонённые альтернативы

- **Пулы без тегов — отдельная библиотека на пул.** Изоляция железная, но библиотека
  одна, и заводить отдельную ради каждого клиента нереально.
- **Считать пул «своим» по метаданным Phobos, не тегами.** Теги — единственный штатный
  способ влиять на выбор носителя при записи; остальное пришлось бы вычитать из DSS.
- **Полагаться на то, что tapegw всегда пишет с тегом.** Именно так и есть, но без
  стартовой проверки лент это держится на аккуратности оператора, а не на системе.
