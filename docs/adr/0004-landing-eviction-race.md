# ADR-0004. Гонка GET и вытеснения landing-копии

- **Статус:** принято 2026-11-02
- **Дата:** 2026-11-02
- **Этап плана:** M2 (чтение из landing), M4 (janitor)
- **Связано:** `docs/ARCHITECTURE.md`, «Потоки запросов → GetObject», «Janitor»;
  [`docs/reviews/2026-11-02-architecture-review.md`](../reviews/2026-11-02-architecture-review.md) §B1

## Контекст

В архитектуре закрыта только половина окна:

> Файл открывается до ответа, поэтому вытеснение во время чтения безопасно:
> Linux держит inode до закрытия дескриптора.

Это верно для удаления **после** `open()`. Промежуток между чтением состояния и
`open()` не закрыт:

1. GET читает строку `objects`, видит `landing = true`;
2. janitor вытесняет копию (объект уже `archived`, watermark превышен);
3. GET делает `open("landing/ab/<uuid>")` → `ENOENT`.

Клиент получает `500 InternalError` вместо корректного `InvalidObjectState`.

## Решение

Две меры, обе обязательны.

**1. janitor помечает вытеснение до удаления файла.**

```
BEGIN; UPDATE objects SET landing = false WHERE id = $1 AND state = 'archived'; COMMIT;
unlink(landing/<2 hex>/<uuid>)
```

Порядок **обратный правилу 6** («сначала файл, потом commit»), и это не
противоречие, а его зеркало: правило 6 защищает от ситуации «БД знает об
объекте, а файла нет». При удалении опасна обратная — «файла нет, а БД знает,
что он есть». Снятый флаг заставляет любой новый GET пройти мимо файла, а
`unlink` уже не может застать читателя врасплох.

`unlink` вне транзакции может не состояться (падение между commit и unlink).
Тогда файл останется сиротой без строки `landing=true` — его подберёт orphan GC
из M6. Это безопасный исход: лишний файл, а не потеря.

**2. GET на `ENOENT` перечитывает состояние и повторяет решение.**

`ENOENT` при открытии файла спула — не ошибка клиента, а признак устаревшего
снимка состояния. Обработка:

```
открыли ENOENT → перечитать строку → пересчитать решение (cache / InvalidObjectState)
```

с ограничением на число повторов (настраиваемое, по умолчанию 2). После
исчерпания — `InvalidObjectState`, а не `InternalError`: что бы ни произошло,
«нет онлайн-копии» честнее, чем «внутренняя ошибка».

## Последствия

- В `ARCHITECTURE.md` нужно добавить оговорку к правилу 6 про обратный порядок
  при вытеснении — иначе следующий читатель «исправит» код обратно.
- В `test/e2e` — сценарий «GET и evict одновременно» на малом watermark.
- Метрика `tapegw_get_enoent_retries_total`: нетипично большое число значит, что
  watermark выставлен слишком агрессивно.
- То же ограничение касается `SlowDown` из ADR-0002: он не должен блокировать
  `DeleteObject`, иначе при переполнении диска мы запретим то единственное,
  что диск освобождает.

## Отклонённые альтернативы

- **Блокировать вытеснение на время чтения** (счётчик открытых файлов в БД).
  Требует записи в Postgres на каждый GET и убивает смысл кэша метаданных.
- **Не вытеснять вовсе, пока объект читается.** Нужен таймаут «читается», то есть
  ещё одно состояние и ещё одна гонка.
- **Повторять `open` в цикле без перечитывания состояния.** Не решает: файл уже
  удалён, а состояние `landing=false` нужно прочитать, чтобы ответить правильно.
