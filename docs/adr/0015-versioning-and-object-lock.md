# ADR-0015. Версионирование и Object Lock, совместимые с AWS

- **Статус:** принято 2026-11-03 (решение владельца)
- **Дата:** 2026-11-03
- **Этап плана:** **V** (вместе с M2 и T1, до закрытия M2)
- **Связано:** [ADR-0014](0014-encryption-per-tenant.md),
  [предложение 0010](../proposals/0010-owner-decisions.md)

## Контекст

Эталон совместимости — поведение AWS S3 и тесты versitygw; отдельного продукта, под
который подгоняется семантика, нет. Но в первый год обязателен Object Lock, а в AWS
блокировка работает **только при включённом версионировании**. Упрощённый режим
versitygw (блокировка без версий) не подходит.

Версионирование уходит из «не целей MVP» в обязательные. Это меняет смысл ровно тех трёх
операций M2, которые ещё не написаны: перезаписи, удаления и листинга.

## Решение

**Модель данных.** Текущая схема почти готова: каждая запись — уже новая строка с UUID.

- `versionId` = UUID строки `objects`.
- `objects`: `is_delete_marker`, `retention_mode`, `retain_until`, `legal_hold`,
  `wrapped_dek`, `is_null_version`.
- `buckets`: `versioning` (`unversioned`/`enabled`/`suspended`), `object_lock_enabled`,
  `default_retention`.
- **`is_null_version`** — пометка null-версии. В AWS у объекта, записанного до
  включения версий или в приостановленном бакете, `versionId` равен строке `"null"`, и
  запись в приостановленный бакет заменяет именно её, не трогая остальные версии. У нас
  `versionId` — всегда UUID строки, поэтому без отдельного признака отличить null-версию
  нечем и правило «заменить предыдущую null-версию» не выражается. Частичный уникальный
  индекс `objects_null_version (bucket_id, key) WHERE is_null_version` запрещает больше
  одной null-версии на ключ — то есть правило живёт в схеме, а не в коде.
- **Заполнение `is_null_version` — первый PR этапа V, вместе с условным `deleting`.**
  Раньше нельзя: прежняя версия при перезаписи сейчас остаётся живой в состоянии
  `deleting`, а с `is_null_version = true` на обеих строках уникальный индекс отверг бы
  вторую. То есть правильная запись null-версии и условный `deleting` — одна правка, а
  не две.

### Переходы версионирования: назад в unversioned нельзя

Как в AWS, из `enabled` можно уйти только в `suspended`; обратного перехода в
`unversioned` нет. Для нас это не косметика, а условие корректности логики PutObject:
она предполагает, что в бакете `unversioned` текущая версия всегда null-версия. Если
бы бакет мог вернуться в `unversioned`, в нём остались бы обычные версии, и ветка
«unversioned» начала бы удалять то, что удалять не должна.

Поэтому `PutBucketVersioning` обязан отвергать переход `enabled|suspended →
unversioned` (в AWS это `InvalidBucketState`). Разрешены только
`unversioned → enabled`, `enabled → suspended`, `suspended → enabled`.

### Почему suspended — это два запроса, а не один

В приостановленном бакете текущей может быть **обычная** версия, записанная, пока
версии были включены. По AWS заменяется только null-версия, поэтому:

```sql
-- 1. текущая обычная версия просто перестаёт быть текущей
UPDATE objects SET is_current = false
 WHERE bucket_id = $1 AND key = $2 AND is_current AND NOT is_null_version;

-- 2. null-версия (текущая или нет) заменяется
UPDATE objects SET is_current = false, state = 'deleting', is_null_version = false
 WHERE bucket_id = $1 AND key = $2 AND is_null_version;
```

Один запрос `WHERE is_current` даёт две поломки, и обе проверены тестами и мутацией:

- **тихая потеря данных**: `enabled: PUT k` → `suspended: PUT k` — версия `v1`,
  сохранённая ради истории, уходит в `deleting` без единой ошибки;
- **ошибка вместо записи**: `unversioned: PUT k` → `enabled: PUT k` → `suspended: PUT k`
  — прежняя null-версия остаётся нетекущей с флагом, и новый `INSERT` с
  `is_null_version = true` упирается в `objects_null_version`. Транзакция откатывается,
  данные целы, но клиент получает ошибку.

Для `unversioned` те же два запроса дают тот же результат, что и один: там текущая
строка и есть null-версия, поэтому первый запрос не находит строк.
- `Suspended` и версия `null`: при записи в приостановленный бакет предыдущая null-версия
  **заменяется**, остальные версии сохраняются.
- Перезапись ключа в бакете с `enabled`: старая версия **остаётся** (`is_current=false`,
  состояние не меняется), а не уходит в `deleting`.
- `DeleteObject` без `versionId` в бакете с версиями создаёт delete marker.

Ограничение `buckets_lock_needs_versioning` (`CHECK (NOT object_lock_enabled OR
versioning = 'enabled')`) зашито в миграции T0: в AWS lock нельзя включить без версий,
и выключить версии при включённом lock нельзя.

**Новые операции:** `ListObjectVersions`, GET/HEAD/DELETE по `versionId`,
`PutBucketVersioning`, `Get/PutObjectLockConfiguration`, `Get/PutObjectRetention`,
`Get/PutObjectLegalHold`. `CopyObject` с `x-amz-copy-source` на конкретную версию.

### Что уже делает versitygw — и где из-за этого тихая дыра

Правила изменения retention проверяет **versitygw, а не мы**. В
`auth.IsObjectLockRetentionPutAllowed` (`auth/object_lock.go:246`) уже реализовано:
продление срока доступно всем; COMPLIANCE нельзя ни укоротить, ни понизить до
GOVERNANCE — никому, даже с заголовком bypass и даже root; для GOVERNANCE ослабление
требует `x-amz-bypass-governance-retention` и право на обход. В бэкенд `PutObjectRetention`
приходит уже проверенный XML, параметра bypass там нет. **Дублировать эти правила в
`meta` не нужно.**

Но вся проверка берёт состояние блокировки **из наших геттеров**, и контракт кодов
(`auth/object_lock.go:481–560`) такой:

| Что вернём | Как это поймёт versitygw |
| --- | --- |
| `GetObjectLockConfiguration` → `ObjectLockConfigurationNotFound` | бакет считается разблокированным, **все проверки пропускаются** |
| `GetObjectRetention` → `NoSuchKey` / `NoSuchVersion` | «защищать нечего», пропуск |
| `GetObjectRetention` → `MethodNotAllowed` | «это delete marker», пропуск |
| `GetObjectRetention` → `NoSuchObjectLockConfiguration` | retention не проверяется, legal hold — да |
| любая другая ошибка | запрос отклоняется (fail closed, правильно) |

Отсюда обязательное требование: **заглушка, отвечающая `NotFound` на всё, молча отключает
неизменяемость** — запросы проходят, ошибок нет, Object Lock «не работает» без единого
признака. Три геттера пишутся одновременно с проверкой и покрываются тестом на каждый код
из таблицы. Заглушек «на потом» в этих методах быть не должно.

Второе следствие: при включённом версионировании удаление **без** `versionId` блокировку
не проверяет — создаётся delete marker. Значит маркеры и блокировка обязаны быть в одном
этапе: пока маркеров нет, версия остаётся живой под маркером, клиент считает её удалённой,
и Object Lock выглядит сломанным при полном отсутствии ошибок.

### Где проверяем мы

Одна функция, тест-перебор всех путей:

- `DeleteObject` и `DeleteObjects` **с** `versionId`;
- `deleter`: версия под блокировкой не удаляется, даже если попала в `deleting`;
- удаление тенанта и уничтожение TEK ([ADR-0014](0014-encryption-per-tenant.md));
- admin-API `tapegw`: оператор в COMPLIANCE удалить версию не может. Прямое
  `phobos delete` вне контроля tapegw — фиксируется в эксплуатационной документации как
  запрещённая операция.

**Поправка к уже слитому коду (PR #6).** PutObject переводит прежнюю версию в `deleting`
безусловно. Для бакета без версий это верно, для бакета с `enabled` — уничтожение истории
и обход блокировки. Переход обязан стать условным от `buckets.versioning`. Это **первый
PR этапа V, до листинга.**

**Архивные версии и блокировка.** Продление срока (`PutObjectRetention`) — операция только
над метаданными, лента не нужна. Клиенты регулярно продлевают неизменяемость, и это не
должно вызывать restore.

## Последствия

- `objects_listing` сужен до `WHERE is_current AND NOT is_delete_marker` (ListObjects
  маркеры не показывает), добавлен `objects_versions` по всем строкам для
  `ListObjectVersions`.
- Листинг и удаление пишутся сразу с версиями — второй раз переписывать дороже.
- Некурентные версии и delete markers считаются в квотах
  ([ADR-0011](0011-quotas.md)).
- Тесты: применимая часть тестов versitygw на версионирование и Object Lock; e2e на
  aws-sdk-go-v2 для полного Glacier-цикла; Object Lock в COMPLIANCE с продлением срока на
  архивном объекте **без restore**. Список исключений с причинами — `test/e2e/EXCLUDED.md`.

## Обход GOVERNANCE: бэкенд доверяет заголовку

Бэкенд принимает обход GOVERNANCE по одному заголовку
`x-amz-bypass-governance-retention` и сам право `s3:BypassGovernanceRetention`
не проверяет. Это осознанное допущение, а не забытая проверка:

контроллер versitygw на DeleteObject сам вызывает `auth.CheckObjectAccess`, и
там право на обход проверяется **до** вызова бэкенда. Наша проверка — вторая
линия, и безопасна она ровно в объёме этого допущения.

Отсюда два следствия, их нельзя терять:

- если маршрут DeleteObject когда-нибудь поедет мимо `auth.CheckObjectAccess`
  (свой роут, прямой вызов бэкенда из другого места), доверие заголовку
  превращается в дыру: обход станет доступен любому, кто умеет поставить
  заголовок. Тогда право обязан проверять тот, кто вызывает бэкенд;
- `COMPLIANCE` и `legal hold` заголовком не обходятся ни при каких условиях —
  это единственное, что бэкенд гарантирует сам и независимо от контроллера.

Проверить цепочку целиком нужно e2e-тестами, когда появится конфигурация Object
Lock: (1) обычный ключ без права на обход + заголовок — отказ на версии под
governance; (2) root удаляет версию под compliance — отказ. Во втором случае
versitygw для администратора свою проверку может пропускать, и бэкенд остаётся
единственным барьером.

## Обход GOVERNANCE: право пока негде взять

Заголовок бэкенд уважает (см. выше), и `TestGovernanceBypassAtBackend` это
проверяет. Но сквозного пути обхода в текущей сборке нет: root с
`x-amz-bypass-governance-retention` получает `ErrObjectLocked` от самого
versitygw ещё до вызова бэкенда, а выдача `s3:BypassGovernanceRetention` в
политике бакета обычному ключу права не добавила.

Практический эффект: GOVERNANCE для клиента ведёт себя как COMPLIANCE. Это не
дыра (строже — не опаснее), но и не то, что обещает AWS, поэтому вопрос
отмечен отдельно: либо разбираться, какой слой versitygw требует права на
обход при удалении, либо признать GOVERNANCE у нас «мягкой блокировкой без
обхода» и записать это в документацию пользователя.

## Судьба маркера удаления

Маркер — живая версия без данных: `state = 'marker'`, `retired_at IS NULL`. Он не
относится к терминальным строкам и чисткой по `meta.terminal_retention` не
удаляется, иначе похороненные под ним версии воскресли бы массово и молча.

Удаление маркера по `versionId` — штатный способ S3 вернуть объект — удаляет
строку **физически**. Данных у маркера нет ни на диске, ни на ленте, deleter ему
не нужен, а «удалённая версия нулевого размера» — сущность, которой никогда не
существовало. Для аудита достаточно журнала (T4).

Следствие для T3: маркеры учитываются в квоте на число объектов, поэтому их
физическое удаление должно уменьшать счётчик — точка одна (`deleteVersion`).

## Отклонённые альтернативы

- **Оставлять удалённый маркер в `deleted`.** Строка «удалённой версии без
  данных» ничего не значит, а `CHECK (is_delete_marker = (state = 'marker'))`
  такое сочетание запрещает: клиент получил бы 500 на штатную операцию
  восстановления объекта.
- **Object Lock без версий (режим versitygw по умолчанию).** Не совместимо с AWS и не
  проверяется клиентами корректно: версия под маркером остаётся, а клиент считает её
  удалённой.
- **Делать версии после M2.** Тот же код листинга и удаления пишется дважды; именно
  поэтому этап V вклеен в M2, а не идёт после него.
- **Своя нумерация versionId.** UUID строки уже есть и уже уникален; отдельная последовательность
  добавила бы горячую строку и ничего не дала бы.
