# Копии, размещение и реестр носителей

- **Статус:** решение владельца 2026-11-05; модель данных — до кода migrator (M4)
- **Куда положить:** `docs/proposals/0013-copies-placement-media.md`
- **Связано с:** ADR-0008 (носитель объекта), ADR-0013 (пулы и теги), ADR-0020 (формат
  записи), ADR-0021 (протокол mover), 0011 (repack), 0012 (разделение серверов), Б3/Б4

## Что решаем

Четыре сценария владельца требуют одного и того же — у объекта Phobos (пачки или
крупного объекта) может быть **несколько мест хранения**, и они **меняются со временем**:

1. **Две копии: левая и правая сторона библиотеки.**
2. **Ленивая миграция поколений:** в библиотеку с двумя LTO-7 добавляются два LTO-8,
   новые данные пишутся на LTO-8, старые переезжают постепенно.
3. **Переезд на другую библиотеку** (24 слота → 48): физический перенос картриджей или
   копирование через драйвы.
4. **Копия вне площадки** (Б4) — когда понадобится.

Вместо четырёх отдельных механизмов — один: **политика размещения пула** и **сверка
фактического размещения с политикой**. Новые измерения (стойка, комната, площадка)
добавляются тегами и конфигом, без изменения кода.

---

## 1. Принципы

**Метка ленты уникальна во всей установке**, а не внутри библиотеки. Библиотека — это
где лента лежит сейчас, а не часть её имени. Проверяется при добавлении ленты.

**Источник истины разделён.** Что лента физически содержит и где лежит — знает Phobos
(DSS). Что нужно tapegw сверх этого (жизненный цикл, здоровье, история, сторона,
политика) — реестр носителей tapegw. Поля Phobos в tapegw **не дублируются как
источник истины**: библиотека и свободное место читаются у Phobos, при необходимости
кэшируются с явной пометкой «кэш».

**Размещение задаётся тегами.** Каждая лента несёт теги: пул, поколение, сторона, при
необходимости — площадка, стойка. Запись идёт с полным набором тегов копии. По находке
M0-08 теги в Phobos работают как «И» и защищают в одну сторону, поэтому правило
«каждая лента и каждая запись с тегами» остаётся обязательным.

**Расширяемость — данными, а не миграциями.** Поля, от которых зависит логика
(состояние, поколение, сторона, пул, WORM), — типизированные колонки. Всё
информационное и производителезависимое (атрибуты MAM, счётчики, модель) — в `attrs
jsonb`. История — в журнале событий только на добавление. Новая политика (например,
«выводить ленту после N загрузок») пишется поверх уже собранных данных без миграции.

---

## 2. Политика размещения пула

У пула — список **спецификаций копий**. Каждая спецификация — имя и набор тегов. Число
копий = длина списка.

```yaml
pools:
  shared:
    library_write: lib-main         # куда пишем сейчас; меняется при переезде
    copies:
      - name: left
        tags: [pool:shared, gen:lto8, side:left]
      - name: right
        tags: [pool:shared, gen:lto8, side:right]
```

Примеры, которые ложатся на ту же модель без кода:

| Сценарий | Политика |
| --- | --- |
| Одна копия, MVP | `copies: [{name: main, tags: [pool:shared, gen:lto7]}]` |
| Две стороны | две копии с `side:left` и `side:right` |
| Ленивая миграция LTO-7 → LTO-8 | поменять `gen:lto7` на `gen:lto8` в политике; старые копии становятся «не по политике» |
| Копия вне площадки | третья копия с `site:vault` |
| Переезд библиотеки | поменять `library_write`; старые ленты переносятся физически |

**Когда объект считается архивным.** Только когда записаны **все** копии текущей
политики. До этого landing не очищается: иначе между первой и второй записью на ленте
лежит одна копия, а на диске — ничего.

---

## 3. Сверка размещения (reconciler)

Фоновый процесс сравнивает фактические копии каждого объекта Phobos с текущей политикой
его пула и приводит к ней. Один механизм закрывает:

- **ленивую миграцию поколений:** копии на `gen:lto7` — «не по политике», reconciler
  создаёт копию на `gen:lto8` и затем помечает старую мёртвой;
- **добавление второй копии к уже записанным данным:** у старых объектов одна копия,
  политика требует две — reconciler дописывает недостающую;
- **восстановление потерянной копии:** копия признана нечитаемой (restore, проверка
  целостности) — reconciler пересоздаёт её из живой;
- **освобождение лент при repack** (0011) — частный случай: копия переносится, старая
  становится мёртвой.

Правила reconciler:

- приоритет ниже архивации и restore, работа в окна простоя драйвов;
- источник — любая читаемая копия, при выборе предпочитается уже смонтированная лента;
- старая копия помечается мёртвой **только после** записи новой и проверки SHA-256;
- **ускоритель «перенос при restore»:** если объект прочитан с ленты не по политике, он
  уже в кэше, и недостающая копия пишется из кэша без отдельного чтения ленты.

## 4. Модель данных (M4)

### 4.1. Копии объекта Phobos

`archive_copies` — место хранения каждой копии пачки или крупного объекта:

| Колонка | Смысл |
| --- | --- |
| `oid uuid` | объект Phobos (пачка или крупный объект) |
| `spec text` | имя спецификации копии из политики (`left`, `right`, `main`…) |
| `medium text` | метка ленты (уникальна в установке) |
| `state` | `pending` → `writing` → `done`; `lost` (нечитаема); `dead` (заменена, ждёт repack) |
| `written_at`, `verified_at` | |
| `attrs jsonb` | расширение без миграций |

Объекты (`objects`) ссылаются на `oid`, а не на носитель. Колонки `objects.phobos_medium`
и `packs.medium` из 0011 заменяются этой таблицей — пока данных нет, это бесплатно.

### 4.2. Реестр носителей

`media`:

| Колонка | Смысл |
| --- | --- |
| `label text PK` | метка ленты, уникальна в установке |
| `kind` | `data`, `cleaning`, `diagnostic` |
| `generation text` | `LTO-7`, `LTO-8`, …; задаёт совместимость с драйвами |
| `worm bool` | лента WORM (для будущих compliance-пулов: её нельзя переписать и уплотнить) |
| `pool_id` | пул ленты |
| `side`, `home_slot` | сторона и домашний слот (для своего манипулятора — из геометрии) |
| `lifecycle` | `new` → `formatted` → `active` → `full` → `read_only` → `evacuating` → `retired` |
| `location` | `in_slot`, `in_drive`, `in_transit`, `offline`, `offsite`, `lost` |
| `health` | `ok`, `degraded`, `failing`; вычисляется из истории |
| `last_verified_at` | последняя проверка целостности |
| `attrs jsonb` | атрибуты MAM: серийник картриджа, производитель, дата, счётчик загрузок, объём записано/прочитано за жизнь; модель, Type M и прочее |

Библиотека и свободное место **не** хранятся как источник истины — читаются у Phobos.

`media_events` — журнал только на добавление: загрузка и выгрузка (с драйвом), ошибки
чтения и записи, флаги TapeAlert, перемещения между слотами и библиотеками, смена
состояния, результаты проверки целостности. Отсюда считаются `health` и политики вывода
из оборота.

### 4.3. Реестр драйвов

`drives`: серийник (PK), библиотека, поколение, модель, прошивка, состояние (`online`,
`offline`, `needs_cleaning`, `failed`), `attrs jsonb`. `drive_events` — как у носителей:
монтирования, ошибки, чистки, TapeAlert.

### 4.4. Совместимость поколений — в конфиге

```yaml
generations:
  LTO-7: { read: [LTO-7, LTO-8], write: [LTO-7, LTO-8] }
  LTO-8: { read: [LTO-8, LTO-9], write: [LTO-8, LTO-9] }
  LTO-9: { read: [LTO-9, LTO-10], write: [LTO-9, LTO-10] }
```

Значения — стартовые и сверяются со спецификацией LTO и конфигом совместимости Phobos
(`tape_type` / `drive_type`) в спайке. Используется для выбора mover и для проверки
«эту ленту ещё есть чем прочитать».

**Алерт поколения:** если в установке есть живая копия на поколении, которое не читает
ни один драйв из запланированных к работе, — предупреждение. LTO-9 ленты LTO-7 не
читает: миграцию с LTO-7 нужно закончить до вывода последнего драйва LTO-7/LTO-8.

## 5. Сценарии по шагам

### 5.1. Две стороны библиотеки

1. Ленты левой стороны получают тег `side:left`, правой — `side:right`; `media.side`
   заполняется из геометрии слота.
2. Политика пула — две копии с тегами сторон.
3. Каждая пачка или крупный объект пишется дважды, отдельными операциями протокола с
   разными тегами. Встроенный `raid1` Phobos не умеет «эту реплику на левую, ту на
   правую»; возможность задать теги каждой копии через механизм копий Phobos 3 —
   вопрос спайка.
4. **Правило:** лента не меняет сторону. Домашний слот всегда на стороне её тега.
   `klipper-tlc` проверяет при каждой выгрузке, что слот возврата на той же стороне.
5. Restore выбирает копию, чья лента смонтирована или на стороне со свободным драйвом.
   При ошибке чтения — другая копия, а сбойная получает `lost` и уходит в reconciler.

Защищает от отказа одной ленты и частично от локального повреждения одной стороны. **Не
защищает** от отказа общего робота, драйвов и от аварии площадки — это задача копии вне
площадки.

### 5.2. Ленивая миграция LTO-7 → LTO-8 в той же библиотеке

1. Добавить два драйва LTO-8 и новые ленты LTO-8 с тегами `pool:…`, `gen:lto8`.
2. В политике пула заменить `gen:lto7` на `gen:lto8`: новая запись идёт только на LTO-8
   и только через драйвы LTO-8.
3. Чтения старых лент маршрутизируются предпочтительно на драйвы LTO-7, чтобы LTO-8
   оставались под запись.
4. Reconciler переносит копии с LTO-7 на LTO-8 в фоне; перенос при restore ускоряет
   переезд читаемых данных.
5. Лента LTO-7 без живых копий → `retired`. Когда живых копий на LTO-7 не осталось —
   драйвы LTO-7 выводятся.

### 5.3. Переезд в другую библиотеку

**Физический перенос** (поколение совместимо):

1. Подключить библиотеку B: TLC, драйвы, mover (`mover://<библиотека>/<драйв>`).
2. Поменять `library_write` пула на B.
3. Партиями: лента → `location: in_transit` (recaller ждёт, а не повторяет) → выгрузка из
   A → установка в B → `phobos tape rename --new-library B` → обновление inventory TLC → 
   `location: in_slot`.
4. Библиотека A пуста — вывести из конфигурации.

**Копирование через драйвы** (поколения несовместимы): обе библиотеки онлайн, новая
политика ссылается на теги лент в B, reconciler переносит копии.

## 6. Recaller: недоступная лента

Состояния `location` `in_transit`, `offline`, `offsite`, `lost` и `lifecycle`
`evacuating` — штатные. Если у объекта есть копия на доступной ленте — читается она. Если
доступных копий нет — запрос ждёт со статусом «носитель недоступен» и алертом оператору,
без бесконечных повторов. Это же состояние нужно для копии вне площадки (Б4).

## 7. Спайк M0-11 (до кода migrator)

На mhVTL: две виртуальные библиотеки и драйвы двух поколений (mhVTL эмулирует разные
модели LTO).

1. `phobos tape rename --new-library` есть в 3.4.1; после переноса `phobos_get` читает
   объект из новой библиотеки без переимпорта. То же для `drive --new-library`.
2. Совместимость поколений в конфиге Phobos: лента LTO-7 читается драйвом LTO-8; запись с
   `gen:lto8` идёт только на ленты LTO-8.
3. Копии объекта в Phobos 3: можно ли вторую копию записать с другими тегами; как
   `phobos_get` выбирает копию и что делает при недоступности одной из них. Если нельзя —
   копии ведёт tapegw отдельными объектами Phobos, и это фиксируется в ADR.
4. `phobos tape repack` с целевым тегом (для reconciler и миграции).
5. Чтение атрибутов MAM при загрузке (`klipper-tlc` уже читает метку): какие счётчики
   **берутся из MAM, а не из Phobos**. Счётчик загрузок — из MAM: на стенде
   `phobos tape list -o stats.nb_load` показывает `0` при заведомо выполненных
   загрузках, тогда как `Load count` из MAM растёт (6 после шести). Полагаться на
   `stats.nb_load` для политик здоровья нельзя — политики молча перестанут
   срабатывать. Читать MAM можно только в окнах Load/Unload, где LTFS в драйве
   нет: `Unit Attention` сообщается один раз на инициатора, а мы с LTFS — один
   инициатор ([спайк M0-12](../spikes/M0-12-write-flag-mailslots.md)).
   доступны на виртуальных драйвах, чтобы проверить сбор в `media.attrs`.

Результат — `docs/spikes/M0-11-libraries-generations-copies.md`.

## 8. Изменения плана

- **До кода migrator:** спайк M0-11; ADR «копии и политика размещения» по разделам 2–4.
- **M4:** `archive_copies` вместо колонок носителя; `media`, `drives`, журналы событий;
  политика копий пула в конфиге; правило «архивный = все копии записаны»; уникальность
  метки при добавлении ленты.
- **M5:** выбор копии при restore; состояние «носитель недоступен».
- **M7/M8 (`klipper-tlc`):** сторона слота из геометрии и проверка «лента не меняет
  сторону»; сбор атрибутов MAM при каждой загрузке в `media_events`.
- **После MVP:** reconciler (ленивая миграция, дописывание копий, восстановление
  потерянных), политики здоровья и вывода лент, WORM-пулы для compliance.

## 9. Тесты (к реализации)

- запись с политикой «две стороны» → две копии на лентах с разными тегами стороны;
  мутация «одинаковые теги у обеих копий» ловится;
- объект не становится `archived`, пока не записана вторая копия; landing не очищается;
- restore при `lost` первой копии читает вторую;
- метка ленты, уже существующая в другой библиотеке, отклоняется при добавлении;
- смена политики `gen:lto7` → `gen:lto8`: новые записи идут только на LTO-8, старые
  копии видны как «не по политике»;
- лента в `in_transit`: restore объекта с единственной копией ждёт со статусом, а не
  повторяет.
