# ADR-0023. События журнала: та же транзакция и счётчик на тенанта

- **Статус:** принято 2026-11-10
- **Дата:** 2026-11-10
- **Этап плана:** «Журнал метаданных на ленте» (первая часть, Ж1)
- **Связано:** [ADR-0020](0020-tape-record-format.md) §3 (формат сегмента),
  [ADR-0015](0015-versioning-and-object-lock.md) (что вообще бывает с блокировками),
  [ADR-0014](0014-encryption-per-tenant.md) (ключ на тенанта),
  `docs/ARCHITECTURE.md` — пункт плана «Журнал метаданных на ленте», PR #43–#45

## Контекст

Решения #43–#45 и ADR-0020 §3 определили, как журнал выглядит **на ленте**:
сегменты по тенанту, `journal_seq` внутри тенанта, отдельный поток пачек журнала,
шифрование ключом тенанта, снимки состояния. Но между «метаданные изменились» и
«сегмент лёг на ленту» ничего не описано, а именно там теряются данные:

- событие можно записать **после** коммита изменения — и падение в этом окне
  даст изменение без события; для продлённого COMPLIANCE это значит «срок
  изменился, на ленту он не попал», то есть снятую неизменяемость;
- номера событий можно брать из `sequence` Postgres — и откатившаяся операция
  оставит пропуск, а пропуск в журнале `rebuild-meta` обязан читать как потерю
  события, то есть ложная тревога станет нормой;
- не перечислено, **какие** изменения вообще порождают событие, — а пропущенный
  вид не всплывёт никогда: всё работает, просто при восстановлении чего-то нет;
- событие ссылается на бакет, а `buckets.id` после `rebuild-meta` другой.

## Решение

**1. Событие пишется в той же транзакции, что и изменение.** `meta.appendEvent`
принимает транзакцию вызывающего и не умеет открывать свою. Таблица
`journal_events` — исходящая очередь (outbox) в той же базе, что и сами
данные: отдельный брокер здесь означал бы ровно то же окно, только между двумя
системами, где атомарности нет вовсе.

Тест, который это держит, устроен «наоборот»: яд ставится на саму вставку
события, а проверяется, что **изменение** не состоялось. Если событие однажды
уедет из транзакции, тест упадёт — а не пройдёт молча.

**2. `journal_seq` — счётчик на строке тенанта, а не sequence.**

```sql
UPDATE tenants SET journal_seq = journal_seq + 1 WHERE id = $1 RETURNING journal_seq
```

Это не «обновить счётчик», а способ взять строку тенанта на запись: параллельные
изменения одного тенанта сериализуются на ней и получают соседние номера, а
откат откатывает номер. Номера плотные по построению, и любой пропуск при
чтении — это авария, а не штатная дырка.

**Порядок блокировок:** строка тенанта берётся **последней** — после
advisory-лока ключа, бакета и строк `objects`. Все места журнала следуют ему;
обратный порядок в одном месте дал бы взаимоблокировку между двумя изменениями
одного ключа. Цикла не возникает и с остальными writers: `SELECT … FOR UPDATE`
на `tenants` в коде нет вовсе, а единственные другие изменения строки тенанта —
`EnsureTenantKey`/`SetTenantKey`/`DestroyTenantKey` — однострочные, то есть
держат только эту строку и не могут ждать то, что держит транзакция журнала.
Проверяется тестом со смешанными параллельными изменениями, а не рассуждением.

**3. Сегмент описывается диапазоном `seq_first..seq_last`, а не ссылкой события
на сегмент.** Поэтому события остаются таблицей только на добавление (тот же
триггер `tapegw_journal_append_only`, что у `media_events`): UPDATE им не нужен
вовсе, и ограничение не приходится ни для кого обходить.

**4. Что входит в журнал** (сверено с ADR-0015 по списку операций, которые
меняют блокировку):

| Вид | Источник |
| --- | --- |
| `retention` | `PutObjectRetention` |
| `legal_hold` | `PutObjectLegalHold` |
| `delete_marker` | `DeleteObject` без `versionId`; удаление маркера по `versionId` (флаг `removed`) |
| `delete_version` | `DeleteObject` по `versionId`, в том числе с обходом GOVERNANCE (флаг `bypass`); удаление объекта в бакете без версий; замена null-версии при перезаписи |
| `bucket_config` | создание бакета, версионирование, Object Lock, ACL, политика, смена владельца, удаление бакета |

Не входят сознательно:

- **сама запись версии** — её описывает манифест, записанный вместе с данными;
  retention и legal hold, проставленные при записи, живут там же;
- **теги бакета** — на сохранность и доступ не влияют, в снимок не входят.

**5. `bucket_config` — снимок целиком, а не дифф.** Применять диффы при
восстановлении значит хранить историю полей и их порядок; снимок применяется
повтором идемпотентно. Состав: версионирование, Object Lock с `lock_config`
(срок по умолчанию живёт именно там — колонка `buckets.default_retention` кодом
не используется), владелец и его тенант, ACL, политика, признак удаления.

**6. Версии в событиях — по UUID, бакет — по имени.** UUID версии после
восстановления сохраняется (он и есть id объекта Phobos), а `buckets.id`
генерируется заново, поэтому событие называет бакет именем. Имена лежат в
зашифрованном сегменте, так что правило «в открытом виде не бывает имён» не
нарушается.

**7. Тенант события берётся из строки, а не из учётки запроса.** Под обходом по
роли страж отдаёт «все тенанты», и событие уехало бы в несуществующий тенант —
та же форма ошибки, что с DEK на PR #127.

## Измерение цены (после PR #136)

Плотная нумерация стоит блокировки строки тенанта, и её стоимость измерена, а не
оценена: `internal/meta/journal_throughput_test.go` гоняет 1000 параллельных
`PutObjectRetention` по разным объектам **одного** тенанта (16 горутин, пул 16 —
размер пула задан явно, иначе pgxpool поставил бы `max(4, NumCPU)` и измерялась
бы очередь пула) тремя путями:

| Путь | Что делает | Результат |
| --- | --- | --- |
| a | штатный `PutObjectRetention`: событие + `UPDATE tenants` в той же транзакции | ≈1000/сек |
| b | то же без журнала: `SELECT … FOR UPDATE` + `UPDATE objects` + commit | ≈6700–8300/сек |
| c | то же событие, но номер из обычной `sequence`, строка тенанта не трогается | ≈6000/сек |

```
TAPEGW_TEST_DSN=… go test -count=1 -run TestJournalRetentionThroughput -v ./internal/meta/
```

Разложение: **само событие стоит x1.1–1.4, вся остальная цена (x6–x8) — строка
тенанта.** Механизм не в дороговизне `UPDATE`, а в том, что блокировка держится
до коммита: транзакции одного тенанта выстраиваются в очередь, и каждая делает
свой `fsync` в одиночестве — групповой коммит, который и кормит путь (b) при
16 параллельных участниках, не складывается. Замеры на dev-машине (Postgres 16 в
docker, локальный диск), между прогонами отношение гуляет x7…x8.4; абсолютные
числа — порядок величины, а не гарантия.

**Решение: оставляем счётчик на строке тенанта.** Причина не в том, что x7 мало,
а в том, для чего журнал нужен: retention, проставленный при записи, в журнал не
попадает вообще (он в манифесте), а `PutObjectRetention` — это продление или
изменение уже записанного срока, то есть операция управления хранилищем, а не
потоковая запись. Тысяча таких в секунду на одного тенанта — с запасом над
сценарием «продлить срок на хранилище», где объекты идут пачкой, но пачка эта
раз в сутки, а не непрерывно.

**Триггер пересмотра.** Если у одного тенанта понадобится больше нескольких
сотен журналируемых изменений в секунду устойчиво, переходят к варианту (c):
при записи событие получает только служебный id из обычной `sequence` (пропуски
допустимы) и строку тенанта не трогает, а плотный `journal_seq` выдаёт воркер
сегментов при запечатывании (Ж2). Порядок событий одного объекта при этом
сохраняется — изменения одного объекта и так сериализованы блокировкой его
строки, а порядок событий разных объектов при восстановлении не важен. Цена
перехода: плотность тогда проверяется по сегментам, а не по таблице событий,
первичным ключом `journal_events` становится служебный id, и «пропуск в
нумерации» перестаёт быть свойством таблицы — им становится свойство диапазона
запечатанного сегмента. Решение принято принимать на Ж2, пока формат сегмента не
записан на ленту.

## Последствия

- `tenants.journal_seq` — «горячая» строка на тенанте с активным трафиком
  блокировок: изменения одного тенанта, которые пишут событие, выполняются
  строго по одному, сколько бы соединений ни было. Измерено в разделе выше:
  ≈1000 продлений в секунду на тенанта, из них x6–x8 даёт именно эта строка.
  Другой цены у плотной нумерации нет.
- Часть функций про бакет перестала быть однострочной и стала транзакцией:
  `CreateBucket`, `SetBucketACL`, `SetBucketPolicy`. Иначе событие в той же
  транзакции выразить нечем. `SetBucketTags` осталось без транзакции — см. п. 4.
- Перезапись null-версии в `PutObject` идёт через `markDeletingIDs`, а не голый
  `UPDATE`: попутно выяснилось, что прежний `UPDATE` не списывал байты версии с
  живого остатка её пачки, то есть `live_bytes` после перезаписи оставался
  завышенным навсегда.
- До появления воркера сегментов таблица `journal_events` растёт: события —
  единственная запись об изменениях, и удалять их до архивации нельзя. Рost —
  воркер сегментов (Ж2), который помечает диапазон ушедшим на ленту.
- Тесты миграций 0017–0019 обязаны снимать Down 0027 до Down 0018: триггер
  журнала висит на функции из 0018.

## Отклонённые альтернативы

- **`sequence` Postgres для `journal_seq`.** `nextval` не откатывается:
  откатившаяся операция оставляет пропуск, а пропуск в журнале — это «потеряно
  событие». Отказ от него и есть смысл счётчика на строке. Как *служебный* id
  sequence возвращается в варианте (c) из раздела «Измерение цены» — там
  пропуски допустимы именно потому, что плотный номер выдаёт воркер сегментов.
- **Событие отдельным шагом после коммита** (фоновый писатель, лог-файл,
  отдельный брокер). Окно «изменение есть, события нет» становится окном между
  системами, где атомарности нет уже никак. Именно этого требует избежать п. 1.
- **Отметка «изменилось» на самой строке `objects`** вместо отдельной таблицы.
  Одна строка не хранит историю: retention меняют много раз, и каждое изменение
  должно быть видно по отдельности, иначе восстановление применит только
  последнее.
- **Дифф конфигурации бакета** вместо снимка. Меньше байт, но применение
  перестает быть идемпотентным и требует порядка полей — при восстановлении это
  ровно тот источник расхождений, который ищут годами.
- **Внешние ключи `journal_events.object_id → objects` и `bucket_id → buckets`.**
  janitor физически удаляет строки `objects` в `deleted` по
  `meta.terminal_retention`; FK либо отверг бы чистку, либо каскадом стёр бы
  журнал вместе с данными. Событие обязано пережить строку, о которой оно.
- **Отдельная таблица «сегменты» уже сейчас.** Таблица сегментов нужна воркеру
  (Ж2); заводить её вместе с событиями означало бы хранить состояние, которое
  никто не читает.
