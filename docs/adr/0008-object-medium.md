# ADR-0008. Носитель объекта узнаётся при архивации и хранится у нас

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** **M4** (колонка заполняется при архивации), используется в M5
- **Связано:** [ADR-0006](0006-libphobos-linkage.md),
  [ADR-0007](0007-mover-worker.md),
  [`docs/spikes/M0-02-libphobos-api.md`](../spikes/M0-02-libphobos-api.md)

## Контекст

Чтобы группировать батч recaller по лентам и не гонять картриджи туда-сюда, для
каждого объекта нужно знать, на каком он носителе.

Спайк [M0-02](../spikes/M0-02-libphobos-api.md) показал: через `libphobos_store`
этих данных нет. `phobos_getmd` отдаёт только пользовательские атрибуты, а
`phobos_store_copy_list` возвращает `copy_info` без extents. Расположение живёт в
DSS (`struct extent.media`) и достаётся либо через приватную `libpho_core`, либо
напрямую из таблиц Postgres.

## Решение

**Носитель узнаётся один раз — при архивации — и кладётся в нашу колонку
`objects.phobos_medium`.**

После успешного батча делается **один** вызов `phobos extent list` на весь батч,
но результат записывается **по каждому объекту отдельно** — CLI принимает список
oid и отдаёт носитель для каждого. Стоимость та же, что при «одно значение всем»,
а допущение исчезает.

Раньше этот ADR опирался на свойство «один `phobos_put` пишет на один носитель»,
которое показал спайк. На него полагаться нельзя: спайк проверял 20 объектов по
1 MiB, которые заведомо влезли на один носитель. Когда лента заполняется посреди
батча, Phobos вправе продолжить на другой — и тогда «один запрос, одно значение
всем» **тихо запишет неверный носитель части объектов**. Ошибка без симптомов,
хуже которой нет.

Recaller потом группирует очередь по `objects.phobos_medium` и в DSS не ходит
вообще.

### Источник данных, по убыванию предпочтения

**1. CLI `phobos extent list` с машиночитаемым выводом.** Проверено на 3.4.1,
работает и поодиночке, и пакетом:

```bash
$ phobos extent list -f json -o oid,media_name,offset,size spike2/D-00
[{"oid": "spike2/D-00", "media_name": ["/var/lib/phobos2"],
  "offset": [0], "size": [1048576]}]

$ phobos extent list -f json -o oid,media_name oid1 oid2 oid3 oid4
[{"oid": "oid1", "media_name": ["/var/lib/phobos2"]}, ...]
```

CLI — интерфейс для пользователей, он стабильнее внутренней схемы. Один вызов на
батч из нескольких сотен объектов стоит копейки на фоне минутной записи на ленту.

**2. Если CLI по какой-то причине не подходит** — один read-only SQL-запрос к
таблицам DSS. Условия, при которых это допустимо:

- запрос изолирован в **одной** функции, больше нигде схема Phobos не используется;
- при старте проверяется версия схемы Phobos, и при несовпадении tapegw **отказывается
  запускаться**, а не работает вполоборота;
- на стенде `ci-dir` есть тест, который падает, когда схема меняется.

## Объект целиком на одном носителе

**Пишем батч с `no_split`.** В API это `bool no_split` в
`struct pho_xfer_put_params` (`phobos_store.h`): «all targets inside a xfer of
the put command should be written without split (e.g. on the same media)».
Профиль его задать не может, только прямо в вызове.

Смысл в том, чтобы **носитель стал свойством объекта**, а не свойством
расположения. Пока объект целиком на одном носителе:

- `objects.phobos_medium` — полное описание местоположения, restore ищет один
  картридж и одну позицию;
- группировка очереди recaller по колонке честная: батч не рассыпается на
  половину ленты;
- нет случая «объект частично на одной ленте, частично на другой», который
  удваивает число загрузок при restore.

Цена — объект обязан влезть на носитель. Поэтому в конфиг добавляется
`s3.max_object_size`, заметно меньший ёмкости ленты, и **такие объекты
отклоняются на PUT**, а не падают позже в migrator'е. Ошибка на PUT — это
ответ клиенту `EntityTooLarge`, ошибка в migrator'е — это застрявшая очередь и
алерт в три часа ночи.

Проверка `no_split` обязательна: без него Phobos дробит объект между носителями
(у CLI для этого есть `--no-split`), и тогда колонка с носителем врёт.

### Что это стоит и как Phobos выбирает носитель

Флаг относится ко **всему батчу**, значит на ленту должна влезть вся пачка, а не
один объект. Замерено в [M0-07](../spikes/M0-07-mhvtl-ltfs.md):

- если хоть один носитель свободен настолько, что вмещает батч целиком, Phobos
  **сам его выбирает** — ошибки нет;
- если не вмещает ни один — `ENOSPC`, и **ничего не записывается**, каталог и
  копии остаются чистыми.

Отсюда два следствия.

**Migrator не должен уметь дробить батч под остаток ленты** — эта ветка логики
оказалась не нужна.

**`batch_max_bytes` — это ещё и объём потерь.** Лента, на которую батч не влез,
остаётся с незаполненным хвостом, в среднем порядка половины батча. Для LTO-8
(12 TiB нативную) и батча 200 GiB это ~1,5 % ёмкости.

Поэтому ограничения конфига связаны:

```
s3.max_object_size  <=  migrator.batch_max_bytes  <=  свободное место на одной ленте
```

`max_object_size` заведён именно здесь: объект крупнее `batch_max_bytes` никогда
не был бы заархивирован, и узнавать об этом нужно на PUT (`EntityTooLarge`), а не
после трёх попыток в migrator'е.

## Отклонённая альтернатива

**Линковаться с `libpho_core` и держать собственный DSS-хендл**
(`dss_extent_get` с фильтром по uuid объекта).

Отклонено: `libpho_core` — приватная библиотека из `/usr/lib64/phobos`, не
публичный API. Связанность с внутренностями получается такая же, как при чтении
таблицы напрямую, но дополнительно через ABI. Худший вариант: и привязка к
внутренностям, и хрупкость бинарного интерфейса.

Отдельно отмечу: этот вариант выглядел «чистым» только на первый взгляд. Он не
избавляет от знания схемы — `struct extent` отражает те же колонки.

## Последствия

- Миграция: `objects.phobos_medium **text[]**`. В выводе CLI `media_name` —
  массив, и при `repl_count=2` носителей действительно два: layout raid1
  пишет реплики на разные носители. Хранить один скаляр означало бы потерять
  вторую реплику, а потом удивляться, что recaller ищет объект на одном
  носителе.
- Колонка nullable: известна только у архивированных объектов.
- Механизм появляется в **M4**, а не в M5: колонка должна заполняться в момент
  архивации, задним числом её не восстановить без обхода всех лент.
- Зависимость от CLI — это зависимость от установленного Phobos в том же
  контейнере, где крутится mover. Разместить mover рядом с Phobos всё равно
  придётся (ADR-0007), так что новой стоимости здесь нет.
- Формат вывода CLI (`-f json`) считаем стабильным договором; если Phobos его
  сломает, это увидит тест на `ci-dir`.
- Формулировка «задним числом не восстановить» была **неверной** и противоречила
  пункту про отсутствие backfill: CLI отдаёт носитель для любого архивного
  объекта в любой момент. Причина делать это при архивации — **экономия** (один
  вызов на батч вместо отдельного прохода по всем объектам при первом restore), а
  не невозможность.
- Для объектов, заархивированных до включения механизма, колонка останется NULL.
  Заполнить их можно и позже: при первом restore носитель будет запрошен и
  дописан в колонку. До этого recaller для них группирует «всё одним батчем».
