# План: PR#2b — ChangeBucketOwner переносит тенанта, проверки доступа внутри тенанта 2

Продолжение `pr2a-iam-service.md`. Процесс — тот же (см. раздел «Процесс» там же):
субагент реализует и коммитит после каждого шага, агент проверяет своими
мутациями, PR ревьюеру — только после проверки.

## Что сделать

### 1. ChangeBucketOwner переносит тенанта

- Переносить бакет в тенант **нового владельца** (`ProjectID` берётся из IAM),
  если бакет **пуст**.
- **Отказывать** в переносе между тенантами, если в бакете есть объекты: объекты,
  квоты и пул лент так просто не переходят.

Это **заменяет** строку чек-листа T1 «новый владелец из того же тенанта» в
`docs/ARCHITECTURE.md` — её нужно переформулировать, иначе следующий автор будет
соответствовать отменённому требованию.

### 2. Проверки доступа внутри тенанта 2

Проверка «политика разрешает чтение» строится **внутри тенанта 2** двумя ключами
одного тенанта: одна учётка создаёт бакет и выдаёт права другой. Это настоящий
сценарий клиента (несколько ключей одного тенанта). Прежний вид теста по факту
проверял доступ к бакету системного тенанта.

## Чем подтвердить (критерий ревьюера)

Основной сценарий роли `user` **целиком**:

1. admin создаёт бакет (бакет попадает в системный тенант);
2. admin передаёт владение ключу клиента из тенанта 2;
3. клиент **пишет и читает** в этот бакет.

Плюс отдельный отказ, когда в бакете **уже есть объекты**.

Каждую проверку подкреплять мутацией, падающей по существу. Отдельно убедиться,
что тест на шаг 3 не проходит «виртуозно»: если `ChangeBucketOwner` не переносит
`tenant_id`, а страж пропускает по другой причине, тест обязан упасть.

## Готовность

Как в `pr2a-iam-service.md`: сборка, тесты с DSN (выполняются, не скипаются),
e2e зелёный, `go vet` / `staticcheck` / `gofmt` чисто, каждый коммит собирается.

## Мелочи из ревью PR#20 (взять в этот PR)

### 1. Секрет в `tapegw-iamctl` не должен светить в процессах

`-secret` в командной строке виден в `ps` и остаётся в истории shell. Для CI это
неважно, для боевой выдачи ключей клиентам — нет. Читать секрет из stdin (или
файла), флаг `-secret` оставить только для тестов либо убрать вовсе.

### 2. Закрепить связку «статус ↔ секрет» в схеме

После того как `secret_wrapped` стал nullable, ничто не мешает активной учётке
остаться без секрета или отозванной — остаться с секретом. Дешёвое ограничение:

```sql
CHECK ((status = 'revoked') = (secret_wrapped IS NULL))
```

### 3. Down-миграция 0007 после первого отзыва невозможна

`Down` возвращает `secret_wrapped SET NOT NULL` и упадёт, если в базе есть хоть
одна отозванная учётка (секрета у неё уже нет, восстанавливать не из чего).
Либо записать это прямо в миграции как осознанное ограничение, либо обрабатывать
отозванные строки перед `SET NOT NULL`.
