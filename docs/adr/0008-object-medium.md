# ADR-0008. Носитель объекта узнаётся при архивации и хранится у нас

- **Статус:** принято 2026-11-03
- **Дата:** 2026-11-03
- **Этап плана:** **M4** (колонка заполняется при архивации), используется в M5
- **Связано:** [ADR-0006](0006-libphobos-linkage.md),
  [ADR-0007](0007-mover-worker.md),
  [`docs/spikes/M0-02-libphobos-api.md`](../spikes/M0-02-libphobos-api.md)

## Контекст

Чтобы группировать батч recaller по лентам и не гонять картриджи туда-сюда, для
каждого объекта нужно знать, на каком он носителе.

Спайк [M0-02](../spikes/M0-02-libphobos-api.md) показал: через `libphobos_store`
этих данных нет. `phobos_getmd` отдаёт только пользовательские атрибуты, а
`phobos_store_copy_list` возвращает `copy_info` без extents. Расположение живёт в
DSS (`struct extent.media`) и достаётся либо через приватную `libpho_core`, либо
напрямую из таблиц Postgres.

## Решение

**Носитель узнаётся один раз — при архивации — и кладётся в нашу колонку
`objects.phobos_medium`.**

Это возможно благодаря свойству, которое показал тот же спайк: **один
`phobos_put` пишет на один носитель**. Значит после успешного батча достаточно
**одного** запроса, и результат записать всем объектам батча — не по запросу на
объект.

Recaller потом группирует очередь по `objects.phobos_medium` и в DSS не ходит
вообще.

### Источник данных, по убыванию предпочтения

**1. CLI `phobos extent list` с машиночитаемым выводом.** Проверено на 3.4.1,
работает и поодиночке, и пакетом:

```bash
$ phobos extent list -f json -o oid,media_name,offset,size spike2/D-00
[{"oid": "spike2/D-00", "media_name": ["/var/lib/phobos2"],
  "offset": [0], "size": [1048576]}]

$ phobos extent list -f json -o oid,media_name oid1 oid2 oid3 oid4
[{"oid": "oid1", "media_name": ["/var/lib/phobos2"]}, ...]
```

CLI — интерфейс для пользователей, он стабильнее внутренней схемы. Один вызов на
батч из нескольких сотен объектов стоит копейки на фоне минутной записи на ленту.

**2. Если CLI по какой-то причине не подходит** — один read-only SQL-запрос к
таблицам DSS. Условия, при которых это допустимо:

- запрос изолирован в **одной** функции, больше нигде схема Phobos не используется;
- при старте проверяется версия схемы Phobos, и при несовпадении tapegw **отказывается
  запускаться**, а не работает вполоборота;
- на стенде `ci-dir` есть тест, который падает, когда схема меняется.

## Отклонённая альтернатива

**Линковаться с `libpho_core` и держать собственный DSS-хендл**
(`dss_extent_get` с фильтром по uuid объекта).

Отклонено: `libpho_core` — приватная библиотека из `/usr/lib64/phobos`, не
публичный API. Связанность с внутренностями получается такая же, как при чтении
таблицы напрямую, но дополнительно через ABI. Худший вариант: и привязка к
внутренностям, и хрупкость бинарного интерфейса.

Отдельно отмечу: этот вариант выглядел «чистым» только на первый взгляд. Он не
избавляет от знания схемы — `struct extent` отражает те же колонки.

## Последствия

- Миграция: `objects.phobos_medium` (nullable — известна только у архивированных
  объектов).
- Механизм появляется в **M4**, а не в M5: колонка должна заполняться в момент
  архивации, задним числом её не восстановить без обхода всех лент.
- Зависимость от CLI — это зависимость от установленного Phobos в том же
  контейнере, где крутится mover. Разместить mover рядом с Phobos всё равно
  придётся (ADR-0007), так что новой стоимости здесь нет.
- Формат вывода CLI (`-f json`) считаем стабильным договором; если Phobos его
  сломает, это увидит тест на `ci-dir`.
- Для объектов, заархивированных до включения механизма, колонка останется NULL, и
  recaller для них деградирует до группировки «всё одним батчем». Это приемлемо и
  не требует backfill.
