# Вертикальный срез на ci-dir

Цель: один прогон в контейнере доказывает, что архитектура работает целиком.
Лента для этого не нужна — `dir` ведёт себя как носитель, а механика ленты
добавляется потом и архитектуру не меняет.

## Что должно получиться

Один стенд: `tapegw` + один `tapegw-mover` + Phobos (`dir`) + Postgres.
Один тенант, одна копия, бакет без версий, **маленький объект** (крупные —
после среза, см. конец документа).

```
PUT объекта   → принят, лежит в landing (флаг landing)
архивация     → пачка ушла в Phobos, state=archived
вытеснение    → файл из landing удалён по online_until (ADR-0004)
RestoreObject → пачка прочитана, участник извлечён в cache
GET           → вернулись исходные байты (совпала sha256)
срок вышел    → GET отвечает InvalidObjectState
```

Восстановленные данные — **в cache, а не в landing** (ADR-0003): landing —
это незаархивированные данные, cache — временная копия после restore. Если их
смешать, janitor и учёт места перестанут различать «ещё не на ленте» и
«временная копия».

После истечения срока GET отвечает **`InvalidObjectState`** — другого кода в S3
для этого нет, и так сделано ещё в M2.

## Что уже есть

- `store/phobos`: `Put`/`Get`/`Delete`/`Stat`/`Extents` через cgo, владелец-горутина;
- `storetest`: общий набор сценариев для `fake` и настоящего Phobos;
- `mover`: протокол, реестр буферов, mTLS, клиент и сервер; `movertest` — стенд;
- `pack`: формат пачки (запись и чтение), детерминизм;
- `migrator`: выборка батча, запечатывание до отправки, возобновление с пачки,
  владение воркера, блокировка разобранной пачки, цикл архивации с проверкой
  ожидаемой `sha256`;
- `meta`: таблицы пачек, копий, носителей, восстановлений; очереди;
- `ci-dir`: контейнер с Phobos и `dir`-библиотекой поднимается одной командой.

## Чего нет

1. **Ни одного фонового воркера в `tapegw`.** `cmd/tapegw/main.go` migrator не
   создаёт, `internal/worker` — только `doc.go`. Цикл архивации существует как
   библиотека, в бинаре его никто не вызывает.
2. **Загрузчика участников пачки из landing нет** (`LoadItems` в migrator —
   «его пишет воркер M4», не написан).
3. **Клиента mover по конфигу `phobos.movers` нет** — есть клиент как класс.
4. **`RestoreObject` в бэкенде не реализован вовсе.** Таблица `restores` есть с
   миграции 0005, в `meta` функций под неё нет; `x-amz-restore` в HEAD/GET тоже.
5. **Нет пути архивации крупных объектов.** Migrator умеет только пачки; объект
   от 25 МБ на ленту сейчас не уйдёт никак. Для среза неважно, для MVP — обязательно.
6. **Бинаря `tapegw-mover` нет** — mover живёт только как библиотека и в тестах.

## Шаги среза: по одному PR

| # | Что | Готово, когда |
|---|---|---|
| **0** | `stand-status`: проверки DSS закрыты при сбое | неверный DSN → красный, а не «упущено»; тест на это |
| **S1** | `cmd/tapegw-mover`: конфиг, mTLS-сервер, слот, горутина-владелец `store/phobos` | в ci-dir mover стартует, `movertest`-клиент пишет и читает через него настоящий Phobos |
| **S2** | Воркеры в `tapegw`: запуск и остановка по сигналу, загрузчик из landing, клиент mover из `phobos.movers` | в ci-dir объект после PUT сам доходит до `archived`, пачка видна в `phobos extent list` |
| **S3** | Janitor, только вытеснение: `landing=false` → `unlink` по `online_until` | после срока файла в landing нет; HEAD — `GLACIER` без `x-amz-restore`; GET — `InvalidObjectState` |
| **S4** | `RestoreObject` в бэкенде + `restores` в `meta` + `x-amz-restore` | запрос создаёт строку, повтор продлевает срок, HEAD показывает `ongoing-request="true"` |
| **S5** | Минимальный recaller: `get` пачки через mover → извлечь участника → **cache** → `restored` | после restore GET отдаёт исходные байты |
| **S6** | Стенд и e2e: tapegw + mover + Phobos `dir` + Postgres, полный путь одним тестом | один прогон: те же SHA-256 на входе и на выходе; после срока restore — снова `InvalidObjectState` |

S1–S3 проверяются по отдельности, S4 от них не зависит, S5 опирается на S1–S4,
S6 — финал. Каждый шаг помещается в один заход.

### Что нужно знать заранее

- **В e2e-стенде `landing_min_retention` — секунды**, иначе вытеснения не
  дождаться. В бою он же обязателен и велик (24 часа по умолчанию).
- **Restore одного объекта из пачки читает с носителя всю пачку**: Phobos не
  умеет частичного чтения. Для среза это нормально, но mover отдаёт пачку
  целиком, а участника извлекает tapegw.

## После среза: путь до MVP

По важности для сохранности данных:

1. **Крупные объекты** — отдельный объект Phobos, атрибуты с `seq`.
2. **Две копии в боевом пути** — политика из конфига, догонка недостающих копий
   из landing и буфера mover.
3. **Deleter (M6)** — удаление версий и пачек в Phobos, учёт `live_bytes`,
   инвариант «файл участника запечатанной пачки не удаляется до её решения».
4. **Журнал на ленте** — изменения блокировок, удаления, снимки конфигурации
   бакетов. Без него восстановление после аварии вернёт старые сроки COMPLIANCE.
5. **Recaller полностью (M5)** — уровни, группировка по носителю, ограничение
   кэша, продление срока.
6. **1a-3 на mhVTL**, затем **`klipper-tlc` (M7)** и **манипулятор (M8)**.
7. **T3** — квоты и справедливость; затем **T4** — жизненный цикл тенантов.
8. **M9** — метрики, health, systemd-юниты для tapegw и mover, DR-процедуры.

Всё из фазы 2 предложения 0014 (reconciler, миграции поколений, слив магазинов,
repack) — после MVP.

## Правило проверки для каждого PR

Вопрос один: **приближает ли это к критерию своего шага в таблице выше.** Если
нет и это не исправление корректности — PR откладывается, а не идёт параллельно.
