# ADR-0005. Перезапись одного ключа: сериализация advisory-локом, не ретрай

- **Статус:** принято 2026-11-02
- **Дата:** 2026-11-02
- **Этап плана:** M2 (PutObject)
- **Связано:** `docs/ARCHITECTURE.md`, «Модель данных», раздел «Правила»
  (перезапись ключа);
  [`docs/reviews/2026-11-02-architecture-review.md`](../reviews/2026-11-02-architecture-review.md) §M1

## Контекст

Перезапись ключа — это транзакция «вставить новую строку `objects` с новым UUID и
в той же транзакции перевести старую текущую в `is_current=false, state='deleting'`».
Частичный уникальный индекс `objects_current (bucket_id, key) WHERE is_current`
гарантирует единство текущей версии.

Два параллельных PUT одного ключа обе транзакции читают «текущую» как
отсутствующую или как одну и ту же строку, и обе вставляют свою. Индекс одну
отклонит по `unique_violation`.

Первоначальное предложение в ревью было «ретрануть транзакцию при
`unique_violation`». Отклонено ревьюером, и аргумент веский: на **первой**
записи ключа текущей строки ещё нет, поэтому ретраить приходится не только
конфликт перезаписи, но и гонку «оба создают первый объект». Логика ретрая при
этом не сводится к «повтори» — нужно заново читать состояние и перепроверять, не
потеряли ли мы версию конкурента.

## Решение

Сериализовать запись по ключу **до** чтения состояния:

```sql
SELECT pg_advisory_xact_lock(hashtextextended($bucket || '/' || $key, 0));
```

в самом начале транзакции PutObject/CompleteMultipartUpload/DeleteObject для
этого ключа. Лок снимается коммитом, отдельного освобождения не требуется, и
падающий процесс не оставляет висячего лока.

Почему advisory lock, а не блокировка строки:

- работает и когда текущей строки нет — то есть закрывает гонку первой записи,
  а не только перезаписи;
- не зависит от наличия индекса и плана выполнения;
- `hashtextextended` даёт `bigint`, то есть один аргумент лока — без проблем с
  парой `(bucket_id, hashtext(key))`, где коллизия `hashtext` уже внутри строки.

Коллизии хеша означают лишнюю сериализацию между разными ключами, но не ошибку:
лок только упорядочивает, инвариант держит уникальный индекс.

Ожидание лока ограничено `db.advisory_lock_timeout` из конфига: зависший PUT
хуже отказа.

**Гонка PUT и DeleteBucket.** Advisory-лок сериализует только операции над
ключом, а `DeleteBucket` локов не берёт вообще — он работает с бакетом. Без
дополнительной меры PUT может вставить объект в бакет, который ровно в этот
момент помечают удалённым, и останется строка `objects`, висящая на
`deleted_at IS NOT NULL` бакете.

Поэтому транзакция PUT/Complete/DeleteObject после advisory-лока обязана взять
бакет на чтение:

```sql
SELECT id FROM buckets WHERE name = $1 AND deleted_at IS NULL FOR SHARE;
```

`DeleteBucket` берёт тот же бакет `FOR UPDATE` в своей транзакции — `FOR SHARE`
с ним конфликтует, а два параллельных PUT друг другу не мешают (оба берут
`SHARE`). Взаимоблокировки не возникает: путь `DeleteBucket` advisory-локов не
берёт вообще, то есть порядок захвата в нём короче.

## Последствия

- Все пути, меняющие текущую версию ключа (PutObject, CompleteMultipartUpload,
  DeleteObject, DeleteObjects, CopyObject поверх существующего), обязаны брать
  лок **первым** — иначе он ничего не сериализует. Это стоит проверить тестом на
  два параллельных PUT одного ключа, где оба обязаны вернуться 200, а
  «победившей» оказаться одна из версий.
- `DeleteObjects` (до 1000 ключей) обязан брать локи в **детерминированном
  порядке** (сортировка по хешу), иначе два батча с пересекающимися наборами
  ключей устроят взаимоблокировку.
- Настройка `db.advisory_lock_timeout` в конфиг (правило 9).
- Все пути изменения текущей версии ключа обязаны брать **сначала advisory-лок,
  потом `FOR SHARE` на бакет** — в этом порядке, иначе лок не сериализует то,
  для чего взят.
- См. также правило «ни одна транзакция Postgres не открыта во время вызова
  Phobos» в `AGENTS.md`: оно ограничивает время удержания и advisory-лока, и
  `FOR SHARE` на бакете.

## Отклонённые альтернативы

- **Ретрай по `unique_violation`.** Не покрывает гонку первой записи без текущей
  строки; требует повторного чтения и перепроверки, то есть сложнее, а не проще.
- **`SELECT … FOR UPDATE` на строке бакета.** Сериализует все ключи бакета
  последовательно: бэкап, льющий файлы в один бакет, упрётся в один лок на всё.
- **`INSERT … ON CONFLICT DO NOTHING` + проверка.** Не даёт «последний победил»:
  проигравший обязан увидеть свою запись как вытесненную, а не как ошибку.
