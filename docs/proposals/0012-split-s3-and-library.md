# Разделение сервера S3 и сервера библиотеки

- **Статус:** решение владельца 2026-11-05
- **Куда положить:** `docs/proposals/0012-split-s3-and-library.md`
- **Влияет на:** ADR-0021 (протокол tapegw ↔ mover) — требования ниже обязательны для
  него; ADR-0007 (mover как процесс); ADR-0020 (где собирается пачка); M4, M9

## Решение

S3 и ленточная библиотека работают на **разных серверах**. Деплой «всё на одном хосте»
остаётся допустимым, но как частный случай: mover подключается по loopback, а не по
локальным путям к файлам.

| Сервер S3 | Сервер библиотеки |
| --- | --- |
| versitygw + tapegw: S3, IAM, страж, очереди; migrator и recaller как планировщики | phobosd (LRS), `tapegw-mover` (по процессу на драйв) |
| landing (зеркало) и cache | локальный буфер (staging) на NVMe |
| Postgres (схема `tapegw` и DSS Phobos) — здесь или на отдельном сервере БД рядом | драйвы (SAS/FC), `klipper-tlc`, связь с роботом |
| **все ключи:** KEK, TEK, DEK | **ни одного ключа**, только шифротекст и обёрнутые DEK |

Граница «без ключей» из ADR-0007 и ADR-0014 становится физической: компрометация сервера
библиотеки не раскрывает данные клиентов.

## Почему именно так

**Буфер на сервере библиотеки, а не общий NFS.** Драйву нужен ровный поток в сотни МБ/с.
Если `phobos_put` читает файл через сеть, любая заминка сети останавливает драйв, лента
начинает «чистить» (shoe-shining) и изнашивается. Mover сначала принимает батч или пачку
по сети в локальный буфер и только после полного приёма и `fsync` вызывает
`phobos_put` с локального файла. Сеть и лента развязаны. Restore — в обратную сторону:
`phobos_get` в буфер, затем передача в cache сервера S3.

**Пачка собирается на стороне S3.** Индекс пачки требует `version_seq` и обёрнутых DEK из
БД. tapegw собирает пачку целиком (tar pax, индекс, футер) и передаёт mover готовым
потоком известного размера. Mover не знает формата пачки, не ходит в БД и не держит
ключей: он принимает поток, проверяет контрольную сумму, пишет в Phobos.

**Postgres рядом с S3.** tapegw обращается к БД на каждом S3-запросе, phobosd — заметно
реже. Задержка до БД важна для S3, поэтому БД стоит рядом с ним, а phobosd ходит к DSS
по сети.

## Требования к ADR-0021 (протокол tapegw ↔ mover)

Обязательны, независимо от того, разнесены ли серверы в конкретном деплое.

**Данные передаются в протоколе, а не путями.** Ни одна команда не содержит пути к
файлу на стороне tapegw. Put — поток байт с заранее объявленным размером и контрольной
суммой (SHA-256). Get — поток байт от mover к tapegw.

**Идемпотентность по UUID.** Каждая операция имеет UUID батча или пачки. Повтор той же
операции после обрыва:

- если запись в Phobos уже завершена, mover отвечает успехом и не пишет второй раз;
- если данные лежат в буфере частично, передача продолжается с места обрыва (докачка
  по смещению);
- состояние операции на стороне mover переживает его перезапуск.

**Обратное давление.** Mover сообщает, сколько места свободно в буфере. tapegw не начинает
передачу, которая не поместится. Переполнение буфера — штатное «подожди», а не ошибка
записи.

**Проверка целостности на приёме.** Mover считает SHA-256 принятого потока и сравнивает с
объявленной до вызова `phobos_put`. Несовпадение — отказ без записи на ленту.

**Аутентификация — взаимный TLS.** Оба конца проверяют сертификаты друг друга. Иначе любой
в сети может записать в архив мусор или прочитать шифротекст и обёрнутые DEK. Сертификаты
и их ротация — в документации деплоя (M9).

**Версия протокола** в рукопожатии. Несовместимые версии — отказ соединения с понятной
ошибкой, а не ошибки разбора посреди передачи.

**Долгие операции.** Запись батча на ленту длится минуты, ожидание драйва — десятки минут.
Протокол различает «принято в буфер», «записывается», «записано» и «ошибка», tapegw
опрашивает или получает уведомления. Обрыв соединения во время записи не отменяет запись:
результат забирается после переподключения по UUID операции.

**Что mover никогда не получает:** развёрнутые ключи, TEK, KEK, имена бакетов и объектов,
доступ к БД. Это проверяется тестом на набор полей сообщений протокола, по образцу теста
«в атрибутах нет TEK».

**Сколько mover на сервер.** По одному процессу на драйв (ADR-0007). Каждый слушает свой
адрес или регистрируется у tapegw; это решается в ADR-0021.

## Последствия для плана

- **ADR-0021** пишется по требованиям выше до кода mover.
- **M4:** migrator и recaller работают как клиенты протокола, а не как вызывающие
  локальной библиотеки. Буфер mover: размер, очистка после успешной записи, восстановление
  после перезапуска.
- **M9 (деплой):**
  - два варианта топологии в документации — один хост и два сервера;
  - пропускная способность сети между серверами не меньше суммарной скорости драйвов
    (например, четыре драйва по ~400 МБ/с требуют 25-гигабитного канала);
  - размер буфера на сервере библиотеки — не меньше двух целевых батчей или пачек на драйв;
  - выдача и ротация сертификатов mTLS.

## Тесты

- обрыв соединения посреди передачи → повтор по тому же UUID продолжает с места обрыва,
  на ленте один объект;
- обрыв после «записано», до получения ответа tapegw → повтор возвращает успех без второй
  записи;
- переполненный буфер → tapegw ждёт, ошибки записи нет;
- искажённый байт в потоке → mover отказывает по SHA-256, на ленту ничего не попадает;
- клиент без валидного сертификата → соединение отклонено;
- в сообщениях протокола нет полей с ключами, TEK и именами объектов.
