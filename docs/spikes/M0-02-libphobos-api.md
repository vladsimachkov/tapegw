# M0-02 — минимальная программа через libphobos_store

**Статус: закрыт.** Проверено на тестовом сервере (AlmaLinux 9.8, Phobos `2e3311f`
pkg 3.4.1, семейство `dir`, layout `raid1` с `repl_count=1`, библиотека `dirlib`,
два носителя).

Код спайков в основную ветку не попадает, поэтому ниже — существенные фрагменты.

## Что проверяли

Исходный список: `phobos_init`, батч `put` по fd с атрибутами, `getmd`, `get`,
`delete`. Плюс три вопроса ревью, из которых главный — первый:

1. Использует ли **один** вызов `phobos_put` с `n` объектами несколько драйвов
   параллельно.
2. Можно ли через API узнать носитель объекта (для группировки restore).
3. Как ведут себя `xt_rc` при частичном сбое батча.

## Ответ на главный вопрос: один вызов — один носитель

Батч из 20 объектов одним вызовом `phobos_put` при **двух** доступных носителях:

```
phobos_put rc=0  xd_rc=0  целей успешно: 20, с ошибкой: 0

    medium_id     | count
 -----------------+-------
  /var/lib/phobos |    20      <- все 20 extent'ов сюда
```

Второй носитель был полностью готов к записи — `unlocked`, `fs_status=empty`,
`put=t`, метка `.phobos_dir_label` на месте; `phobos dir status` показывал оба
устройства `unlocked`. То есть отказ выбрать второй носитель — не следствие
неготовности.

Проверка в обратную сторону: **два процесса одновременно**, каждый со своим
`phobos_init`:

```
процесс A: rc=0  xd_rc=0
процесс B: rc=0  xd_rc=0

    medium_id     | count
 -----------------+-------
  /var/lib/phobos  |    62     <- прирост 20 (процесс A)
  /var/lib/phobos2 |    20     <- прирост 20 (процесс B)
```

Разные контексты Phobos взяли разные носители.

**Вывод.** Гипотеза ревью подтвердилась: одна горутина ограничивает пропускную
способность одним драйвом. Параллельность по драйвам достигается **несколькими
процессами, каждый со своим контекстом Phobos** — не потоками внутри процесса и
не размером батча.

Это уточняет ADR-0006: «параллелизм через батч» верен внутри одного носителя
(батч на одну ленту — это и есть смысл батча), но для нескольких лент нужны
отдельные процессы. Значит `phobos.max_inflight` — это число процессов-воркеров,
каждый со своим `phobos_init`, а не число горутин и не размер батча.

Отдельно: это же объясняет, почему батч на одну ленту и задуман — `phobos_put`
собирает объекты на один носитель, чтобы не гонять картриджи.

## Вопрос 2: носитель объекта через API — нет

`phobos_getmd` возвращает только пользовательские атрибуты:

```
getmd ok: xd_rc=0 xt_rc=0
  атрибут tapegw:spike = 2
  атрибут tapegw:seq = 0
```

Сведений о расположении нет. Экспортируемые символы `libphobos_store` целиком:

```
phobos_init  phobos_fini  phobos_init_without_dss
phobos_put   phobos_get   phobos_getmd  phobos_setmd
phobos_delete phobos_undelete phobos_rename
phobos_copy  phobos_copy_rebuild  phobos_locate
phobos_store_object_list  phobos_store_object_list_free
phobos_store_copy_list    phobos_store_copy_list_free
pho_xfer_clean  pho_xfer_desc_clean
```

Ни одна из них не отдаёт extents. `phobos_store_copy_list` возвращает
`struct copy_info`, и там только метаданные копии:

```c
struct copy_info {
    char *object_uuid; int version; const char *copy_name;
    enum copy_status copy_status;
    struct timeval creation_time; struct timeval access_time;
};
```

А носитель живёт на слой ниже, в DSS:

```c
struct extent {
    char             *uuid;
    int               layout_idx;
    enum extent_state state;
    ssize_t           size;
    struct pho_id     media;      /**< identifier of the media */
    struct pho_buff   address;    /**< address on the media */
    ssize_t           offset;     /**< offset of the extent */
    ...
};
```

и достаётся через `dss_extent_get(handle, filter, ...)` из `pho_dss.h`.

**Вывод.** Чтобы группировать restore по лентам, tapegw обязан либо

- линковаться ещё и с `libpho_core` и держать собственный DSS-хендл
  (`dss_extent_get` с фильтром по uuid объекта), либо
- читать таблицу `extent` напрямую из Postgres.

Второе проще и не добавляет связывания, но обходит API Phobos и завязывает нас на
его схему — а схема меняется (`phobos_db migrate` это предполагает). Первое
соответствует правилу «не патчить Phobos» и держит нас на публичном интерфейсе,
но требует второго DSS-подключения.

Принято в [ADR-0008](../adr/0008-object-medium.md): носитель узнаётся один раз
при архивации через CLI `phobos extent list` и кладётся в `objects.phobos_medium`,
recaller в DSS не ходит.

## Вопрос 3: `xt_rc` не заполняется, батч не атомарен для вызывающего

Поле есть в заголовке:

```c
struct pho_xfer_target {
    ...
    int xt_rc;   /**< Outcome for this target's xfer. */
};
```

Но по факту **не заполняется ни при какой ошибке**.

Битый дескриптор у цели №2:

```
phobos_put rc=-9  xd_rc=-9          (EBADF)
  цель 0: xt_rc=0  ok
  цель 1: xt_rc=0  ok
  цель 2: xt_rc=0  ok   <- именно у неё битый fd
  цель 3: xt_rc=0  ok
  цель 4: xt_rc=0  ok
```

Объект уже существует (остальные новые):

```
phobos_put rc=-17  xd_rc=-17        (EEXIST)
  цель 0: xt_rc=0
  цель 1: xt_rc=0
  цель 2: xt_rc=0   <- этот уже существует
  цель 3: xt_rc=0
  цель 4: xt_rc=0
```

И что реально записалось при отказе (заранее заняты `atom-00..02`, батчем кладём
`atom-00..04`):

```
второй вызов: rc=-17 xd_rc=-17
  atom-00: ЕСТЬ      (был занят до вызова)
  atom-01: ЕСТЬ      (был занят до вызова)
  atom-02: ЕСТЬ      (был занят до вызова)
  atom-03: нет       <- не записан
  atom-04: нет       <- не записан
```

**Вывод.** Единственный сигнал об ошибке — возвращаемое значение вызова и
`xd_rc`, и это **первая** ошибка на всём батче. `xt_rc` использовать нельзя.
При отказе батча состояние отдельных объектов вызывающему неизвестно: нельзя
отличить «не записан» от «записан до ошибки».

Для tapegw это означает конкретные ограничения:

- батч надо считать **атомарным с точки зрения вызывающего**: либо `rc == 0` и
  записано всё, либо ошибка и нужен перепроверочный проход;
- чтобы знать, что именно легло, придётся после отказа перечитать DSS (см. вопрос
  2) или разбивать батч и повторять поштучно;
- размер батча — это не только «сколько объектов на одну ленту», но и цена
  повторной проверки после сбоя.

## Про сам cgo-путь (это тоже был предмет спайка)

cgo работает, но четыре вещи надо знать заранее, иначе первые часы уходят на
разбор странных ошибок.

**1. Профиль `xd_params.put.profile` библиотека не читает.** Поле есть в заголовке
и описано как «конфигурационный профиль», но в `src/store/store.c` на него никто
не ссылается — профиль разбирает CLI у себя и подставляет в запрос уже
конкретные `family` / `library` / `layout`. Через API без явных значений PUT
отвечает `-19 ENODEV` («No compatible device found for write alloc»), и из
вывода это не понять:

```c
static void xfer_set_put(struct pho_xfer_desc *x, enum rsc_family fam,
                         const char *library, const char *layout,
                         const char *copy_name) {
    x->xd_params.put.family = fam;
    x->xd_params.put.library = library;
    x->xd_params.put.layout_name = layout;
    x->xd_params.put.copy_name = copy_name;
}
/* + pho_attr_set(&x->xd_params.put.lyt_params, "repl_count", "1") */
```

**2. cgo запрещает передавать Go-указатель на память, содержащую Go-указатели.**
`pho_xfer_desc` содержит `xd_targets`, а цели содержат `xt_objid` и `xt_attrs`.
Паника выглядит так:

```
panic: argument of cgo function has Go pointer to unpinned Go pointer
```

Лечится выделением массива целей и дескриптора через `calloc` в C-памяти
(обёртки `xfer_targets()` / `xfer_new()`).

**3. cgo не раскрывает анонимные union.** `xd_params` приходит как `[128]byte`,
и `x.xd_params.put` не компилируется. Поля union задаются только C-хелперами.

**4. Линковка `libpho_core`.** Она ставится в приватный `/usr/lib64/phobos/` и
подтягивается через rpath у `libphobos_store`, поэтому `-lpho_core` линкер не
находит. Но `pho_attr_get` живёт именно там, и без явной ссылки получаем
`undefined reference to 'pho_attr_get'`. Рабочий набор флагов:

```
#cgo CFLAGS: -I/usr/include/glib-2.0 -I/usr/lib64/glib-2.0/include
#cgo LDFLAGS: -lphobos_store -L/usr/lib64/phobos -l:libpho_core.so.0 \
              -lglib-2.0 -lgthread-2.0 -Wl,-rpath,/usr/lib64/phobos
```

`-Wl,-rpath` обязателен: без него бинарь собирается, но падает на старте с
`libpho_core.so.0: cannot open shared object file`.

Ещё одна мелочь, на которую я потратил цикл: комментарии внутри C-преамбулы cgo
обязаны быть в стиле `//`. Вложенный `/* ... */` закрывает внешний блок
комментария, и Go потом выдаёт «non-declaration statement outside function body»
со ссылкой на строку C-кода.

## Дополнение по замечаниям ревью

Первый отчёт содержал два нечистых замера: тест с EEXIST падал на **первом**
объекте, поэтому до ошибки ничего не успевало записаться, а содержимое при EBADF
не проверялось. Доснял оба на том же стенде.

### А. Сбой в середине батча: не легло ничего

Батч из 5 объектов, у цели 2 битый источник (`xt_fd = -1`), цели 0, 1, 3, 4
полностью исправны и до ошибки не дошло:

```
phobos_put rc=-9 xd_rc=-9
проверка содержимого каждой цели:
  цель 0: НЕТ в каталоге
  цель 1: НЕТ в каталоге
  цель 2: НЕТ в каталоге  <- битый источник
  цель 3: НЕТ в каталоге
  цель 4: НЕТ в каталоге
```

Даже цели **до** ошибки не записаны. Для EBADF и EEXIST батч ведёт себя как
атомарный: либо всё, либо ничего. Проверка — не только факт наличия, но и md5
содержимого.

### Б. Обрыв процесса посреди put: getmd НЕДОСТАТОЧЕН

Здесь первая версия отчёта была бы опасна. Убийство процесса `SIGKILL` во время
записи объекта в 4 GiB:

```
--- вывод убитого ---
источник готов: 4096 MiB. кладу 4096 MiB, меня можно убить
Killed

$ phobos getmd kill/kill-00
tapegw:etag=etag-kill-00                      <- объект ЕСТЬ

$ phobos copy list -f json -o copy_name,status kill/kill-00
[{"copy_name": "source", "status": "incomplete"}]

на носителе остался частичный файл 497 MiB
```

**`getmd` возвращает объект, у которого копия `incomplete`.** Если проверять
только наличие по `getmd`, мы примем недописанный объект за архивный и потеряем
данные — ровно тот сценарий, на который вы указывали.

Для завершившегося put статус другой, так что проверка разграничивает:

```
успешный put  -> {"copy_name": "source", "status": "complete"}
обрванный put  -> {"copy_name": "source", "status": "incomplete"}
```

Отсюда исправленный алгоритм восстановления батча:

1. батч упал (или mover умер) → для каждого объекта: `getmd` **и** статус копии;
2. объект найден, атрибут `etag` совпал **и** `copy_status == complete` → `archived`;
3. иначе → обратно в `pending`;
4. на повторе исключать уже подтверждённые, иначе батч снова упрётся в EEXIST.

`phobos_store_copy_list` для этого и нужен — я зря записал его в «не помогает»:
для наличия он бесполезен, а для полноты необходим.

### Побочное: осиротевшие файлы на носителе

После прерванной записи на носителе остаётся файл, который ни на что не ссылается:

```
/var/lib/phobos2/.../kill_kill-00.<uuid>   497 MiB
```

в DSS на него нет ни одной ссылки (`select ... where address like '%<uuid>%'` → 0
строк). То есть аварийные записи **копят мусор на носителях**, и его должен кто-то
убирать. В штатном Phobos для этого есть состояние extent `orphan` и
`phobos extent list -s orphan`; в tapegw это обязанность janitor'а, и в плане M6
это надо явно прописать.

## Что из этого следует для плана

- **M4/M5:** воркеры — отдельные процессы `tapegw-mover`, у каждого свой
  `phobos_init`; вместо `phobos.max_inflight` два пула
  `phobos.movers.migrator` / `phobos.movers.recaller`. Оформлено в
  [ADR-0007](../adr/0007-mover-worker.md).
- **M4:** способ узнавать носитель объекта — [ADR-0008](../adr/0008-object-medium.md).
- **M4:** при отказе батча перепроверять, что легло, причём **обязательно по
  статусу копии**, а не только по наличию: `getmd` вретёт на прерванной записи.
  Полагаться на `xt_rc` нельзя вовсе.
- **M6:** janitor обязан чистить осиротевшие файлы на носителях — прерванная
  запись оставляет на носителе гигабайты, ни к чему не привязанные.
- Правило 13 (не держать транзакцию Postgres во время вызова Phobos) становится
  ещё важнее: батч на одну ленту — это минуты, и мьютекс сериализации в это время
  занят.
