# 0017. Страж тенанта: доступ по учётке из контекста, отказ — AccessDenied

- Статус: принято
- Дата: 2026-11-03
- Обсуждение: docs/proposals/0009-multitenancy-and-gaps.md, ADR-0009, ADR-0010

## Контекст

До этого ADR бэкенд не знал, кто делает запрос: `buckets.tenant_id` заполнялся
константой `DefaultTenantID`, и любой аутентифицированный ключ видел любые
бакеты. Нужен страж, который не даст тенанту коснуться чужого бакета — ни одним
из методов `backend.Backend`, включая те, которые versitygw вызывает сам в ходе
проверки доступа.

Кажется, что методы `backend.Backend` не получают учётку: в сигнатурах её нет.
Это не так, цепочка проверена по исходникам versitygw, fiber v3 и fasthttp:

```
middlewares/authentication.go:111   utils.ContextKeyAccount.Set(ctx, account)
  → httpctx.Set            → ctx.Locals("account", account)
  → fiber req.go:1161      → fasthttp.SetUserValue("account", account)
бэкенду передают ctx.RequestCtx(); fasthttp server.go:2868:
  RequestCtx.Value(key)    → ctx.UserValue(key)
```

Значит в любом методе бэкенда `ctx.Value("account")` даёт `auth.Account`.

Ложная зацепка, которую важно не использовать: posix читает
`ctx.Value("bucket-owner")`. Этот ключ versitygw ставит ровно в одном месте —
админский `CreateBucket` (`s3api/controllers/admin.go:197`). Обычный путь S3 его
не заполняет, страж на нём построить нельзя.

Отдельно: `middlewares/set-default-keys.go:33` кладёт пустой `auth.Account{}`
для анонимного запроса. У анонима `ProjectID` не «отсутствует», а равен нулю —
поэтому одно условие `ProjectID == 0` закрывает и анонимные запросы, и «забыли
проверить», без отдельной ветки.

## Решение

### 1. Отказ — `AccessDenied` (403), а не `NoSuchBucket`

Три причины:

- так ведёт себя AWS: обращение к чужому бакету даёт 403;
- скрывать существование бесполезно. Имена бакетов глобальные, и `CreateBucket`
  всё равно ответит `BucketAlreadyExists`. `NoSuchBucket` ничего не прячет, но
  вносит противоречие: бакета «нет», а создать его нельзя;
- сам versitygw отвечает `AccessDenied`, когда отказывает по ACL. Если страж
  отвечает так же, клиент не отличит по коду, какой слой сработал, — а смешение
  `NoSuchBucket` и `AccessDenied` наоборот ломает предсказуемость.

Различение «бакета нет» / «бакет чужой» делается вторым, дешёвым запросом и
только когда основной ничего не нашёл. На обычном пути (свой бакет) лишних
запросов нет.

### 2. Тенант — параметр функций `meta`, а не отдельная предпроверка

В `meta` вводится тип `TenantID`, и он становится **обязательным параметром**
всех функций, работающих с бакетом; каждый запрос получает
`AND tenant_id = $n`. Как устроен сам тип и почему он не может быть `int64` —
в пункте 3а.

Отдельная предпроверка «прочитать `buckets.tenant_id` и сравнить» отклонена:
это лишний запрос на каждый вызов, и главное — такую проверку можно забыть в
новом методе. С обязательным параметром забыть тенанта означает не собрать
программу.

Бэкенд один раз достаёт тенанта из контекста (`tenantFromContext`) и передаёт
его в `meta`.

### 3. Обход для системных ролей — по роли

`root` и `admin` проходят мимо стража, как они проходят мимо политик versitygw
(`authorizationApplies`, `auth/access-control.go:266`). Проверять **роль** из
учётки.

Проверено по исходникам, какую роль получает root в контексте (сомнение ревьюера
было обосновано: пустая роль означала бы отказ всему административному пути,
пусть и в безопасную сторону):

```
auth/iam.go:49          ролей три: RoleUser, RoleAdmin, RoleUserPlus — RoleRoot нет
authentication.go:44    rootAccount := auth.Account{..., Role: auth.RoleAdmin}
authentication.go:111   ContextKeyAccount.Set(ctx, account)
```

Значит root доезжает до бэкенда с `Role == RoleAdmin`, и проверки по роли
достаточно; отдельный флаг `IsRoot` из `AccessOptions` не нужен. То же в
`presign-auth.go:30` и `object-post-auth.go:54` — там root собирается так же.

Ранее здесь было написано «ключей у root может быть несколько» — неверно: root
задаётся одной парой ключей в конфиге (`RootUserAccess`/`RootUserSecret`).
Проверять роль всё равно правильнее, но по другой причине: роль — это то, что
versitygw сам использует для обхода проверок, и страж обязан опираться на тот же
признак, а не на своё отдельное сравнение ключей, которое может разойтись.

Для таких запросов тенант в запросах `meta` не фильтруется (явный
`TenantAllTenants`, см. пункт 3а).

### 3а. `TenantAllTenants` нельзя сделать подделываемым

Значение, отключающее фильтр тенанта, опасно само по себе: если кто-то подставит
его в обычном методе, изоляция исчезнет без единой ошибки. Поэтому:

- `TenantID` — **структура с неэкспортируемым полем**, а не `int64`. Написать
  `meta.TenantID(-1)` из чужого пакета невозможно в принципе.
- Значение «все тенанты» создаётся **одной функцией**, которую вызывает только
  страж (`backend/tenant_guard.go`).
- Тест проверяет, что эта функция упоминается только в файле стража. Это не
  линтер и не «красивая конвенция», а исполняемое ограничение: новый файл, который
  попробует её вызвать, роняет тест.

Обычные тенанты конструируются из `Account.ProjectID` той же функцией-конструктором
в страже; `meta` принимает `TenantID`, но создать «обходной» экземпляр сам не
может.

### 4. Частные случаи

- **`CreateBucket`** — бакета ещё нет, поэтому страж не проверяет, а назначает:
  `tenant_id` берётся из учётки. При `ProjectID == 0` — отказ.
- **`ListBuckets`** — фильтрует по тенанту, а не только по владельцу. Внутри
  тенанта владельцы будут разные, когда появятся несколько ключей.
- **`CopyObject`, `UploadPartCopy`** — два бакета, проверяются оба. Межтенантное
  копирование запрещено (ADR-0010).
- **Внутренние вызовы versitygw** — `GetBucketAcl`, `GetBucketPolicy`,
  `GetObjectLockConfiguration` versitygw вызывает сам, в ходе проверки доступа,
  с тем же контекстом. Страж обязан дать тот же отказ, что и на обычных методах,
  иначе чужой бакет станет различим по тому, на каком шаге пришёл отказ.

### 5. Тест-перебор проверяет поведение, а не наличие кода

Рефлексия по `backend.Backend` годится только чтобы получить список методов.
Решить «под стражем или нет» по исходному коду она не может. Поэтому каждый
метод из списка **реально вызывается** с контекстом чужого тенанта, и ожидается
`AccessDenied`.

Белый список — методы без бакета, каждый с причиной: `ListBuckets` (фильтрует, а
не проверяет), `CreateBucket` (назначает тенанта), `ListBucketsAndOwners`
(admin API), `Shutdown`, `String`.

Обязательна мутация: добавить в бэкенд метод с бакетом без стража и убедиться,
что тест-перебор на нём падает. Без этой проверки тест-перебор бесполезен ровно
так же, как бесполезен тест, который не ловит регрессию.

## 6. Кто платит за обход по роли: у учётки root нет ProjectID

Проверка по исходникам вскрыла дыру в самом ADR. `authentication.go:44`
собирает root так:

```go
rootAccount := auth.Account{Access: root.Access, Secret: root.Secret, Role: auth.RoleAdmin}
```

Поле `ProjectID` не заполнено, то есть у root он **равен нулю** — тому самому
значению, по которому ADR отказывает анонимам. Буквальное прочтение
«сначала проверяем `ProjectID == 0`» отрезало бы от стража весь админский
путь: root не смог бы ни прочитать, ни создать бакет. Отказ в безопасную
сторону, но ломающий продукт и все e2e-проверки, которые поднимаются под root.

Поэтому порядок проверок в страже зафиксирован явно:

1. учётки в контексте нет → `AccessDenied`;
2. `Role == RoleAdmin` → обход (см. п. 3);
3. `ProjectID == 0` → `AccessDenied`;
4. иначе — тенант из учётки.

Роль проверяется **до** нуля `ProjectID`, а не после.

Отсюда следствия, о которых иначе забудут:

- **Бакеты, созданные root, живут в тенанте `default` (id = 1).** Бакет обязан
  принадлежать одному тенанту, «все тенанты» как владелец бакета — это дыра, а
  не решение, поэтому учётке с обходом по роли при создании бакета назначается
  тенант `default` (в коде — `meta.AdminTenantID`, не магическая единица в теле
  функции). Когда появится админский вывод тенантов, создавать бакет за root
  нужно будет с явным тенантом — константу видно и она гуглится.
- **Обычный ключ с `ProjectID == 0` отвергается, в том числе на `CreateBucket`.**
  Аноним не получает права заводить бакеты: отказ на назначении тенанта —
  часть стража, а не исключение из него.
- **Объект наследует тенанта бакета, а не учётки.** Иначе запись в чужой бакет
  (которую страж уже не пропустил бы) ещё и спорила бы с FK на `tenants`, а
  учётка с обходом по роли не смогла бы писать ни в один бакет.
- **Стенды обязаны выдавать обычным учёткам ненулевой `projectID`.** Учётка с
  нулём в стенде означает «страж откажет до всякой политики», и проверки
  доступа начинают проверять отказ стража вместо политики — тихая подмена,
  из-за которой тесты остаются зелёными и ничего не проверяют. В CI userplus
  переведён с `projectID: 0` на `projectID: 1`, в тот же тенант, что и бакеты
  root: иначе проверка «политика разрешает чтение» не сходится — страж
  отказывает раньше политики.

## Следствия

- `DefaultTenantID` из `internal/meta/tenant.go` упраздняется: тенант приходит из
  учётки. `DefaultPoolID` остаётся до T2/M4.
- Все запросы `meta`, работающие с бакетом, получают дополнительный предикат.
  Для запросов **внутри бакета** это почти дёшево: отбор идёт по `bucket_id`, а
  `tenant_id` отсекает одну-две строки. Ценен предикат там, где бакета в условии
  нет — в очередях и в учёте:
  - `objects_tenant_queue` — `(pool_id, tenant_id, next_try_at)`, ведущая колонка
    `pool_id`, а не `tenant_id` (так стало после ревью миграции 0005: migrator
    сначала батчит внутри пула, ADR-0013);
  - `objects_tenant (tenant_id) INCLUDE (size)` — индекс-only скан для
    ежедневной сверки учёта.
- **Публичного доступа нет — по построению.** Анонимная учётка имеет
  `ProjectID == 0`, а страж отказывает при `TenantAnonymous` до всякой политики
  бакета. Значит `AccessDenied` придёт даже тогда, когда политика разрешает
  публичное чтение. Это согласуется с ADR-0010, где гранты `AllUsers` и `*`
  запрещены, но здесь ограничение сильнее и оно не в политике, а в страже:
  **публичные бакеты не поддерживаются по построению**. Кто-то неизбежно
  попробует разрешить `AllUsers` и не поймёт, почему запросы отклоняются, —
  поэтому записано явно.
- Тесты `meta`, которые готовили данные без тенанта, перестраиваются: тенант
  теперь часть контракта каждой функции.
